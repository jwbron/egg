# Plan: Design formal BRC protocol state machine with action guards

## Summary

The BRC consensus protocol in `peer_consensus.py` has accumulated individual fixes for
specific deadlock scenarios (#1405, #1576, #1411) without a formal specification of when
each action is valid. Issue #1579 calls for a formal state machine with explicit action
guards (preconditions), a state transition diagram, protocol invariants, and evaluation
of existing recovery mechanisms.

This plan decomposes the work into 4 phases within a single PR: (1) define and enforce
action guards for all protocol actions, (2) implement auto re-propose on producer
push/commit, (3) add a reviewer "changes reviewed" confirmation guard, and (4) add
comprehensive tests and documentation.

## Approach

The implementation follows an incremental guard-addition strategy rather than a rewrite.
Each action handler (`handle_propose`, `handle_ack`, `handle_nack`, `handle_withdraw`,
`handle_confirmed`, `handle_re_propose`) already has *some* guards. We add the missing
guards identified in the issue, along with two new behavioral features: auto re-propose
on push/commit and a "changes reviewed" reviewer confirmation guard.

### Key decisions

1. **Guards as precondition checks, not exceptions**: Follow the existing pattern where
   guards return `{"status": "pending_acks", "message": ...}` on failure rather than
   raising exceptions. Callers check the status field.

2. **No structural refactor of PeerConsensusTracker**: The tracker is 1233 lines and
   well-tested (195+ tests). We add guards to existing handlers, not extract a new state
   machine abstraction. The state machine is *documented* formally but *implemented*
   via guards in the existing handler methods.

3. **Auto re-propose via signal layer**: The "push/commit triggers re-propose" feature
   is implemented in `orchestrator/routes/signals.py` where push/commit signals already
   arrive. This keeps the tracker stateless with respect to git operations.

4. **Recovery mechanisms kept as defense-in-depth**: `_un_confirm_stale_reviewers()` and
   `_invalidate_pre_proposal_acks()` remain. Even with comprehensive guards, race conditions
   between agents mean recovery paths add safety. The formal spec documents when they fire
   and why they're still needed.

5. **State transition diagram as module docstring**: The formal state machine spec lives
   as an extended docstring at the top of `peer_consensus.py`, serving as both documentation
   and the canonical reference for guard implementation.

## Phase breakdown

### Phase 1: Action guards and state machine specification

**Goal**: Add missing precondition guards to all 6 protocol actions and document the
formal state machine with preconditions, transitions, and postconditions.

This is the core of the issue. Each handler gets explicit guards that validate the
current state before mutating it.

**Guard additions by handler:**

- **`handle_propose`** — Add guard: producer must be in WORKING state (not already PROPOSED
  or CONFIRMED). Current code only checks "not fully ACKed" which is incomplete.
- **`handle_ack`** — Add guard: producer must be in PROPOSED state (prevents ACK while
  producer is WORKING). Add guard: ACK version must match current proposal version
  (prevents stale ACKs at ACK time, not just at confirmation time).
- **`handle_nack`** — Add guard: producer must be in PROPOSED state. Add guard: reviewer
  must not NACK a producer that hasn't proposed yet (version 0).
- **`handle_confirmed`** — For producers: add unresolved-NACK check (producer shouldn't
  confirm if any reviewer NACKed and producer hasn't re-proposed). This is the symmetric
  case to the reviewer guard added in #1576. For reviewers: add "all changes reviewed"
  guard (Phase 3).
- **`handle_withdraw`** — Add guard: producer must be in PROPOSED state (withdrawing
  from WORKING is a no-op that shouldn't mutate state).
- **`handle_re_propose`** — Add guard: producer must have been NACKed (at least one
  NACKED entry) OR this is triggered automatically by push/commit (Phase 2).

**ApprovalMatrix helpers:**

- `get_nack_entries_for(producer)` — Returns all NACKED entries for a producer.
- `has_unresolved_nacks_as_producer(producer)` — True if any reviewer has NACKed and
  producer's current version == the NACKed version (producer hasn't re-proposed since).
- `get_latest_review_versions(reviewer)` — Returns dict of producer→version for the
  reviewer's latest ACK on each producer (for "changes reviewed" guard).

### Phase 2: Auto re-propose on push/commit

**Goal**: When a producer pushes or commits new changes after proposing, automatically
trigger a re-proposal that invalidates existing reviews and forces re-review.

The issue states: "any push/commit by a producer should automatically trigger a re-propose,
invalidating existing reviews and requiring reviewers to re-review the new changes."

This is implemented in the signal layer (`signals.py`) because push/commit signals arrive
there. The flow:

1. Push/commit signal arrives for a producer agent
2. Signal handler checks if producer is in PROPOSED or CONFIRMED state
3. If so, automatically calls `tracker.handle_re_propose()` with the new commit SHA
4. Sends `CONSENSUS_RE_REVIEW` messages to all affected reviewers
5. Reviewers' ACKs are invalidated; they re-enter REVIEWING state

### Phase 3: Reviewer "all changes reviewed" confirmation guard

**Goal**: Prevent a reviewer from confirming if any producer has produced new changes
since the reviewer's last review.

The issue states: "All producer changes must have been reviewed — a reviewer cannot
confirm if any producer has produced new changes since the reviewer's last review."

This guard compares each producer's current proposal version against the version the
reviewer ACKed. If a producer has re-proposed (version incremented) since the reviewer's
last ACK, confirmation is rejected.

This extends the existing version-match guard (lines 422–459) which currently only catches
stale ACKs on *different* versions. The new guard catches the case where a producer
re-proposed *after* the reviewer's ACK but the reviewer hasn't re-reviewed yet. Combined
with the auto re-propose from Phase 2, this ensures all pushes/commits are reviewed.

### Phase 4: Tests and documentation

**Goal**: Comprehensive test coverage for all new guards, auto re-propose behavior, and
the formal state machine transitions. Documentation of the state transition diagram,
invariants, and recovery mechanisms.

## Invariants (from issue)

These invariants must hold at all times and will be validated in tests:

1. No agent in CONFIRMED with an unresolved NACK where producer hasn't re-proposed
2. No agent in CONFIRMED with a stale ACK (version mismatch)
3. No reviewer in CONFIRMED if any producer has changes that haven't been reviewed
4. `is_fully_acked` must be consistent with the actual matrix state
5. `_confirmed` set must only contain agents where both producer and reviewer phases
   (if applicable) are CONFIRMED

## Dependency ordering

```
Phase 1 (guards + spec) ← Phase 2 (auto re-propose) ← Phase 3 (changes-reviewed guard) ← Phase 4 (tests + docs)
```

Phase 2 depends on Phase 1 because auto re-propose uses the state guards to determine
when to trigger. Phase 3 depends on Phase 2 because the "changes reviewed" guard is
meaningful only when push/commit auto-triggers re-proposals (otherwise the version
wouldn't increment on new changes). Phase 4 depends on all prior phases.

## Test strategy

### Automated tests

1. **Guard unit tests** (`test_brc_state_machine_guards.py`): One test per guard per handler.
   Test both the rejection path (guard fires, returns error) and the pass-through path
   (guard allows action). ~30 test cases covering:
   - propose: rejects if not WORKING, allows if WORKING
   - ack: rejects if producer not PROPOSED, rejects stale version, allows current version
   - nack: rejects if producer not PROPOSED, rejects if version 0
   - withdraw: rejects if not PROPOSED, allows if PROPOSED
   - confirmed (producer): rejects with unresolved NACKs, allows when fully ACKed
   - confirmed (reviewer): rejects with un-reviewed changes, allows when all reviewed
   - re_propose: rejects if no NACK and not auto-triggered

2. **Auto re-propose tests** (`test_brc_auto_repropose.py`): ~10 test cases covering:
   - Push after proposal triggers re-propose
   - Push while WORKING does NOT trigger re-propose
   - Re-propose invalidates all reviewer ACKs
   - Reviewers receive CONSENSUS_RE_REVIEW messages
   - Reviewer cannot confirm until re-reviewing
   - Full cycle: propose → push → auto-repropose → re-review → confirm

3. **Integration tests** (additions to `test_peer_consensus_integration.py`): ~10 test
   cases covering full scenarios from related issues:
   - #1576 scenario with new guards
   - #1405 scenario with version-match at ACK time
   - #1411 scenario with withdraw state validation
   - #1598 scenario: reviewer confirms while producer has zero commits
   - Invariant validation across multi-agent scenarios

4. **Existing test updates**: Some existing tests may need minor adjustments if they
   relied on the absence of guards (e.g., tests that ACK before producer proposes).

### Manual verification

- Run full test suite: `make test` — verify no regressions
- Run orchestrator tests specifically: `pytest orchestrator/tests/ -v`
- Review state machine docstring for accuracy against implementation

## Risk assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| New guards break existing valid flows | MEDIUM | HIGH | Run full test suite; guards return errors (not exceptions), so callers can handle gracefully |
| Auto re-propose creates excessive re-review cycles | LOW | MEDIUM | Only triggers on actual push/commit, not on every signal; throttle via existing cooldown |
| Dual-role agents (tester) interact unexpectedly with new guards | MEDIUM | MEDIUM | Dedicated test cases for tester as both producer and reviewer |
| Existing tests rely on guard-less behavior | MEDIUM | LOW | Update affected tests in Phase 4; changes are backward-compatible error responses |
