# Plan: Design formal BRC protocol state machine with action guards

> Revision 2 — Addresses reviewer NACK: (1) hybrid transition guard table per HITL
> decision-6, (2) debounce/rate-limiting/feature flag for auto-re-propose, (3) excuse_producer
> escape hatch for non-delivering producers.

## Summary

The BRC consensus protocol in `peer_consensus.py` has accumulated individual fixes for
specific deadlock scenarios (#1405, #1576, #1411, #1598) without a formal specification
of when each action is valid. Issue #1579 calls for a formal state machine with explicit
action guards (preconditions), a state transition diagram, protocol invariants, and
evaluation of existing recovery mechanisms.

This plan decomposes the work into 4 phases within a single PR: (1) define a transition
guard table and enforce action guards, (2) implement excuse_producer escape hatch and
tighten zero-version confirm guard, (3) implement auto re-propose on push/commit with
debounce and feature flag, and (4) add comprehensive tests and documentation. Phases are
ordered by increasing risk per the risk analyst's recommendation.

## Approach

The implementation uses **Approach C (Hybrid Transition Guard Table)** from the architect
analysis, aligned with **HITL decision-6** which selected "Hybrid: transition table for
state, handlers for side effects." This means:

1. A **transition guard table** — a Python dict mapping `(action, role_type)` to a list
   of named guard functions — is defined as the authoritative protocol specification.
2. Each existing handler method **checks the guard table** before executing its
   side effects (event emission, message bus, matrix updates).
3. The handlers themselves are NOT replaced — they remain for side effects. The guard
   table gates them.

### Key decisions

1. **Hybrid transition table per HITL decision-6**: A module-level `GUARD_TABLE` dict
   maps `(action, role_type) → list[guard_fn]`. Each guard function takes the tracker
   and relevant args, returns `None` (pass) or a rejection dict. Handlers call
   `_check_guards(action, role_type, ...)` before mutating state. This is the single
   source of truth for "when is action X valid?"

2. **Guards as precondition checks, not exceptions**: Follow the existing pattern where
   guards return `{"status": "...", "message": ...}` on failure rather than raising
   exceptions. The `_check_guards()` utility returns the first rejection or `None`.

3. **Auto re-propose with debounce, max counter, and feature flag (default OFF)**:
   Addresses RISK-1 (HIGH) from risk analysis. Debounce window (configurable, default
   60s), max auto-re-propose counter per producer (default 5), and feature flag
   (`auto_repropose_enabled`, default `False`). This prevents the infinite re-proposal
   loops and version inflation identified by the risk analyst.

4. **excuse_producer escape hatch**: Analogous to existing `excuse_reviewer()` (line 686).
   Allows HITL-gated removal of a non-delivering producer from the review graph so
   reviewers can proceed. Required to safely tighten the zero-version NACK confirm guard.

5. **Recovery mechanisms retained as defense-in-depth**: `_un_confirm_stale_reviewers()`
   and `_invalidate_pre_proposal_acks()` remain with counters/metrics to detect if they
   fire (indicating guard gaps). Per HITL decision-4 and risk analyst M-4-1.

6. **Invariant checker (assert_invariants)**: A method on PeerConsensusTracker that validates
   all 6 invariants after every state-mutating operation. Enabled in tests, opt-in in
   production via flag. Per architect component_3 and risk analyst M-4-2.

## Phase breakdown

### Phase 1: Transition guard table, action guards, and state machine specification (LOW risk)

**Goal**: Define the formal guard table, add missing guards, implement invariant checker,
and document the state machine. This phase formalizes existing behavior and adds missing
guards — it does NOT change trigger models or add new features.

The guard table is a module-level `GUARD_TABLE` dict:
```python
GUARD_TABLE: dict[tuple[str, str], list[GuardFn]] = {
    ("propose", "producer"): [guard_producer_in_working_state, guard_not_fully_acked, guard_valid_attestation],
    ("ack", "reviewer"): [guard_edge_exists, guard_producer_proposed, guard_version_match, guard_valid_review],
    ("nack", "reviewer"): [guard_edge_exists, guard_producer_proposed, guard_valid_review],
    ("confirm", "producer"): [guard_is_fully_acked, guard_no_unresolved_nacks_as_producer],
    ("confirm", "reviewer"): [guard_all_reviewed, guard_no_stale_acks, guard_no_unresolved_nacks, guard_no_zero_proposal_producers, guard_all_changes_reviewed],
    ("withdraw", "producer"): [guard_producer_in_proposed_state, guard_reason_required, guard_cooldown, guard_flip_flop_limit],
    ("re_propose", "producer"): [guard_has_nacks_or_auto_triggered, guard_valid_attestation],
}
```

Each handler calls `_check_guards()` which iterates the guard list and returns the first
rejection, or `None` if all pass. The guard table IS the protocol specification.

### Phase 2: excuse_producer and zero-version confirm guard (MEDIUM risk)

**Goal**: Implement `excuse_producer()` escape hatch and tighten the reviewer confirm
guard to block when any producer has version 0 (never proposed). The escape hatch
ensures non-delivering producers don't permanently block consensus.

`excuse_producer()` follows the pattern of existing `excuse_reviewer()` (line 686):
removes the producer from the review graph for all reviewers, allowing them to proceed
without that producer's deliverable. Gated behind HITL decision.

The zero-version guard (`guard_no_zero_proposal_producers`) is added to the confirm
reviewer guard list in the GUARD_TABLE. It rejects confirmation if any assigned producer
has proposal_version == 0. Combined with `excuse_producer()`, this closes the #1598 gap
without creating permanent blocks.

### Phase 3: Auto re-propose on push/commit with safety mechanisms (HIGH risk)

**Goal**: Detect when a producer pushes new commits after proposing and automatically
trigger a re-proposal. Gated by feature flag (default OFF), debounced (60s window),
and rate-limited (max 5 auto-re-proposes per producer).

**Safety mechanisms** (per risk analyst RISK-1 mitigations):
- **Debounce** (M-1-1): Record `_last_auto_repropose_timestamp[producer]`. Skip if
  within configurable `auto_repropose_debounce_seconds` (default 60).
- **Max counter** (M-1-3): `_auto_repropose_counts[producer]` increments on each auto
  trigger. After `max_auto_repropose` (default 5), log warning and require explicit
  re-propose from agent.
- **Feature flag** (M-1-4): `auto_repropose_enabled` parameter on PeerConsensusTracker
  (default `False`). Must be explicitly enabled per-pipeline or globally.
- **Overlap-aware** (M-1-2): Only trigger if pushed files overlap with proposed
  artifacts (using `invalidate_overlapping_acks()` check). Skip if no ACKs would be
  invalidated.

The `guard_all_changes_reviewed` confirm guard (already in the GUARD_TABLE from Phase 1)
provides the blocking mechanism at confirm time. Auto re-propose provides the proactive
notification. Together they ensure all pushes are reviewed.

### Phase 4: Tests and documentation

**Goal**: Comprehensive test coverage (~60 new test cases) for guards, invariants,
auto re-propose with debounce, excuse_producer, and formal documentation.

## Invariants

These invariants are enforced by `assert_invariants()` and tested:

1. **INV-1**: No agent in CONFIRMED with an unresolved NACK where producer hasn't re-proposed
2. **INV-2**: No agent in CONFIRMED with a stale ACK (version mismatch)
3. **INV-3**: No reviewer in CONFIRMED if any assigned producer has version == 0 (unless excused)
4. **INV-4**: `is_fully_acked` must be consistent with the actual matrix state
5. **INV-5**: `_confirmed` set must only contain agents where both producer and reviewer
   phases (if applicable) are CONFIRMED
6. **INV-6**: No reviewer in CONFIRMED if any producer has pushed commits after the
   reviewer's ACK (tracked via commit SHA comparison)

## Dependency ordering

```
Phase 1 (guard table + guards) → Phase 2 (excuse_producer + zero-version guard) → Phase 3 (auto re-propose + debounce) → Phase 4 (tests + docs)
```

Phase ordering follows risk analyst recommendation: LOW → MEDIUM → HIGH. Phase 2 depends
on Phase 1 because `excuse_producer` needs the guard table infrastructure. Phase 3
depends on Phase 2 because auto re-propose combined with the zero-version guard needs
the excuse_producer escape hatch. Phase 4 depends on all prior phases.

   - Invariant checker: verify all 6 invariants after complex multi-agent scenarios

   - Feature flag OFF: push does NOT trigger re-propose
   - Feature flag ON: push after PROPOSED triggers re-propose
   - Debounce: rapid pushes within window trigger only one re-propose
   - Max counter: after limit, auto-re-propose stops and requires explicit action
   - Overlap-aware: push to non-overlapping files does NOT trigger re-propose
   - Full cycle: propose → push → auto-repropose → re-ACK → confirm
   - Reviewer cannot confirm until re-reviewing after auto re-propose

3. **Integration scenarios** (additions to `test_peer_consensus_integration.py`, ~10 cases):
   - #1576 scenario with new guards
   - #1405 scenario with version-match at ACK time
   - #1411 scenario with withdraw state validation
   - #1598 scenario: reviewer blocked by zero-version guard, then excuse_producer unblocks
   - excuse_producer: crashed producer excused, reviewer can confirm
   - excuse_producer with dual-role agent (tester)

4. **Existing test updates**: Adjust tests that relied on guard-less behavior.

## Risk assessment

| Risk | Severity | Mitigation |
|------|----------|------------|
| Auto re-propose infinite loops (RISK-1) | HIGH | Feature flag (OFF), debounce (60s), max counter (5), overlap-aware triggering |
| All-changes-reviewed liveness hazard (RISK-2) | HIGH | Feature flag gates auto-re-propose; without it, version only increments on explicit re-propose |
| Zero-version guard blocks non-delivering producer (RISK-3) | HIGH | excuse_producer() escape hatch, gated behind HITL decision |
| Recovery mechanism removal causes regression (RISK-4) | MEDIUM | Retained as defense-in-depth with counters (M-4-1) |
| Tracker reconstruction replays auto-re-propose (RISK-5) | MEDIUM | Tag auto-re-propose messages with metadata; apply debounce during replay |
| New guards break existing valid flows | MEDIUM | Guard table returns errors (not exceptions); full test suite validation |
