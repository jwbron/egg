# Implementation plan — issue #3393 (multi-repo pipelines: coordinated PRs across repositories in one pipeline)

Task-planner plan, grounded on the ratified refine analysis
(`.egg-state/drafts/3393-analysis.md`, v5) and re-verified against the live
worktree (HEAD `f085265b7`). All eight refine acceptance criteria and all six
binding operator rulings (plus HITL cq-1) are carried into the slices below.

## Orientation

Every slice in this pipeline lives in the **egg repo** (`jwbron/egg`) — this
pipeline *builds* multi-repo support; it does not itself span repos. So each
slice's `repo` is `jwbron/egg` and there is no cross-repo merge-sequencing to
exercise inside this plan; the merge-sequencing hold (slice 5) is built and
unit-tested here, not driven end-to-end.

The refine analysis established the central, verified thesis: **the single-repo
assumption is concentrated, not pervasive.** The gateway worktree list,
per-repo credentials, `create_slice_pr(repo=...)`, and repo-agnostic push
policy already exist. The real work is (a) giving the persisted contract a
**repo dimension** (`Slice.repo`) via a schema migration, (b) stopping the
**`repos[0]` collapse** at the three enumerated sites, (c) **list-shaped
submission** with uniform-visibility and uniform-auth validation, (d) routing
each slice's PR / work-branch / context-PR to the slice's repo, and (e) a
**merge-sequencing hold** (auto draft→ready on upstream PR merge; HITL for
beyond-merge-state blocks).

## Why a single serialized chain

Five of the six slices edit `orchestrator/routes/pipelines.py`, and slices 1
and 3 both edit `orchestrator/models.py`. Per the #3046 file-overlap validator,
slices sharing a file must be ordered along one dependency chain or their
integration branches collide at merge. Rather than thread a partial DAG through
the one mega-file, the slices form a **single linear chain**
`slice-1 → slice-2 → slice-3 → slice-4 → slice-5 → slice-6`. The chain is also
value-ordered: the schema foundation lands first (everything reads it), then
submission, then the env/collapse fix, then PR routing, then the hold, then
per-repo gate scoping.

The chain forks off nothing exotic — each slice's integration branch is cut
from its parent's tip, so the later slice always sees the earlier slice's edits
to the shared file.

## Slice detail

### Slice 1 — Repo dimension across the two model layers (foundation)
The load-bearing gap, split across the two model layers per the ratified
architect design (aeb3528) and risk_analyst R1. **Contract layer**
(`shared/egg_contracts/models.py`): `Slice.repo: str | None = None` is added and
`Contract.schemaVersion` bumps `1.3 → 1.4` as a **pure additive after-stamp**
(`_migrate_schema_version_to_1_4`, mirroring `_migrate_schema_version_to_1_3`
verbatim — guarded on "1.3", idempotent, **no field mutation**). Crucially the
contract model carries **no repo field** and cannot see the orchestrator
Pipeline, so `Slice.repo` stays `None` on a legacy load — the migration does
**not** fill it. **Orchestrator layer** (`orchestrator/models.py`): `RepoSpec`
+ `Pipeline.repos: list[RepoSpec]` (validator synthesizes the list from a legacy
singleton and mirrors `repos[0]` back for legacy readers), a `primary_repo`
property, and a **runtime resolver** `resolve_slice_repo(slice, pipeline)` where
absent-`Slice.repo` ⇒ primary is resolved (it needs the pipeline as a second
input, which the contract model cannot provide). N=1 pipelines behave
identically. Nothing downstream may write `Slice.repo` until this lands — hence
it is the chain root.

### Slice 2 — List-shaped submission + uniform-visibility/auth validation
`submit_task` and `POST /api/v1/pipelines` accept a **list** of
`{repo, base_branch}` (a bare single repo stays accepted, back-compat). New
submission-time validation rejects (a) mixed-visibility sets and (b)
mixed-auth-mode sets, each with an actionable error — reusing
`get_repo_visibility` and per-repo `get_auth_mode`. Same-name repo sets are NOT
rejected (operator ruling #6 mandates the `owner/repo` re-key instead). One repo
is designated **primary** (first in the list unless flagged) for pipeline
naming and as the slice-default repo.

### Slice 3 — Stop the `repos[0]` collapse; owner/repo-keyed worktree map
Removes all three enumerated collapse sites —
`kubernetes_spawner/_spawn.py:452/:464` (+ `EGG_PIPELINE_REPO` at `:523`),
`commit_authorship_store.py:932-933`, `routes/pipelines.py:732` — and exposes
the **full** repo→worktree map to the agent environment, **re-keyed by full
`owner/repo`** (operator ruling #6; today `_worktree.py:74-79` keys by bare
name and would collide on `ownerA/foo` vs `ownerB/foo`). A ratchet test plus a
`grep -rn 'repos\[0\]'` sweep guard against regressions and catch any
un-enumerated site (the sweep must continue to treat the `len(repos)==1`-guarded
`sandbox/egg_lib/sdlc_hitl.py:82` as NOT a collapse).

### Slice 4 — Slice-PR routing + lazy per-repo work branch & context PR
Each slice's PR is created in `slice.repo` (route `create_slice_pr` to
`slice.repo`; today the caller passes the singleton). **Lazy-per-repo** (operator
ruling #1): every repo with ≥1 slice gets its own `egg/<id>/work` branch and its
own context PR; submitted repos that end up with no slices get neither. PR
descriptions cross-reference sibling PRs in the pipeline.

### Slice 5 — Cross-repo merge-sequencing hold (cq-1 two-tier)
Implements the operator-resolved (cq-1) two-tier model with **fully pinned
failure semantics** (architect layer_6 / reviewer_plan R3). **Tier A
(automated):** a cross-repo dependent slice is developed in parallel; its PR
opens as **draft** and a poll on the existing reconcile cadence detects the
upstream PR's merge via the **merged boolean / `mergedAt`** (`gh pr view --json
state,mergedAt`, *not* head-SHA equality — a squash/rebase merge changes the
SHA) and **auto-marks the dependent PR ready** (new `mark_pr_ready` gateway verb
wrapping `gh pr ready`). Two failure terminals are pinned: an upstream PR
**closed-unmerged** does **not** auto-ready — it escalates to a **HITL hold**;
and the poll is **bounded** — a never-merging upstream that exceeds the bound
likewise escalates to a HITL hold rather than leaving the PR draft indefinitely.
**Tier B (HITL):** a distinct hold type for beyond-merge-state conditions (a
release/publish of the upstream repo, a version-pin choice, or a genuine
cannot-continue development block) is held and released by a HITL decision,
never by programmatic detection. Dependencies do **not** serialize development —
they bite only at merge-readiness.

### Slice 6 — Per-repo test-gate + reviewer-diff scoping + conventions
The slice↔repo 1:1 rule makes this mechanical (operator rulings #3, #5): the
test gate runs in the **slice's repo worktree only**, the reviewer diff is `git
diff` in that worktree against **that repo's** base, and the agent works with
cwd in the slice's repo worktree under **that repo's** `CLAUDE.md`, linters, and
check commands — egg's `make lint`/`make test` apply only to slices whose repo
is egg. Documenter updates the multi-repo docs to describe the shipped model.

## Risks / notes for the architect and reviewers

- **The migration must land before any producer writes `Slice.repo`.** Chain
  root ordering enforces this.
- **The contract migration is a pure additive stamp, not a field-filler**
  (risk_analyst R1 / architect aeb3528): the Contract model has no repo field
  and cannot see the Pipeline, so absent-`Slice.repo`⇒primary is a **runtime
  resolver** (`resolve_slice_repo`) at the orchestrator layer, and the pipeline
  repo list lives only on `orchestrator/models.py`, never on the Contract.
- **`pipelines.py` is the shared mega-file.** The linear chain is deliberate; do
  not re-parallelize slices 2–6 into independent roots (would trip #3046).
- **Draft→ready polling is new orchestrator machinery** but bounded: a mechanical
  GitHub merge-state signal, explicitly NOT release detection (cq-1 forbids
  automating release/version signals).
- **Owner/repo re-key fan-out** (ruling #6): if genuinely prohibitive at
  implement time, surface a **new HITL** — never silently fall back to
  reject-same-name-sets.
