# Implementation Plan: Build Custom Coding Harness with Multi-Provider Support

> Issue: #1570 | Phase: plan | Single-PR implementation

## Overview

This plan decomposes the architecture analysis into a phased, single-PR implementation of `shared/egg_harness/` — a custom coding harness that replaces `claude_agent_sdk.query()` for headless pipelines with a provider-abstracted LLM client, owned tool system, and agent loop.

**Approach**: Hybrid client (Anthropic SDK for Anthropic provider + httpx for OpenAI-compatible), as recommended by the architecture analysis (Option D). The harness provides a drop-in `run_agent_async()` replacement with identical CLI interface.

**Scope**: Headless (pipeline) mode only for MVP. Interactive terminal mode is deferred — it adds UI complexity without advancing the multi-provider goal. Egg-native tools (EggOrch, EggContract, etc.) shell out to CLIs initially to reduce risk; native Python implementations are a post-MVP optimization.

**Single PR**: All work ships in one PR with phases organized as logical commit groups. The harness defaults to opt-in (`EGG_HARNESS=egg`) during the transition period, with `claude-sdk` remaining the default.

## Phase Breakdown

### Phase 1: Foundation — Package Skeleton, Provider Abstraction, Config

**Goal**: Establish the `shared/egg_harness/` package with provider interface, Anthropic provider implementation, and configuration system.

**Rationale**: The provider abstraction is the architectural core. Getting this right first enables all subsequent work to build on stable types and interfaces.

**Tasks**:

1. **TASK-1-1: Create package skeleton and config module**
   - Create `shared/egg_harness/__init__.py`, `config.py`, `result.py`
   - `ProviderConfig` dataclass: `provider` (Literal["anthropic", "openai-compatible"]), `model`, `endpoint`, `api_key_env`
   - Model alias mapping: `opus` → `claude-sonnet-4-20250514` (etc.), with `[1m]` suffix support for max tokens
   - Re-export `AgentResult` from `egg_agent.result` (same dataclass, avoid duplication)
   - Acceptance: Package importable, config validates provider/model combinations, alias mapping works

2. **TASK-1-2: Define provider interface (abstract base)**
   - Create `shared/egg_harness/providers/base.py`
   - Abstract `Provider` class with `send_message(messages, tools, system, model) → AsyncIterator[Event]`
   - Define `Event` union type: `TextDelta`, `ToolUse`, `ToolResult`, `StopSignal`, `UsageInfo`
   - Acceptance: Interface is importable, type-checks with mypy, events cover all Claude API response types

3. **TASK-1-3: Implement Anthropic provider**
   - Create `shared/egg_harness/providers/anthropic.py`
   - Use `anthropic.AsyncAnthropic(base_url=gateway_url)` for API calls
   - Streaming support via `client.messages.stream()` — yield `Event` types
   - Non-streaming fallback via `client.messages.create()`
   - Token counting from `usage` response field, cost calculation with hardcoded per-model rates
   - Cache control headers (`anthropic-beta: prompt-caching`) passed through
   - Acceptance: Can send a message through the gateway proxy and receive streamed events; token/cost tracking returns plausible values

4. **TASK-1-4: Implement OpenAI-compatible provider**
   - Create `shared/egg_harness/providers/openai_compat.py`
   - Use `httpx.AsyncClient` for `/v1/chat/completions` with streaming SSE
   - Map Anthropic-style messages to OpenAI chat format (system → system message, tool results → tool role)
   - Map OpenAI tool_calls response back to `Event` types
   - Acceptance: Can send a message to a mock OpenAI-compatible endpoint and receive events; tool call round-trip works

### Phase 2: Tool System

**Goal**: Implement all tools that egg agents use, with a registry for dispatch.

**Rationale**: The tool system is the largest surface area. Each tool is independent and can be developed/tested in isolation. Ordering: Bash first (most complex, most used), then filesystem tools, then search tools, then CLI wrappers.

**Tasks**:

5. **TASK-2-1: Tool registry and base class**
   - Create `shared/egg_harness/tools/registry.py` and `__init__.py`
   - `Tool` base class with `name`, `definition() → dict` (JSON schema), `execute(input) → str`
   - `ToolRegistry`: register tools, look up by name, list definitions, support disallow list
   - Acceptance: Can register a tool, retrieve its definition, dispatch execution by name; disallow list filters tools from definitions

6. **TASK-2-2: Bash tool**
   - Create `shared/egg_harness/tools/bash.py`
   - Execute shell commands via `asyncio.create_subprocess_shell`
   - Timeout handling (configurable, default 120s), working directory support
   - Output truncation for large results (configurable limit)
   - Signal handling: SIGTERM → SIGKILL after grace period
   - Acceptance: Can execute commands, respects timeout, truncates output, kills runaway processes

7. **TASK-2-3: Filesystem tools (Read, Write, Edit, Glob)**
   - Create `shared/egg_harness/tools/read.py`, `write.py`, `edit.py`, `glob_tool.py`
   - Read: file contents with offset/limit, line numbers (cat -n format)
   - Write: create/overwrite files with content
   - Edit: string replacement (old_string → new_string) with uniqueness check
   - Glob: pattern matching via `pathlib.Path.glob()`, sorted by mtime
   - Acceptance: Each tool handles edge cases (missing files, non-unique edits, empty patterns); file operations match Claude Code behavior

8. **TASK-2-4: Search tools (Grep, WebFetch, WebSearch)**
   - Create `shared/egg_harness/tools/grep.py`, `web_fetch.py`, `web_search.py`
   - Grep: shell out to `rg` with regex, glob filter, context lines, output modes
   - WebFetch: HTTP GET + HTML→markdown conversion (disabled in private mode)
   - WebSearch: Web search API integration (disabled in private mode)
   - Acceptance: Grep returns correct results with all output modes; web tools respect private mode disable

9. **TASK-2-5: NotebookEdit tool**
   - Create `shared/egg_harness/tools/notebook_edit.py`
   - Jupyter notebook cell editing: replace, insert, delete modes
   - Parse/write .ipynb JSON format
   - Acceptance: Can edit notebook cells in all three modes; preserves notebook structure

10. **TASK-2-6: CLI wrapper tools (EggOrch, EggContract, EggCheckpoint, GitOps, GhCli)**
    - Create `shared/egg_harness/tools/egg_orch.py`, `egg_contract.py`, `egg_checkpoint.py`, `git_ops.py`, `gh_cli.py`
    - All shell out to respective CLIs via subprocess (same as Bash tool pattern)
    - GitOps and GhCli route through gateway (use existing HTTPS remote / gh CLI config)
    - Acceptance: Each CLI wrapper executes the underlying command and returns output; error handling for missing CLIs

### Phase 3: Agent Loop and Permission Layer

**Goal**: Implement the core agentic loop and permission enforcement.

**Rationale**: The agent loop ties providers and tools together. The permission layer must be integrated before the loop is usable in pipeline mode.

**Tasks**:

11. **TASK-3-1: Permission/interception layer**
    - Create `shared/egg_harness/permissions.py`
    - Re-use `tool_interceptor.check_file_write_permission()` from `egg_agent`
    - `can_use_tool` callback interface: check before tool execution, return deny message or None
    - Tool disallow list enforcement (WebFetch/WebSearch in private mode)
    - Acceptance: Write/Edit/NotebookEdit blocked for out-of-scope paths when EGG_AGENT_ROLE set; disallowed tools rejected before execution

12. **TASK-3-2: System prompt / CLAUDE.md loading**
    - Create `shared/egg_harness/prompt.py`
    - Load `~/.claude/CLAUDE.md` (user rules) and `$EGG_REPO_PATH/CLAUDE.md` (project rules)
    - Load and merge rule files from `sandbox/agent-config/rules/` (replicating current `setup_claude` behavior)
    - Combine into system prompt with section headers
    - Accept `--system-prompt` override that prepends to loaded rules
    - Acceptance: System prompt includes both CLAUDE.md files and rule files; override prepends correctly

13. **TASK-3-3: Core agent loop**
    - Create `shared/egg_harness/loop.py`
    - `async def agent_loop(provider, tools, messages, system, config) → AgentResult`
    - Loop: send messages → parse response → execute tools → append results → repeat
    - Stop conditions: `stop_reason == "end_turn"`, max turns, timeout
    - Streaming: yield text deltas to `on_output` callback as they arrive
    - Tool execution: parallel execution of independent tool calls (when supported)
    - Graceful SIGTERM handling: finish current tool, return partial result
    - Cost accumulation across turns (sum usage from each API response)
    - Acceptance: Loop completes a multi-turn conversation with tool use; respects max turns and timeout; streams output; SIGTERM produces clean exit

### Phase 4: Client API, CLI, and Harness Selection

**Goal**: Provide the high-level `run_agent_async()` interface, CLI entry point, and harness selection mechanism.

**Rationale**: This phase wires everything together into the public interface that consumers (orchestrator, consensus wrapper, babysit) will use.

**Tasks**:

14. **TASK-4-1: High-level client API**
    - Create `shared/egg_harness/client.py`
    - `async def run_agent_async(prompt, *, model, max_turns, system_prompt, cwd, timeout, on_output, env, intercept_tools) → AgentResult`
    - Identical signature to `egg_agent.client.run_agent_async()`
    - Internally: construct provider, load tools, load system prompt, run agent loop
    - Acceptance: Interface matches egg_agent exactly; can run a simple prompt end-to-end through the harness

15. **TASK-4-2: CLI entry point**
    - Create `shared/egg_harness/__main__.py`
    - Same args as `egg_agent.__main__`: `--model`, `--max-turns`, `--system-prompt`, `--timeout`, positional prompt (or stdin)
    - Same exit code semantics (0 = success)
    - Streaming stdout output
    - Acceptance: `python3 -m egg_harness --model opus --max-turns 10 "hello"` produces streamed output and exits cleanly

16. **TASK-4-3: Harness selection and build_agent_command integration**
    - Update harness selection logic: `EGG_HARNESS` env var → `egg` | `claude-sdk` | `claude-code`
    - Default: `claude-sdk` (existing behavior, no disruption)
    - When `EGG_HARNESS=egg`: `build_agent_command()` returns `python3 -m egg_harness ...` instead of `python3 -m egg_agent ...`
    - Acceptance: `EGG_HARNESS=egg` causes agents to use new harness; unset/`claude-sdk` preserves current behavior

### Phase 5: Tests and Validation

**Goal**: Comprehensive test coverage and parallel validation.

**Rationale**: This is the most critical execution path in egg. Tests must cover each layer independently and the full integration path.

**Tasks**:

17. **TASK-5-1: Unit tests for providers**
    - Test Anthropic provider with mocked API responses (streaming + non-streaming)
    - Test OpenAI-compatible provider with mocked responses
    - Test model alias mapping and config validation
    - Test event type mapping from API responses
    - Acceptance: >90% coverage of provider code; all event types tested

18. **TASK-5-2: Unit tests for tools**
    - Test each tool's execute() with mocked filesystem/subprocess
    - Test tool registry registration, lookup, disallow list
    - Test Bash timeout, output truncation, signal handling
    - Test Edit uniqueness check, Read offset/limit, Glob sorting
    - Acceptance: Each tool has tests for happy path + edge cases; >90% coverage

19. **TASK-5-3: Unit tests for agent loop and permissions**
    - Test loop with mock provider (canned responses) — verify tool dispatch and result feeding
    - Test max turns enforcement, timeout enforcement
    - Test permission layer blocks and allows correctly per role
    - Test SIGTERM graceful shutdown
    - Acceptance: Loop tests cover multi-turn, max turns, timeout, and error paths

20. **TASK-5-4: Integration tests**
    - End-to-end test: `run_agent_async()` with mock LLM backend (httpbin or local mock server)
    - CLI test: subprocess `python3 -m egg_harness` with mock backend
    - Test harness selection: verify `EGG_HARNESS=egg` vs `claude-sdk` routing
    - Test against gateway proxy (if available in test environment)
    - Acceptance: Full round-trip works; CLI produces correct output; harness selection works

21. **TASK-5-5: Add anthropic and httpx dependencies**
    - Add `anthropic` and `httpx` to `shared/pyproject.toml` dependencies
    - Verify no dependency conflicts with existing packages
    - Update `make deps` to install new dependencies
    - Acceptance: `make deps && make test` passes; no dependency conflicts

**Parallelizable work streams**:
- Phase 1 tasks (1-1, 1-2) can start in parallel
- Phase 2 tools (2-2 through 2-6) are independent of each other once 2-1 is done
- Phase 2 tools and Phase 1 providers can proceed in parallel
- Test tasks for each phase can begin as soon as that phase completes

## Test Strategy

### Automated Tests

- **Unit tests** (Phases 1–3): Each module tested with mocked dependencies. Providers use canned API responses. Tools use mocked filesystem/subprocess. Agent loop uses mock provider.
- **Integration tests** (Phase 5): End-to-end with mock LLM server returning scripted tool-use conversations. CLI subprocess tests. Harness selection routing tests.
- **Existing test suite**: `make test` must continue passing — the harness is additive (new package, no changes to existing code except `build_agent_command`).

### Manual Verification

- Run `python3 -m egg_harness --model opus --max-turns 5 "List files in the current directory"` against the gateway proxy in a sandbox container
- Compare output quality/behavior with `python3 -m egg_agent` on the same prompt
- Verify streaming output appears in real-time (not buffered until completion)
- Verify cost/token tracking in `AgentResult` metadata

## Risk Mitigations

1. **Streaming correctness**: The Anthropic SDK handles SSE parsing, reducing risk vs raw httpx. Integration tests verify event ordering.
2. **Tool behavior parity**: Each tool implementation mirrors Claude Code's documented behavior. Edge case tests ensure compatibility.
3. **Migration safety**: Default remains `claude-sdk`. The new harness is opt-in via `EGG_HARNESS=egg`. No existing behavior changes unless explicitly opted in.
4. **Gateway compatibility**: The harness uses the same `/v1/messages` endpoint through the same `ANTHROPIC_BASE_URL` — no gateway changes needed.
