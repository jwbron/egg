# Plan: MCP tooling gaps for the new Kubernetes deployment

> Issue: #1759 | Phase: plan | Pipeline: issue-1759-v3

## Summary

Close the pipeline-centric blind spot in egg's MCP surface by landing **five
new k8s-facing MCP tools** and **two diagnostic skills** in a single PR.
Adopts Option A from the refine analysis (unified umbrella) with the two
remaining refine carve-outs:

1. **Include** `rebuild_and_rollout` (Decision 4, per the HITL decision-8
   resolution: #1763 has merged, unblocking the implementation). Shipped as
   a thin MCP wrapper over `make redeploy` that streams via the
   orchestrator progress API (see TASK-2-6).
2. **Drop** the `submit_task` task-id-reuse papercut (Decision 3) — tracked
   separately as #1804.
3. **Drop** the in-situ gateway `EGG_ORCHESTRATOR_URL` bug — separate issue.

Skills ship against currently-reachable evidence (Decision 5); a separate
follow-up (#1805) addresses log persistence for short-lived crashed pods.
The known-failure-mode catalogue used by the pattern-matched error
classifier is **inlined in each skill on first ship** and extracted to a
shared YAML once #1806 lands (answers risk-analyst Q3).

**In scope for this PR**:

- MCP tool `get_deployment_context` — runtime/cluster/image introspection.
- MCP tool `validate_deployment_manifests` — static kustomize overlay checks.
- MCP tool `prune_stale_worktrees(dry_run=true)` — worktree cleanup on both
  `git worktree` state and orphan dirs under `~/.egg-worktrees`. Mutating
  path proxies to a new gateway route that holds the worktree mutex
  (risk-analyst Q1: NOT dry-run-only — full path supported via the gateway
  mutex pattern).
- MCP tool `validate_network_isolation(pipeline_id, role)` — throwaway probe
  Job in `egg-agents` verifies Calico enforcement post-deploy.
- MCP tool `rebuild_and_rollout` — thin wrapper over `make redeploy`
  (build image → `k3s ctr images import` → `kubectl rollout restart`).
  Streams progress via the orchestrator progress API
  (`orchestrator/routes/progress.py`) rather than via a blocking MCP call
  because build + import + rollout can exceed FastMCP's ~60 s tool-call
  budget. Gated on `EGG_RUNTIME=kubernetes`; rejects concurrent invocations
  via an in-process flag (idempotency guard). See TASK-2-6.
- Skill `deployment-diagnose` — prioritized control-plane evidence report.
- Skill `agent-diagnose` — per-agent-pod failure triage with pattern-matched
  error classification, reusing `_PROTECTED_ENV_KEYS` from
  `kubernetes_spawner` plus `*_TOKEN`/`*_SECRET`/`*_KEY`/Bearer-JWT regex
  redaction on all env and log output.

**Success metric** (acceptance for the PR as a whole): re-run the #1692
validation pass using only the new tools/skills for diagnosis. Any step that
still requires raw `kubectl` is a specific, filed gap rather than a generic
"tools didn't help."

## Approach

No new architecture. We reuse the existing patterns documented in the refine
analysis:

- **MCP tool schemas** appended to `PIPELINE_TOOLS` in `orchestrator/mcp_tools.py`
  (currently ends at line 687). New handlers attached to `PipelineToolHandler`
  and wired into the `handle_tool_call` dispatch table (line 704+).
- **Orchestrator HTTP routes** for new logic go under `orchestrator/routes/`
  as a new `deployment.py` Blueprint (mirrors `health.py` / `containers.py`),
  registered in `orchestrator/api.py` alongside the other blueprints. Every
  new route uses `@require_lifecycle_secret` (matching the #1769 fix
  pattern) — see the per-route auth table below.
- **Kubernetes access** via `get_kubernetes_client()` (`kubernetes_client.py:943`).
  `_resolve_job_name` (line 867) is reused for any Pod-UID→Job-name lookups
  the skills need.
- **Worktree pruning** reuses `WorktreeManager.cleanup_orphaned_worktrees`
  (`gateway/worktree_manager.py:1182`) plus a new thin wrapper to surface the
  `git worktree prune` step that the existing method does not invoke. Exposed
  via a new gateway route that holds the worktree in-process mutex; the
  orchestrator proxies via `GatewayClient`.
- **Skills** are markdown files with YAML frontmatter dropped under `skills/`
  alongside the existing three (Decision 2 Recommended — no operator/agent
  subtree split yet; #1765 can handle that separately).
- **Secret redaction** reuses the `_PROTECTED_ENV_KEYS` frozenset in
  `orchestrator/kubernetes_spawner.py` as the base denylist. Extend with
  `*_TOKEN`, `*_SECRET`, `*_KEY`, `GITHUB_TOKEN`, `GH_TOKEN`,
  `ANTHROPIC_API_KEY`, `CLAUDE_API_KEY` patterns (case-insensitive); apply
  JWT/Bearer regex scrub to log tails. This helper lives in a new
  `orchestrator/redaction.py` module so both skills and the
  `agent-diagnose`-adjacent tools share one implementation.

### Per-route auth table (responds to risk-analyst RISK-4)

| Route | Method | Auth decorator | Rationale |
|-------|--------|----------------|-----------|
| `/api/v1/deployment/context` | GET | `@require_lifecycle_secret` | Read-only cluster introspection; parity with `/api/v1/health` and existing mutation routes. |
| `/api/v1/deployment/validate-manifests` | POST | `@require_lifecycle_secret` | Static read; no mutation but gated to prevent unauthenticated cluster reads. |
| `/api/v1/deployment/prune-worktrees` (orchestrator proxy) | POST | `@require_lifecycle_secret` | Proxies gateway mutation; must require auth. |
| `/api/v1/worktrees/prune` (gateway) | POST | gateway session token (existing pattern) | Matches every other gateway mutation. |
| `/api/v1/deployment/validate-network-isolation` | POST | `@require_lifecycle_secret` | Spawns a Job; authenticated only. |
| `/api/v1/deployment/rebuild-and-rollout` | POST | `@require_lifecycle_secret` | Kicks off `make redeploy` (build + image import + rollout restart) and returns a progress-stream handle; must be authenticated. |

An integration test sends unauthenticated requests to each new route and
asserts 401/403 (risk-analyst checklist item reused from #1769 regression).

**Route-prefix reconciliation**: the plan uses `/api/v1/deployment/*` for
all five routes; the architect's draft used `/api/v1/cluster/*`. Concrete
reviewer-prescribed route for the new tool is
`/api/v1/deployment/rebuild-and-rollout` (per NACK). The final prefix is
whatever both agents agree on at CONFIRMED; `routes/deployment.py` as the
module name is orthogonal to the URL prefix, so a prefix flip is a
one-line change if the architect re-proposal lands on `/api/v1/cluster/*`.

### Multi-runtime compatibility

`get_deployment_context` is portable by design — it branches on `EGG_RUNTIME`
and returns a structured payload describing whatever runtime is active.
The other four tools (`validate_deployment_manifests`,
`prune_stale_worktrees`, `validate_network_isolation`,
`rebuild_and_rollout`) are k8s-specific. When `EGG_RUNTIME != "kubernetes"`,
they return a structured
`{"error": "not_available_on_runtime", "runtime": "docker"}` payload
rather than failing the MCP call.

`validate_network_isolation` additionally gates on
`get_deployment_context.network_policy_enforcement` — if the detected CNI
does not enforce NetworkPolicies (vanilla flannel, etc.), the tool returns
a `{"error": "network_policy_enforcement_not_detected", "cni": ...}`
rather than silently returning misleading probe results (risk-analyst
DEP-3 mitigation).

### Dependency ordering

```
Phase 1 (introspection tools) ──┐
                                 ├── Phase 3 (skills compose Phase 1+2 tools)
Phase 2 (action tools) ─────────┘

Phase 4 (docs + integration test) waits on Phase 1–3.
```

Within a phase, coder tasks land before tester tasks for the same feature,
and gateway-side changes land before the orchestrator proxy that calls them.

## Risks / Edge Cases (keyed to risk-analyst register)

- **RISK-1 (HIGH)** probe Job NetworkPolicy/secret bypass. **Mitigation
  in plan**: Phase-2 task spec requires the probe Job template to (a) set
  labels `app.kubernetes.io/component=agent`, `egg.probe=true`, matching
  what NetworkPolicies gate on; (b) reuse `_PROTECTED_ENV_KEYS` when
  constructing the probe env (no lifecycle secret, no session token, no
  gateway bearer); (c) set `ttlSecondsAfterFinished=0` for prompt deletion
  (risk-analyst Q on design); (d) set `activeDeadlineSeconds=30`.
- **RISK-2 (HIGH)** hostPath mutation. **Mitigation**: dry_run=true
  default (kept), orchestrator tool proxies to a new gateway route that
  holds the worktree in-process mutex; path-traversal guard enforces
  every candidate path resolves under `~/.egg-worktrees/` via
  `Path.resolve()` + `is_relative_to`.
- **RISK-3 (HIGH)** secret leakage in skill output. **Mitigation**:
  dedicated redaction helper (`orchestrator/redaction.py`), reused by
  any code that emits env or log tail; unit tests seed known secrets
  in input and assert redaction on output.
- **RISK-4 (HIGH)** new-route auth parity with #1769 fix. **Mitigation**:
  per-route auth table above; integration test asserts 401/403 on
  unauth.
- **DEP-3 (MEDIUM)** CNI enforcement not guaranteed. **Mitigation**:
  `validate_network_isolation` gates on `get_deployment_context`'s CNI
  enforcement detection and returns a structured error rather than
  misleading results when enforcement isn't detected.
- **Rate limits on the MCP server (30 req/min)**: each skill caps itself
  at ≤10 primitive calls per invocation; documented budget in SKILL.md.
- **Probe pod side effects**: unique label selector + `ttlSecondsAfterFinished=0`
  + namespace-scoped deletion on exit. Tool asserts no overlap with
  active pipeline agent pods before spawn.
- **Skill discoverability**: new skill directories are filesystem-scanned,
  no harness change required. Manual post-merge verification confirms.
- **Validation warnings on non-k3s clusters**: `validate_deployment_manifests`
  k3s-specific warnings (e.g., containerd image presence) are gated on
  `get_deployment_context.runtime == "kubernetes"` plus a detected k3s
  cluster. **k3s-detection heuristic** (applied in that order, first match
  wins): (a) `kubectl get nodes -o json` shows any node whose `nodeInfo`
  section reports a `kubeletVersion` / server version string ending in
  `+k3s<N>` (e.g., `v1.30.2+k3s1`); (b) the `kube-system` namespace
  contains a DaemonSet whose container image name contains the substring
  `rancher/k3s` (or `rancher/mirrored-k3s-*`). On non-k3s those warnings
  are skipped with a structured `{"skipped": "not_k3s", "detected_runtime":
  "<flavor-hint-or-null>"}` entry so callers see *why* the rule didn't
  fire.
- **#1767 silent-failure scan**: `deployment-diagnose` greps gateway pod
  logs since the **current pod incarnation's start** (bounded by pod
  lifetime, not a persistent aggregator that doesn't yet exist).

## Risk-analyst open questions — answered

1. **Q: Should `prune_stale_worktrees(dry_run=false)` land at all, or
   dry-run-only?** — **A**: Land full support. The gateway-mutex proxy
   pattern (Phase 2, TASK-2-1) is well-established and keeps hostPath
   mutation safe; dropping `dry_run=false` would force operators right
   back to raw shell.
2. **Q: Is `rebuild_and_rollout` expected to be agent-callable?** —
   **A**: Yes — in scope per HITL decision-8 resolution (#1763 has merged).
   Shipped as a thin MCP wrapper over `make redeploy` in TASK-2-6. Auth:
   `@require_lifecycle_secret` on the orchestrator route (parity with the
   other four new routes and the #1769 fix). Timeout: the MCP tool returns
   immediately with a progress-stream handle; the actual build + image
   import + rollout-restart work streams via `orchestrator/routes/progress.py`
   so the ~60 s FastMCP tool-call budget is not exceeded. Runtime-gated on
   `EGG_RUNTIME=kubernetes` (returns `not_available_on_runtime` otherwise).
   Rejects concurrent invocations via an in-process flag so a second call
   while a rollout is live returns `rollout_already_in_progress` rather
   than racing the first. Covered by integration test (happy path + unauth
   → 401).
3. **Q: Known-failure-mode catalogue shared YAML vs inlined?** —
   **A**: Inline in each skill for first ship (YAGNI); extract to a
   shared file when #1806 lands.

   the orchestrator route, returns the progress-stream id verbatim when
   `wait=false` (default), and when `wait=true` additionally
   long-polls the progress stream for the terminal record via the
   existing progress-stream consumer helper, returning the terminal
   record. Wire into the `handle_tool_call` dispatch. (coder)

7. **[TASK-2-7]** Add `orchestrator/tests/test_rebuild_and_rollout.py`
