# Plan: Fix overseer max_turns exhaustion and add respawn visibility

## Summary

The overseer agent crashes mid-pipeline because its `max_turns=500` is too low for its continuous monitoring loop — during active consensus with NACKs and corrective actions, each 30-second poll cycle consumes ~10 SDK turns, exhausting 500 turns in ~25 minutes. The fix adds a configurable `overseer_max_turns` (default 2000) and improves visibility by broadcasting a message bus event on respawn with the old container's exit code and log tail.

**Risks / edge cases**: Log tail capture will fail with `ContainerNotFoundError` if Docker already purged the container — handled by falling back to "container not found" in the metadata. The `_get_message_store()` can return `None` if imports fail — broadcast is best-effort and must not block the respawn.

## Implementation

### Phase 1: Implement

Fix the root cause (max_turns too low) and add respawn visibility (message bus broadcast with diagnostics).

**Tasks**:
1. **[task-1-1]** In `orchestrator/models.py:PipelineConfig`, add `overseer_max_turns: int = Field(default=2000, ge=100, le=10000, description="Max Agent SDK turns for the overseer agent per phase")`. Acceptance: `PipelineConfig()` has `overseer_max_turns == 2000`, values outside 100-10000 are rejected.
2. **[task-1-2]** In `orchestrator/container_spawner.py:spawn_overseer_container()`, add a `max_turns: int = 2000` parameter and use it in the `build_agent_command(prompt=overseer_prompt, model=decision_model, max_turns=max_turns)` call instead of the hardcoded 500. Acceptance: the command list passed to `spawn_agent_container` uses the provided `max_turns` value.
3. **[task-1-3]** In `orchestrator/routes/pipelines.py`, pass `max_turns=pipeline.config.overseer_max_turns` at both spawn sites — the initial spawn at line ~7272 and the respawn in `_check_and_respawn_overseer()` at line ~179. Acceptance: both spawn calls include the config-driven `max_turns`.
4. **[task-1-4]** In `orchestrator/routes/pipelines.py:_check_and_respawn_overseer()`, after detecting an exited container (in the `if needs_respawn:` block) and before spawning the replacement: capture the old container's log tail (20 lines) via `spawner.docker.get_container_logs(overseer_container_id, tail=20)` wrapped in try/except (fall back to "unavailable" on any error). After successful respawn, broadcast an `OVERSEER_ALERT` message to the message bus via `_get_message_store()` with subject `"overseer_restart: overseer [info]"`, body describing the restart, and metadata containing `exit_code`, `old_container_id`, `new_container_id`, `log_tail`, `respawn_attempt`, and `max_respawns`. The broadcast must be best-effort (wrapped in try/except, log warning on failure, never block the respawn). Include `phase=pipeline.current_phase.value` on the message. Acceptance: after a successful respawn, an OVERSEER_ALERT message with the expected metadata appears in the pipeline's message store.
5. **[task-1-5]** Add tests: (a) verify `overseer_max_turns` config default (2000) and bounds (rejects <100 and >10000) in `test_overseer_spawn.py`, (b) verify `spawn_overseer_container` passes `max_turns` through to `build_agent_command` — mock `build_agent_command` or inspect the command list for `--max-turns 2000`, (c) verify `_check_and_respawn_overseer` broadcasts an OVERSEER_ALERT message on successful respawn — mock `_get_message_store` and assert `add_message` is called with correct type, subject pattern, and metadata keys, (d) verify broadcast is skipped gracefully when `_get_message_store()` returns None, (e) verify log tail capture is skipped gracefully when `get_container_logs` raises an exception. Acceptance: all new tests pass and all existing tests continue to pass.
