# Analysis: Sandbox images with cached dependency installation

> Issue: #904 | Phase: refine

## Problem Statement

In private mode, the sandbox container has no network access beyond the Anthropic API, so runtime dependency installation (`pip install`, `npm install`, `make deps`) fails. The current `docker_setup.extra_packages` config only supports OS-level packages (apt/dnf) during the shared image build. There is no mechanism for running project-specific dependency installation commands (e.g., `npm ci`, `pip install -r requirements.txt`) at image build time with proper Docker layer caching.

The goal is to support **build-time dependency installation** via user-defined commands that run during `docker build`, with results baked into the `egg` image. Docker layer caching should ensure dependency layers are only rebuilt when the relevant dependency files (lockfiles, requirements files) change.

## Current Behavior

### Image Build Pipeline

The image build is orchestrated by `sandbox/egg_lib/docker.py`:

1. **`build_image()`** (`docker.py:555`) checks if a rebuild is needed by comparing a SHA256 hash of all build-affecting files against a hash label stored on the image (`org.egg.build-hash`).
2. **`create_dockerfile()`** (`docker.py:210`) copies egg source files to the build context at `~/.cache/egg/`, including `docker-setup.py`, runtime scripts, shared modules, and the static `sandbox/Dockerfile`.
3. **`compute_build_hash()`** (`docker.py:417`) hashes UID/GID, all sandbox source files, shared modules, and directory contents. It does NOT currently include any user configuration or dependency files.
4. **`docker build`** runs with build args for user identity, a build-hash label, and the `~/.cache/egg/` build context.

### docker-setup.py

The `docker-setup.py` script (`sandbox/docker-setup.py`) runs during the Dockerfile's build phase (line 59-63 of `Dockerfile`). It:
- Detects the Linux distro (Ubuntu/Fedora)
- Loads config from `repositories.yaml` to read `docker_setup.extra_packages`
- Installs core dev packages (git, curl, build-essential, etc.)
- Installs user-configured extra OS packages (apt/dnf)

### Existing `extra_packages` Config

Configured under `docker_setup.extra_packages` in `repositories.yaml`:
```yaml
docker_setup:
  extra_packages:
    apt: [nodejs, python3.11]
    dnf: [nodejs, python3.11]
    packages: [vim]  # generic, both distros
```

### Critical Finding: Config Inaccessible During Build

**The `repositories.yaml` config is NOT copied into the Docker build context** by `create_dockerfile()`. During `docker build`, `docker-setup.py` searches:
1. `EGG_REPO_CONFIG` env var — not set during build
2. `~/.config/egg/repositories.yaml` — HOME is `/root` during build; file doesn't exist
3. `~/repos/egg/config/repositories.yaml` — doesn't exist during build

This means `docker-setup.py` silently gets an empty config and **`extra_packages` are never actually installed** during image build. The feature exists in config/tests but is effectively non-functional. The proposed `build_commands` feature must solve this config-availability problem.

### Dockerfile Structure

The `sandbox/Dockerfile` is **static** — it's copied as-is to the build context. Key layers in order:
1. Ubuntu 22.04 base + system packages
2. GitHub CLI
3. Python 3.11 (deadsnakes PPA)
4. `docker-setup.py` execution (core + extra OS packages)
5. Python pip dependencies (base + private-mode pre-installs)
6. Claude commands/rules, runtime scripts
7. Git/gh hijacking to route through gateway
8. User creation, Claude Code CLI install, entrypoint

### Runtime Repo Mounting

Local repos are mounted at runtime as Docker volumes at `/home/egg/repos/<name>` (generated by `compose.py:192`). This means **anything installed into a repo directory during build will be hidden** by the volume mount at runtime. This is a fundamental constraint for package managers that install locally (e.g., npm's `node_modules/`).

## Constraints

- **Single image**: All repos' dependencies must coexist in one `egg` image — no per-repo images
- **Volume overlay**: Runtime volume mounts at `/home/egg/repos/<name>` will hide any build-time contents at those paths, so local installs (e.g., `node_modules/`) are lost at runtime
- **Config inaccessibility**: `repositories.yaml` is not currently in the Docker build context; must be added or worked around
- **No full repo at build time**: Only watch files (lockfiles, requirements files) are available during build; full repos are mounted at runtime
- **Backwards compatible**: Repos without `build_commands` must be unaffected
- **Static Dockerfile**: The current Dockerfile is copied as-is; dynamic generation would be a design shift
- **Private mode**: The primary motivation — no network at runtime, so deps must be pre-installed
- **Layer caching**: Docker rebuilds all layers after the first changed layer, so watch file COPYs should precede their corresponding RUN commands for optimal caching
- **Build hash**: `compute_build_hash()` must be extended to include watch file contents so dependency changes trigger rebuilds
- **Distro**: Currently Ubuntu 22.04 only in practice (Fedora path exists but is secondary)

## Options Considered

### Option A: Extend docker-setup.py with Generated Config

**Approach**: Copy `repositories.yaml` (or a subset) into the build context in `create_dockerfile()`. Extend `docker-setup.py` to read `build_commands` from config. Copy watch files into the build context. Add a single new Dockerfile layer that copies all watch files and runs all build commands via `docker-setup.py`.

**Pros**:
- Minimal changes to the static Dockerfile (one new COPY + RUN layer)
- Reuses existing config loading in `docker-setup.py`
- Simple mental model — `docker-setup.py` handles all build-time setup
- Fixes the existing `extra_packages` bug as a side effect

**Cons**:
- **Poor per-repo caching**: All watch files are copied in one COPY layer, so changing any repo's lockfile rebuilds ALL repos' dependencies
- All build commands run in a single RUN layer, preventing independent caching
- `docker-setup.py` becomes more complex, mixing OS package installation with project-level dependency management

### Option B: Dynamic Dockerfile Generation with Per-Repo Layers

**Approach**: `create_dockerfile()` reads `build_commands` from config and **appends per-repo COPY + RUN instructions** to the static Dockerfile template before writing it to the build context. Each repo gets its own layers:

```dockerfile
# (existing static layers)

# Dependencies for your-org/web-app
COPY repo-deps/web-app/ /tmp/repo-deps/web-app/
RUN cd /tmp/repo-deps/web-app && npm ci

# Dependencies for your-org/python-service
COPY repo-deps/python-service/ /tmp/repo-deps/python-service/
RUN cd /tmp/repo-deps/python-service && pip install -r requirements.txt
```

**Pros**:
- **Optimal per-repo caching**: Changing one repo's lockfile only rebuilds that repo's dependency layer
- Standard Docker build pattern — COPY before RUN for cache invalidation
- Clean separation — each repo's deps are independent layers
- No runtime script dependency; commands are directly in the Dockerfile

**Cons**:
- Shifts from static to dynamically generated Dockerfile, adding complexity to `create_dockerfile()`
- Dockerfile is no longer 1:1 with what's in the repo — could be confusing when debugging builds
- Must handle the case where `build_commands` config is empty (produce the original static Dockerfile)
- Build arg injection into generated RUN commands requires careful escaping

### Option C: Separate Build Script (No Dockerfile Changes)

**Approach**: `create_dockerfile()` generates a `build-deps.sh` script from the config (embedding commands directly, no YAML parsing at build time). The static Dockerfile gets one new COPY + RUN line for this script. Watch files are still copied individually.

**Pros**:
- No dynamic Dockerfile generation — only a generated shell script
- Dockerfile changes are minimal (2 lines)
- Shell script is easy to debug (`docker run ... cat /tmp/build-deps.sh`)

**Cons**:
- Same poor caching as Option A (single RUN layer for all repos)
- Generated shell script introduces a new build artifact pattern
- Must handle shell escaping of user-provided commands in the script

## Recommended Approach

**Option B: Dynamic Dockerfile generation with per-repo layers** is recommended.

The primary value of this feature is Docker layer caching — if deps haven't changed, skip reinstalling them. Option B maximizes this by giving each repo independent COPY+RUN layers, so changing one repo's lockfile doesn't rebuild another's. This is the standard Docker pattern for dependency caching (e.g., `COPY package-lock.json . && RUN npm ci` before `COPY . .`).

The dynamic Dockerfile generation is a manageable complexity increase to `create_dockerfile()`, which already assembles a build context. The generated lines would be appended to the static template, keeping the core Dockerfile readable in the repo.

Key implementation details:
1. `create_dockerfile()` reads `build_commands` from config, copies watch files from `local_repos.paths` into the build context at `repo-deps/<name>/`, and appends COPY+RUN lines to the Dockerfile
2. `compute_build_hash()` is extended to include watch file contents from all repos
3. `docker-setup.py` changes are limited to fixing the existing `extra_packages` config accessibility bug (copy config to build context)
4. Config schema is extended with `build_commands` under `repo_settings`
5. Config loader in `config/repo_config.py` gets new accessor functions

## Open Questions

### 1. Volume Mount Overlay for Local Dependencies

**Critical**: Runtime volume mounts at `/home/egg/repos/<name>` will HIDE anything the build placed at those paths. Package managers that install locally (e.g., npm creates `node_modules/` in the project dir) will have their build-time installs masked at runtime.

**Affected package managers**:
- **npm/yarn/pnpm**: Install to `./node_modules/` by default
- **Bundler (Ruby)**: `vendor/bundle/` by default
- **Composer (PHP)**: `vendor/` by default

**Not affected** (install to system paths):
- **pip**: Installs to `/usr/local/lib/python3.11/dist-packages/` when run as root
- **Go modules**: Cache at `$GOMODCACHE` (system-level)
- **Cargo (Rust)**: Cache at `$CARGO_HOME` (system-level)
- **apt/dnf**: System packages

**How should locally-installing package managers be handled?** Options include:
- Install to a staging path during build, then copy/symlink at container startup (adds startup latency)
- Install to a global/system path with toolchain flags (e.g., npm `--prefix /opt/deps/web-app` + `NODE_PATH`)
- Document the limitation and recommend users only use `build_commands` for globally-installing package managers
- Use Docker named volumes for `node_modules/` directories (separate from repo mount)

### 2. Config Accessibility During Build

The `repositories.yaml` config is not currently in the Docker build context. The proposed solution is to copy it (or a relevant subset) in `create_dockerfile()`. Should we:
- Copy the full `repositories.yaml` into the build context (simpler, but includes tokens/secrets if any are in the file)
- Extract only the `build_commands` and `local_repos` sections into a minimal config file for the build context (safer, more complex)
- Generate the commands directly into the Dockerfile/script without config parsing at build time (Option B approach — no config needed during build)

Note: Option B (recommended) sidesteps this for `build_commands` by embedding commands in the Dockerfile, but the existing `extra_packages` bug still needs the config available.

### 4. Build Command Execution Context

**User**: The Dockerfile currently runs everything as root before creating the `egg` user (line 147). Build commands would also run as root. Is this acceptable for all expected use cases, or should some commands run as the `egg` user?

**Working directory**: Build commands need a working directory containing the watch files. For Option B, this is a temp dir like `/tmp/repo-deps/<name>/`. Commands like `npm ci` will install relative to this dir, which won't match the runtime path (`/home/egg/repos/<name>`). For system-level installers (pip, go), this doesn't matter. For local installers (npm), this ties into Question 1.

**Environment**: Should there be a way to set environment variables for build commands? (e.g., `GOPATH`, `NODE_ENV=production`, `PIP_NO_CACHE_DIR=1`)

### 5. Watch Files and local_repos.paths Relationship

`build_commands` is configured under `repo_settings` (keyed by `owner/repo`), but watch files must be read from the filesystem at `local_repos.paths`. The mapping between `repo_settings` keys (`your-org/web-app`) and `local_repos.paths` entries (`/home/user/projects/web-app`) is by directory name — the path's basename must match the repo name portion.

- What if `local_repos.paths` is not configured but `build_commands` is? (Cloud-only repos that aren't local)
- What if the repo directory name doesn't match the repo name in `repo_settings`? (e.g., path `/home/user/my-app` but settings key `org/web-app`)
- Should the mapping be explicit rather than by convention?

### 6. Should the Existing `extra_packages` Bug Be Fixed?

`docker_setup.extra_packages` appears non-functional during Docker builds because the config is inaccessible. Should this be fixed as part of this issue, or tracked separately? Fixing it is a natural side-effect of making config available during build.

### 7. Command Ordering and Dependencies

If a repo's `build_commands` includes multiple commands (`npm ci` then `npm run build`), they naturally run in sequence within one `RUN` layer. But what about cross-repo dependencies? (e.g., repo A's build produces a package that repo B's build installs). The issue's design implies repos are independent, but is this always true?

### 8. Security: Arbitrary Command Execution During Build

Build commands are user-configured strings executed as root during `docker build`. Since this is a local development tool where the user controls the config, this is likely acceptable. But should there be any validation or sandboxing of the commands? (The existing `docker-setup.py` already runs arbitrary apt/dnf install commands, so this is precedented.)

### 9. Cache Invalidation Beyond Watch Files

Watch files handle the common case (lockfile changes → rebuild deps). But some scenarios aren't covered:
- A command depends on a package registry's state (e.g., `npm ci` with `latest` tags)
- A command depends on files NOT in the watch list (e.g., a `Makefile` that `make deps` reads)
- Forced rebuild of a single repo's deps without rebuilding everything

Should there be a `--rebuild-deps` flag or similar mechanism for manual cache invalidation?

### 10. Documentation and Example Config

The issue lists updating `repositories.yaml.example` and `sandbox/README.md`. Are there other docs that should be updated? The private mode documentation (`ADR-Internet-Tool-Access-Lockdown.md`) likely needs to reference this feature as the recommended workflow.
