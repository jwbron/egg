# Plan: Surface egg agent capabilities as first-class MCP tools

> Issue: #1765 | Phase: plan | Approach: Hybrid D+B (in-process SDK MCP server + short prompt nudge)

## Strategy

The refine analysis (`.egg-state/drafts/1765-analysis.md`, 874 lines)
recommended **Hybrid D + prompt nudge**: an in-process MCP server
built via `claude_agent_sdk.create_sdk_mcp_server` and registered on
`ClaudeAgentOptions.mcp_servers`, with a short bootstrap paragraph
injected into the system prompt pointing agents at the new
`mcp__*` tool namespaces. The refine-phase HITL gate resolved all
decisions (see `.egg-state/contracts/issue-1765.json`); this plan
adopts them verbatim as fixed context. They are repeated here so
reviewers don't have to chase the contract:

| Item | Resolved answer | Drives |
|---|---|---|
| decision-1 (mechanism) | **Hybrid D+B** — in-process SDK MCP via `create_sdk_mcp_server` + `@tool` on `ClaudeAgentOptions.mcp_servers`, plus a short system-prompt nudge. | Single implementation shape; no new network service, no new auth. |
| decision-2 (schema derivation) | **Hybrid** — auto-derive skeleton from CLI argparse where a CLI exists; allow per-tool overrides for descriptions/JSON-schema where argparse is insufficient. | Schema generation helper + explicit `@tool` files for the 15 core verbs. |
| decision-3 (harness coverage) | **`claude_agent_sdk` only for iteration 1.** Defer parallel registration for experimental `EGG_HARNESS=egg` until it graduates. | No changes to `shared/egg_harness/`; caveat is documented. |
| decision-4 (CLI retention) | **Keep `sandbox/bin/egg-*` CLIs indefinitely.** MCP tools are additive. | Refactor CLIs to thin wrappers but do NOT delete binaries. |
| decision-7 (naming; supersedes 5) | **Semantic / verb-based names grouped by agent function**: `mcp__sdlc__register_open_question`, `mcp__brc__propose`, `mcp__phase__get_context`, etc. | Tool module layout is per-namespace (sdlc/brc/phase/progress/task). |
| decision-8 (scope; supersedes 6) | **BRC + HITL + phase-context core = 15 verbs.** Extras (peer, checkpoint, anchor, overseer, task gap) go to follow-up #1917. | Iteration-1 tool list is fixed; any new verb surfaced during plan is either folded in (if core) or deferred to #1917. |

### Open feedback (Q1–Q8) — resolutions applied in this plan

The refine HITL gate resolved 8 feedback questions (`feedback-1`).
Their answers guide concrete design decisions here:

- **Q2 (drift prevention)**: Flavour **(c) — single handler, shared by
  CLI and `@tool`.** Each `cmd_*` in `sandbox/egg_lib/contract_cli.py`
  and `sandbox/egg_lib/orch_cli.py` is refactored so the argparse
  dispatch and the MCP `@tool` dispatch both call the same pure
  handler function that takes a plain-dict request and returns a
  plain-dict response. Belt-and-suspenders: a CI test asserts every
  `@tool` with a declared CLI counterpart resolves to the same
  handler.
- **Q3 (bootstrap nudge)**: Inject a short (≤200 words) system-prompt
  paragraph naming the `mcp__sdlc__*`, `mcp__brc__*`, `mcp__phase__*`,
  `mcp__progress__*` namespaces and explicitly instructing "prefer
  these over Bash for agent-lifecycle operations." Injected by
  `shared/egg_agent/client.py::run_agent_async` only when the flag is
  on (so prompt weight is zero when tools are not registered).
- **Q4 (tool output shape)**: **JSON payload verbatim.** Tools return
  structured data. `brc_get_state` accepts a `verbose: bool` argument
  for large payload truncation.
- **Q6 (observability)**: Native SDK `tool_use` naming is enough —
  `mcp__sdlc__register_open_question` vs `Bash` surfaces cleanly in
  checkpoint logs. No changes to the checkpoint browser in iteration
  1.
- **Q7 (timeouts)**: Default 60 s SDK-MCP tool timeout is sufficient
  for all 15 core verbs (none are long-running). No start/poll
  splitting needed in iteration 1.
- **Q8 (rollout)**: **Feature-flag gated.** New env var
  `EGG_MCP_TOOLS` (default `false` for iteration 1). Enable for a
  burn-in window of 5–10 pipelines, compare turns-per-phase and
  cost-per-phase between MCP-on and MCP-off, flip default to `true`
  when the refine/plan phases show ≥15 % reduction in turns. Remove
  the flag in a follow-up PR.
- **Q1/Q5 (moot)**: Option D was chosen, so there is no sandbox-facing
  network-transport MCP server to authz or threat-model in iteration
  1.

## Architecture shape

### New package: `sandbox/egg_agent_tools/`

Iteration-1 layout (all files under `sandbox/egg_agent_tools/`):

```
__init__.py              # public: build_sandbox_mcp_server(), TOOL_NAMESPACES, SYSTEM_PROMPT_NUDGE
server.py                # factory: create_sdk_mcp_server(name="egg", tools=[...])
schemas.py               # argparse→JSON-schema skeleton + override hooks
handlers/
  __init__.py
  sdlc.py                # register_open_question, request_feedback, check_hitl_answers handlers
  brc.py                 # brc_propose/ack/nack/confirm/get_state/list_blocking handlers
  phase.py               # phase_get_context, phase_get_assigned_tasks handlers
  progress.py            # progress_emit, progress_signal_error, progress_heartbeat handlers
  task.py                # task_complete handler
tools/
  __init__.py            # imports every namespace; builds the SDK tool list
  sdlc.py                # @tool-decorated async funcs → handlers.sdlc.*
  brc.py                 # @tool-decorated async funcs → handlers.brc.*
  phase.py               # @tool-decorated async funcs → handlers.phase.*
  progress.py            # @tool-decorated async funcs → handlers.progress.*
  task.py                # @tool-decorated async funcs → handlers.task.*
```

The split into `handlers/` (pure request→response) and `tools/`
(`@tool`-decorated wrappers) is the **drift-prevention contract**:
every `tools/*.py` function is a two-line wrapper that calls the
matching `handlers/*` function and serialises the dict result. CLIs
in `sandbox/egg_lib/contract_cli.py` and `sandbox/egg_lib/orch_cli.py`
are refactored to call the same `handlers/*` function from their
existing `cmd_*` argparse entry points. CI asserts the mapping
one-to-one.

### Wire-up: `shared/egg_agent/client.py`

In `run_agent_async` (client.py:65-246), after the environment and
options dict are built (line 193), and gated by `EGG_MCP_TOOLS`
environment variable:

1. Import `sandbox.egg_agent_tools.build_sandbox_mcp_server` lazily
   (import only when the flag is on, to keep the non-MCP code path
   dependency-free).
2. Construct the in-process SDK MCP server: `mcp_server =
   build_sandbox_mcp_server()`.
3. Set `options.mcp_servers = {"egg": mcp_server}` (line ~209
   immediately after the other `ClaudeAgentOptions` kwargs).
4. Concatenate the `SYSTEM_PROMPT_NUDGE` (≤200 words) to any existing
   `options.system_prompt` (preserving the caller's prompt if set).

When `EGG_MCP_TOOLS` is unset/`false`, none of the above runs — the
SDK call is byte-for-byte identical to today. This preserves the AC
"existing CLIs keep working" for pipelines that have not opted in.

### Prompt nudge

`SYSTEM_PROMPT_NUDGE` is a constant inside
`sandbox/egg_agent_tools/__init__.py` (≤200 words):

```
You have first-class MCP tools for the operations you perform in
every phase. Prefer them over Bash-ing the corresponding egg CLI.

Tool namespaces:
- `mcp__sdlc__*` — register a HITL decision, request open-ended
  feedback, check for human answers.
- `mcp__brc__*` — propose, ACK, NACK, confirm; query structured BRC
  state; list agents currently blocking consensus.
- `mcp__phase__*` — get your phase context (role, pipeline id,
  assigned tasks, prior-phase artifacts) and fetch your task list.
- `mcp__progress__*` — emit a progress update, heartbeat, or
  signal an error.
- `mcp__task__*` — mark a task complete.

Use the tool directly; do not run `egg-orch consensus propose`,
`egg-contract add-decision`, etc. through Bash when an MCP tool
covers the same capability. The shell CLIs remain available for
other tooling but are slower and less reliable for agent use.
```

This paragraph is appended to the system prompt only when the feature
flag is on.

### CLI backward compatibility (decision-4)

Every existing `cmd_*` function that gains an MCP counterpart is
refactored as:

```python
def cmd_consensus_propose(args: argparse.Namespace) -> int:
    # Build the same request dict the MCP tool would
    req = {
        "summary": args.summary,
        "artifacts": args.artifacts or [],
        "files_changed": args.files_changed or [],
        ...
    }
    resp = handlers.brc.brc_propose(req)
    # Keep today's text-based stdout for human operators and scripts
    print(...)
    return 0 if resp["ok"] else 1
```

The public argparse signature, stdout shape, and exit codes are
preserved; only the internal call flow changes. The drift-prevention
CI test (`tests/tools/test_mcp_cli_drift.py`) enforces:

1. Every tool in `TOOL_NAMESPACES[*]` is defined.
2. Every tool with a `cli_command` field (e.g.
   `("egg-orch", "consensus", "propose")`) dispatches the same
   handler module function as the CLI subparser.

### Feature-flag rollout path

1. **Iteration 1 (this PR)**: `EGG_MCP_TOOLS` default `false`.
   Operators/developers opt-in by setting the env on a per-pipeline
   basis.
2. **Burn-in window**: 5–10 pipelines with flag on; compare
   turns-per-phase and cost-per-phase.
3. **Follow-up PR (not this one)**: flip default to `true` once
   metrics show ≥15 % reduction in turns-per-phase for refine/plan.
4. **Later follow-up PR**: remove flag entirely.
5. **Iteration 2 (tracked in #1917)**: remaining ~15 verbs from the
   capability audit (peer, checkpoint, anchor, overseer, task-gap).

## Task breakdown

The work fits in a single PR organised into six phases. Each phase
lands as one or more commits; phase 1 and 2 are independent and can
be worked in parallel but phase 2 depends on phase 1 for import
sanity. Phases 3, 4, and 5 serialise on phase 2.

### Phase 1: Shared handlers (extract `cmd_*` bodies)

**Goal**: Every `cmd_*` function that gains an MCP counterpart is
split into (a) a pure handler function in a new module taking a
request dict and returning a response dict, and (b) a thin argparse
shim that builds the request dict from argparse.Namespace, calls the
handler, and renders existing stdout text. No behaviour change for
CLI callers.

### Phase 2: MCP tool package skeleton

**Goal**: New `sandbox/egg_agent_tools/` package lands with: (a)
`build_sandbox_mcp_server()` factory using
`claude_agent_sdk.create_sdk_mcp_server`, (b) all 15 `@tool`-decorated
thin wrappers in `tools/*.py` calling into `handlers/*.py`, (c)
`SYSTEM_PROMPT_NUDGE` constant, (d) schema-derivation helper in
`schemas.py` that converts argparse subparser definitions to
JSON-schema inputs with per-tool override hooks.

### Phase 3: Agent client wire-up

**Goal**: `shared/egg_agent/client.py::run_agent_async` reads
`EGG_MCP_TOOLS` env, when truthy builds the in-process MCP server and
sets it on `ClaudeAgentOptions.mcp_servers`; also appends
`SYSTEM_PROMPT_NUDGE` to `options.system_prompt` when the flag is on.
Off-path is byte-identical to today.

### Phase 4: Tests

**Goal**: pytest coverage for every handler, every `@tool` wrapper,
the server factory, the client wire-up (flag on/off), and the
drift-prevention CI test. All tests run offline using fakes/mocks of
the gateway and the SDK — no real claude-agent-sdk call needed.

### Phase 5: Docs

**Goal**: User-facing docs for the new surface: `docs/reference/` gets
an `agent-tools.md` page listing the 15 tools, their schemas, and the
mapping to existing CLIs. `docs/guides/sdlc-pipeline.md` adds a
"Agent MCP tools" section pointing at the reference.
`sandbox/agent-config/rules/README.md` mentions that agents
automatically see the new tools when `EGG_MCP_TOOLS=true`.

### Phase 6: Rollout hygiene

**Goal**: Mark `EGG_MCP_TOOLS` in `sandbox/agent-config/rules/environment.md`
(env-var reference), and add a CHANGELOG/release-note paragraph.

## Test strategy

### Automated

- **Handler unit tests** (`tests/sandbox/egg_agent_tools/test_handlers_*.py`):
  Every handler function is tested with a fake gateway (HTTP mock)
  and asserted to return a structured response matching its JSON
  schema. Error paths (bad args, gateway 500) also covered.
- **`@tool` wrapper tests** (`tests/sandbox/egg_agent_tools/test_tools_*.py`):
  Every wrapper is tested to serialise the handler response to a JSON
  string via the SDK tool contract. Schema-compliance asserted.
- **Server factory test**
  (`tests/sandbox/egg_agent_tools/test_server.py`): `build_sandbox_mcp_server()`
  returns an `SdkMcpServer` object with the 15 expected tool names
  registered.
- **Client wire-up tests** (`tests/shared/egg_agent/test_client.py`):
  Extend existing patterns. Asserts:
  - With `EGG_MCP_TOOLS` unset: `options.mcp_servers` is not set and
    `options.system_prompt` is unchanged.
  - With `EGG_MCP_TOOLS=true`: `options.mcp_servers["egg"]` is the
    server object and `options.system_prompt` ends with the nudge.
- **CLI drift test** (`tests/tools/test_mcp_cli_drift.py`): Every MCP
  tool with a declared CLI counterpart dispatches the same handler
  module function the CLI argparse calls. Fails CI if a tool drifts
  from its CLI.
- **Backward-compat tests for refactored CLIs**
  (`tests/sandbox/test_contract_cli.py`,
  `tests/sandbox/test_orch_cli.py`): assert `cmd_add_decision`,
  `cmd_consensus_propose`, `cmd_signal_heartbeat`, etc. still produce
  the same stdout text and exit codes as before the refactor
  (snapshot-style).
- **Schema-derivation test** (`tests/sandbox/egg_agent_tools/test_schemas.py`):
  Fed an argparse subparser, produces a JSON schema with correct
  required/optional/types; overrides merge cleanly.

### Manual

- Set `EGG_MCP_TOOLS=true` on a test pipeline. Confirm the agent
  running `refiner` or `coder` picks up `mcp__brc__propose`,
  `mcp__sdlc__register_open_question`, etc. in its first tool_use
  block and does not `cat /opt/egg-runtime/sandbox/bin/egg-contract`
  to derive the subcommand surface. Capture before/after
  turns-per-phase from `egg-pipeline-watch` / checkpoint logs.
- Run one pipeline with `EGG_MCP_TOOLS` unset and confirm
  byte-for-byte parity with today's behaviour (same tool_use blocks,
  same Bash calls, same duration).
- Exercise a NACK→fix→re-propose cycle end-to-end with the flag on to
  confirm `mcp__brc__nack` / `mcp__brc__propose` / `mcp__brc__confirm`
  interoperate with existing `egg-orch consensus` shell invocations
  from other roles that haven't migrated yet.

## Risks

Deferred to the risk_analyst's concurrent output at
`.egg-state/drafts/1765-risk-assessment.md`. Summary of risks this
plan structurally mitigates:

- **Drift between CLI and MCP tool surface** → single-handler pattern
  + CI drift test.
- **Rollout regression** → feature-flag gated, default off; off-path
  byte-identical to today.
- **Import surface / package boundary** → `sandbox/egg_agent_tools/`
  is under `sandbox/`, imported lazily inside `run_agent_async`, so
  non-sandbox consumers of `shared/egg_agent/client.py` see no change.
- **Experimental `egg` harness omission** → explicitly deferred per
  decision-3; caveat documented in `docs/reference/agent-tools.md`.

## Complexity assessment

**medium**. The change touches ~12 files (11 new under
`sandbox/egg_agent_tools/`, 1 modified in `shared/egg_agent/client.py`,
refactored CLIs in `sandbox/egg_lib/contract_cli.py` and
`sandbox/egg_lib/orch_cli.py`, ~5 new test files, ~2 doc files). No
new long-running services, no new network surface, no new auth layer,
no dependency additions (`mcp[cli]>=1.20.0` and `claude-agent-sdk`
are already pinned). The non-trivial bits are: (a) getting the shared
handler signatures right so both CLI and MCP tool can drive them
cleanly, (b) the drift-prevention CI test, and (c) making sure the
flag-off code path is provably identical to today.
