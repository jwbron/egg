# Plan: Event-driven wake for SDLC skill's monitor loop (host-side)

> Issue: #1932 | Phase: plan | Agent: task_planner

## Summary

The SDLC skill's host-side monitor loop (§Phase 3 and §Phase S5 of
`skills/sdlc/SKILL.md`) polls `get_status(task_id, wait=25)` on a pure
time-based sleep. Every 25 s the orchestrator returns a full snapshot
regardless of whether anything changed on the pipeline, burning tokens
during quiet phases and delaying reactions to `OVERSEER_ALERT`, phase
transitions, and HITL gates by up to a full poll interval.

The refine phase converged on **Option A**: add a new sibling MCP tool
`wait_for_status_change(task_id, wait=25, since=<event_id>)` that
composes the event primitives already landed in #1919 (EventBus
subscription + `message_store.get_messages(wait_for_types=…,
from_tip=True)`). On any watched event it returns the full `get_status`
envelope plus a `changed: true` flag and the cursor ID. On a 25 s
timeout it returns a minimal `{changed: false, current_phase, status,
phase_elapsed_seconds}` payload so dashboard re-render stays cheap.
`get_status` itself is untouched.

This plan breaks the work into four phases inside a **single PR**:
server primitives (route + async wait engine), MCP tool surface
(schema, dispatcher, async wrapper), SDLC skill prompt updates, and
tests/docs.

## Approach

### Architecture (one-sentence summary per change)

1. **New HTTP route** `GET /api/v1/pipelines/<id>/status/wait` in
   `orchestrator/routes/pipelines.py` (or a new `routes/status.py`
   blueprint) — blocks on a composite wait (EventBus + message-bus
   long-poll), returns a structured envelope.
2. **New async wait engine** in a shared helper (e.g.
   `orchestrator/status_wait.py`) — subscribes to EventBus types the
   issue prescribes, registers a parallel `message_store.get_messages`
   blocking read filtered by `OVERSEER_ALERT` /
   `CONSENSUS_CONFIRMED` / `CONSENSUS_NACK` / `CONSENSUS_RE_REVIEW`,
   races them with `asyncio.wait(..., FIRST_COMPLETED)` and a timeout,
   returns `(changed: bool, event_id: str | None)`.
3. **New MCP tool** `wait_for_status_change` in
   `orchestrator/mcp_tools.py` (schema entry and `_handle_*`) +
   `orchestrator/mcp_server.py` (new async wrapper
   `_apply_wait_for_status_change`). On `changed: true` it reuses
   `_handle_get_status` internals to build the full envelope; on
   timeout it returns the minimal payload.
4. **SDLC skill update** — §Phase 3 step 1, §Phase S5 step 1, and the
   surrounding "Important" note in `skills/sdlc/SKILL.md` switch from
   `get_status(task_id, wait=25)` → `wait_for_status_change(task_id,
   wait=25, since=<prior_event_id>)`. First poll still uses
   `get_status(task_id)` (immediate feedback, cheap snapshot); every
   subsequent poll uses the new tool.
5. **Metric** `egg_inflight_host_waits` — parallel gauge to
   `egg_inflight_long_polls` so operators can distinguish host-side
   waits from sandbox-side waits under the Waitress thread budget.
6. **Config** — a new constant
   `WAIT_FOR_STATUS_CHANGE_MAX_WAIT = 25` in `mcp_server.py`
   parameterized so raising it (if Claude Code lifts the streamable-HTTP
   tool-call timeout upstream) is a one-line change.
7. **Tests** — unit tests for the MCP tool (event paths, timeout,
   cursor, filter set), route tests, and a backend-parity test for
   both Redis and in-memory `message_store` implementations.
8. **Docs** — host-side section in
   `docs/reference/agent-wait-patterns.md` and tool-reference update
   next to `get_status`.

### Event trigger set (locked in refine)

The HITL resolution locked "issue-as-written":

| Trigger | Source | Wired via |
|---------|--------|-----------|
| New `OVERSEER_ALERT` | message bus | `message_store.get_messages(wait_for_types=['OVERSEER_ALERT'], from_tip=True)` |
| `DECISION_CREATED` | EventBus | `events.subscribe(EventType.DECISION_CREATED, …)` |
| Phase transition | EventBus | `PHASE_STARTED` / `PHASE_COMPLETED` |
| Terminal state | EventBus | `PIPELINE_COMPLETED` / `PIPELINE_FAILED` |
| Consensus change | message bus | `wait_for_types=['CONSENSUS_CONFIRMED', 'CONSENSUS_NACK', 'CONSENSUS_RE_REVIEW']` |

`DECISION_RESOLVED` is **explicitly excluded** from the trigger set so
the host does not self-wake after it calls `provide_input`.

### Cursor / race semantics (locked in refine)

The tool accepts an optional `since: str` parameter (event ID). On the
first call of a monitoring session the host omits `since` and the
server defaults to `from_tip=True` on the message bus and EventBus
subscription semantics (only future events). On every subsequent call
the host passes the `event_id` returned by the prior `changed: true`
response. That prevents the "stuck on same event" race on event
backlog and matches the #1925 default for `/messages/wait`.

### Response shape

```json
// changed path (event fired)
{
  "changed": true,
  "event_id": "1738012734-0",
  "event_source": "message_bus" | "event_bus",
  "event_type": "OVERSEER_ALERT" | "PHASE_STARTED" | ...,
  "current_phase": "plan",
  "status": "running",
  "phase_elapsed_seconds": 127,
  "pipeline": { ... },
  "running_agents": [ ... ],
  "completed_agents": [ ... ],
  "pending_decisions": [ ... ],
  "recent_messages": [ ... ],
  "concurrent": { ... }
}
// timeout path (25 s, nothing fired)
{
  "changed": false,
  "current_phase": "plan",
  "status": "running",
  "phase_elapsed_seconds": 152
}
```

The timeout payload is deliberately minimal — SDLC skill branches on
`changed` before re-rendering the dashboard.

### Concurrency budget

Add a log line at orchestrator boot that warns when
`EGG_ORCH_WAITRESS_THREADS` is less than `4 × expected_host_sessions`
(documented heuristic). The raise/don't-raise decision on the default
is out of scope for this issue but the warning gives operators a lever.
`egg_inflight_host_waits` makes the current load observable.

## Phases

Phase 1 lays the server-side primitive. Phase 2 adds the MCP tool
surface that calls it. Phase 3 updates the SDLC skill to use the new
tool. Phase 4 tightens tests and writes the docs. All four land in
one PR.

### Phase 1 — Server-side wait primitive

Build the composite event wait as a reusable helper and expose it via
a new HTTP route.

- **TASK-1-1** — Implement `orchestrator/status_wait.py` with
  `async def wait_for_status_change(pipeline_id, since, timeout,
  message_store, event_bus) -> (changed: bool, event_id: str | None,
  event_type: str | None, event_source: str | None)`. Races three
  awaitables: (a) an `asyncio.Event` set by a short-lived EventBus
  handler for `PHASE_STARTED`, `PHASE_COMPLETED`, `PIPELINE_COMPLETED`,
  `PIPELINE_FAILED`, `DECISION_CREATED`; (b) a thread-pool call into
  `message_store.get_messages(..., wait_for_types=['OVERSEER_ALERT',
  'CONSENSUS_CONFIRMED', 'CONSENSUS_NACK', 'CONSENSUS_RE_REVIEW'],
  from_tip=since is None, since_id=since, wait=timeout)`; (c) a
  `asyncio.sleep(timeout)` timeout sentinel. Uses
  `asyncio.wait(..., return_when=FIRST_COMPLETED)`, cancels losers,
  always unsubscribes the EventBus handler in `finally`. Filters
  `DECISION_RESOLVED` out by never subscribing to it.
- **TASK-1-2** — Add a route
  `GET /api/v1/pipelines/<id>/status/wait` (likely in
  `orchestrator/routes/pipelines.py` next to the existing pipeline
  routes). Query params: `since` (optional), `timeout` (int seconds,
  clamped by `EGG_MESSAGE_POLL_MAX_WAIT`). Invokes the helper and
  returns the structured envelope documented above. Track with a new
  `egg_inflight_host_waits` gauge parallel to `egg_inflight_long_polls`.
- **TASK-1-3** — Define `_inflight_host_waits` gauge and
  `_track_host_wait_start/end()` helpers in the same module as the new
  route (or a shared metrics helper). Labels: `{"endpoint":
  "status_wait"}`.
- **TASK-1-4** — Ensure the in-memory `message_store` exercises the
  same `wait_for_types` + `from_tip` semantics as the Redis backend
  (already does per `message_store.py:180-330` — no code change
  needed, but add a backend-parity test matrix in Phase 4).

### Phase 2 — MCP tool surface

Wire the new tool through the MCP server so Claude Code can call it.

- **TASK-2-1** — Add `wait_for_status_change` schema entry to
  `PIPELINE_TOOLS` in `orchestrator/mcp_tools.py` right after
  `get_status` (~line 305). `inputSchema` properties: `task_id`
  (string, required), `wait` (number, default 25, max 25), `since`
  (string, optional).
- **TASK-2-2** — Add `_handle_wait_for_status_change` method to the
  tools class in `orchestrator/mcp_tools.py`. Calls the new
  `/status/wait` endpoint via `self._make_request`, then — on
  `changed: true` — composes the full envelope by re-using
  `_handle_get_status` (refactored to split snapshot building from
  the request). On timeout returns the minimal payload.
- **TASK-2-3** — Register the handler in the dispatcher dict around
  line 1053 of `orchestrator/mcp_tools.py`:
  `"wait_for_status_change": self._handle_wait_for_status_change`.
- **TASK-2-4** — Add async wrapper `_apply_wait_for_status_change`
  to `orchestrator/mcp_server.py` mirroring
  `_apply_get_status_wait` (lines 50-67) — uses a module-level
  constant `WAIT_FOR_STATUS_CHANGE_MAX_WAIT = 25` so raising it later
  is a one-line change. The wait still runs on the event loop, not a
  worker thread, so the client is cancellable.
- **TASK-2-5** — Refactor `_handle_get_status` to extract a private
  `_build_status_snapshot(task_id)` helper so
  `_handle_wait_for_status_change` can compose the same envelope
  without duplicating the fetch logic. `get_status` behaviour is
  unchanged.

## Test Strategy

**Automated**:

- `orchestrator/tests/test_status_wait.py` covers the composite wait
  helper end-to-end for both backends.
- `orchestrator/tests/test_mcp_tools.py` covers the new handler's
  envelope construction and dispatcher wiring.
- `orchestrator/tests/test_mcp_server.py` covers the async wrapper
  cap and loop-vs-thread behaviour.
- `orchestrator/tests/test_status_routes.py` covers the new HTTP
  route, metrics, error paths, and the Redis/in-memory parity.
- Existing `test_mcp_tools.py::_handle_get_status` cases must still
  pass — the refactor in TASK-2-5 is pure extraction.

**Manual verification** (for the PR reviewer):

1. Start an orchestrator with a local pipeline, run the SDLC skill
   in Claude Code, confirm the dashboard still renders every cycle
   on `changed: true` and skips render on `changed: false`.
2. In a second terminal send an `OVERSEER_ALERT` message via
   `egg-orch message send --type OVERSEER_ALERT`, confirm the host
   wakes within < 1 s.
3. Force a phase transition via `egg-contract advance-phase`,
   confirm the host wakes promptly.
4. Resolve a HITL decision via the skill's `provide_input` flow,
   confirm the subsequent wait does NOT immediately return on
   `DECISION_RESOLVED` (the host should NOT self-wake).
5. `curl /metrics | grep egg_inflight_host_waits` while a host
   session is running — expect the gauge to reflect the active wait.

## Manual Steps

**Pre-merge**: none beyond the manual verification above. The new tool
is additive; existing `get_status` consumers are unaffected.

**Post-merge**: operators should watch `egg_inflight_host_waits` in
Grafana after deploy. If the sum of `egg_inflight_long_polls +
egg_inflight_host_waits` approaches `EGG_ORCH_WAITRESS_THREADS`
(default 16) under steady-state load, raise the Waitress thread
budget. No schema migration, no breaking changes to existing pipelines.

## Risks (summary — the risk_analyst produces the authoritative doc)

Enumerated in `.egg-state/drafts/1932-analysis.md` §Recommended
Approach. Briefly:

- **Host self-wake via DECISION_RESOLVED.** Mitigation: never
  subscribe to `DECISION_RESOLVED` (TASK-1-1 filter set).
- **Event backlog race on first call.** Mitigation: `since` cursor +
  `from_tip=True` default (TASK-1-1, TASK-3-1).
- **Waitress thread budget.** Mitigation: new metric + boot-time
  warning log (TASK-1-3).
- **Backend parity.** Mitigation: parameterised test matrix
  (TASK-4-4).
- **Prompt drift.** Mitigation: three coordinated edits in SKILL.md
  (TASK-3-1/2/3/4), and the §MCP Tools Reference update locks the
  tool name and contract in one place.
