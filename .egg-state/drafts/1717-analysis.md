# Analysis

**Problem statement**: Humans reviewing a PR produced by the BRC consensus pipeline can't see what agents actually said during consensus. The PR body shows only counts (`N proposals · M ACKs`), and the committed `brc-history/*.md` file strips metadata (artifact references, versions, commit SHAs) and filters out every non-`CONSENSUS_*` message type. When diagnosing pipeline issues from the PR alone, reviewers are flying blind.

**Source context**: Issue #1717 was opened after investigating the `issue-1707` pipeline — the diagnosis is independent of agent content quality. Replaces #1712 (split for scope); distinct from #1716 (which fixes what agents *send*). #1717 is the persistence layer — even if agents already send structured data (artifact refs, commit SHAs), it's dropped here. Can land in either order relative to #1716.

**Workarounds**: None — reviewers have to hit the orchestrator directly or ssh into a host with the message store to see full content.

**System context**: `_build_pr_body` (`orchestrator/routes/pipelines.py:4594+`) assembles the PR body; it calls `_build_brc_consensus_summary` (`pipelines.py:4515`) at line 4671 to append a BRC section. Separately, `_rewrite_brc_history_for_pr` (`pipelines.py:4293`) iterates completed phases and calls `_write_brc_history` (`pipelines.py:4196`) for each, which writes `.egg-state/brc-history/{identifier}-{phase}.md` to the worktree and commits it. Both renderers read from the in-memory `MessageStore` (`orchestrator/message_store.py`) via `_get_message_store`. The `Message` model (`orchestrator/message_store.py:40`) already carries every field the issue wants persisted — `id`, `to_role`, full `metadata` dict, `timestamp`, `phase` — the losses are purely rendering choices.

**Technical root cause**: Three lossy renderers, all in `orchestrator/routes/pipelines.py`:

1. **`_write_brc_history` (lines 4271–4277)** renders only `timestamp | from_role | message_type | subject | body`. It ignores `id`, `to_role`, `metadata` (which on BRC messages contains `payload.artifact_references`, `payload.ack_version`, `version`, `commit_sha`, `revision_count`).
2. **`BRC_MESSAGE_TYPES` frozenset (lines 4172–4181)** filters to only the six `CONSENSUS_*` types, so the history file omits `STATUS`, `HANDOFF`, `QUESTION`, `AGENT_FAILED`, `NUDGE`, `OVERSEER_ALERT` — the orchestrator's own contextual signals around BRC flow.
3. **`_build_brc_consensus_summary` (lines 4515–4591)** emits per-phase `{roles, counts, ✅/⏳}` only — never any message body — and caps at 2000 chars at phase-block boundaries.

**Files affected**:
- `orchestrator/routes/pipelines.py` — rewrite `_write_brc_history`, split `BRC_MESSAGE_TYPES`, rewrite `_build_brc_consensus_summary`, emit JSON companion, link artifacts from PR body.
- `orchestrator/tests/test_brc_history.py` — update expectations for lossless markdown + new JSON companion.
- `orchestrator/tests/test_pr_phase_brc_rewrite.py` — update expectations for expanded message types at PR time.
- `orchestrator/tests/test_diagnostic_logging_1633.py` — may reference rendered format.
- `orchestrator/tests/test_brc_phase_propagation.py` — check if affected by the split of `BRC_MESSAGE_TYPES`.

**Risks / edge cases**:
- **PR body size**: GitHub caps PR bodies at 65k chars. Collapsing older rounds inside `<details>` keeps final round inline; individual body truncation uses a pointer to the history file rather than dropping messages.
- **Non-JSON-serializable metadata**: `metadata` is free-form `dict[str, Any]`; the JSON companion must use `default=str`.
- **Directed-message disclosure**: Surfacing `to_role` and body content for non-broadcast types (e.g., `HANDOFF`) exposes inter-agent coordination text not previously visible externally. All pipeline artifact data and already reachable via orchestrator logs — no concern identified, noted for reviewer awareness.
- **Test fixtures**: Existing BRC history tests assert exact markdown shape — update assertions, don't bypass them.
- **Back-compat of committed `brc-history/*.md`**: File is part of the branch, externally observable, but always regenerated by `_rewrite_brc_history_for_pr` at PR-creation time — format change is safe for new PRs.
