# Plan: Peer consensus protocol with Broadcast-Review-Converge

> Issue: #1110 | Phase: plan | Revision: 2

## Summary

This plan replaces the current orchestrator-centric consensus system (polling +
READY tallying) with a peer-to-peer Broadcast-Review-Converge (BRC) protocol.
The work spans three layers: (1) Redis Streams transport replacing the in-memory
MessageStore, (2) the BRC protocol engine with asymmetric review graphs and
scoped re-evaluation, and (3) evidence-backed deliberation with per-role
attestations and anti-sycophancy measures.

The work is organized into five phases within a single PR: (1) types and data
model, (2) Redis Streams transport, (3) BRC protocol engine, (4) consensus CLI
and wrapper, and (5) agent prompts and integration tests. Each phase builds on
its dependencies and the entire feature ships as a one-shot replacement — no
backwards compatibility layer.

## Architecture Analysis Summary

The analysis (`.egg-state/drafts/1110-analysis.md`) evaluated three layers of
the consensus problem and concluded:

### Transport Layer Decision: Redis Streams

Replace the in-memory `MessageStore` with Redis Streams backend. Single stream
per pipeline (`pipeline:{id}:messages`). Agents interact via orchestrator API,
not directly with Redis. Long-polling via `XREAD BLOCK` replaces 30s sleep
polling. ~1s message delivery instead of up to 29s.

**Why not SSE**: SSE is server→client only; Redis Streams is bidirectional with
message persistence and replay on reconnect. Redis is already running.

### Protocol Decision: Broadcast-Review-Converge (BRC)

Asymmetric review topology: producers (coder, tester, documenter) propose;
reviewers (rev_code, rev_contract, checker) judge. ~7-10 directed edges instead
of 30 for N=6. Three phases: Broadcast (barrier sync), Review (asymmetric ack),
Converge (confirmation). The orchestrator *observes* consensus, it doesn't
*declare* it.

### Reasoning Layer Decision: Evidence-Backed Deliberation

Per-role attestation requirements on proposals and reviews. Delphi-style ordering
(reviewers form independent judgments before seeing producer self-assessments).
Anti-sycophancy via artifact reference requirements. Integrator cross-verifies
attestations against actual changes.

### Rollout Decision: One-Shot Replacement

No backwards compatibility layer. The current polling + READY-tallying system is
replaced wholesale. The new protocol ships complete.

## Design Decisions

- **Single Redis Stream per pipeline**: `pipeline:{id}:messages` — all messages,
  state changes, and consensus protocol events flow through one ordered log.
- **Orchestrator-mediated access**: Agents don't touch Redis directly. The API
  layer reads from the stream, applies role-based filtering, and serves via
  long-polling.
- **Asymmetric review graph**: Producers propose, reviewers judge. Eliminates
  circular ACK problem. Configurable adjacency per phase.
- **Scoped re-evaluation**: A NACK triggers re-review only from the NACKing
  reviewer. Other reviewers' ACKs stand unless the revision affected their
  referenced artifacts.
- **Delphi ordering**: Producer's CONSENSUS_PROPOSE self-assessment metadata is
  held back from reviewers until they've submitted independent evaluation. A
  conditional release in the long-polling endpoint, not a general visibility
  filter.
- **Commitment devices**: Cooldown after PROPOSED. Retraction requires citing new
  information. Lockout after K flip-flops.
- **Consensus failure modes**: Three specified handlers — attestation verification
  failure, partial consensus at timeout with role-criticality, agent crash with
  review graph removal.

### Phase 3: BRC Protocol Engine

**Goal**: Build the `PeerConsensusTracker` that observes consensus messages on
the stream and manages the BRC protocol state machine. Replace the existing
`ConsensusEvaluator` READY-tallying logic.

**Tasks**:

- **[TASK-3-1]** Create `orchestrator/peer_consensus.py` with
  `PeerConsensusTracker` class. Core state: per-agent `ConsensusPhase` (WORKING,
  PROPOSED, REVIEWING, CONFIRMED), the `ReviewGraph` for the current phase, and
  the `ApprovalMatrix`. Methods:
  - `handle_propose(agent_role, proposal_payload)` — validate attestation schema,
    transition agent to PROPOSED, record in approval matrix
  - `handle_ack(reviewer_role, producer_role, review_payload)` — validate
    attestation, record ACK in matrix, check if producer is fully ACKed
  - `handle_nack(reviewer_role, producer_role, review_payload)` — validate
    attestation, record NACK, transition producer back to WORKING, increment
    revision count for that edge
  - `handle_withdraw(agent_role, reason)` — validate reason non-empty, transition
    back to WORKING, check cooldown/lockout
  - `handle_confirmed(agent_role)` — mark agent CONFIRMED
  - `evaluate()` — check if all agents are CONFIRMED → emit CONSENSUS_REACHED

  **Tester dual-role handling**: The tester is both a producer (proposes test
  artifacts) and a reviewer (evaluates coder's work by running tests). It
  traverses both state machines: it proposes its own test artifacts AND evaluates
  the coder's proposal. The tracker must handle the tester having both a producer
  state (WORKING→PROPOSED→CONFIRMED) and a reviewer state
  (WORKING→REVIEWING→CONFIRMED) simultaneously. Both must reach CONFIRMED for the
  tester to be fully confirmed.

  Wire into message handling: when a consensus message type is received on the
  stream, dispatch to the appropriate handler.
  - **Acceptance**: State transitions follow the specified state machines (producer:
    WORKING→PROPOSED→CONFIRMED with NACK loop; reviewer:
    WORKING→REVIEWING→CONFIRMED with re-review loop). Tester dual-role: both
    producer and reviewer state machines tracked; tester confirmed only when both
    reach CONFIRMED. Attestation validation rejects empty artifact references.
    Revision count increments per edge. All handlers emit appropriate events.
    Unit tests for each state transition pass.

- **[TASK-3-2]** Add scoped re-evaluation logic to `PeerConsensusTracker`. When
  a producer re-proposes after a NACK:
  - Compare the re-proposal's changed artifacts against each existing ACK's
    referenced artifacts
  - If overlap: invalidate that ACK (reviewer must re-review)
  - If no overlap: ACK stands
  - The NACKing reviewer must always re-review regardless of overlap

  Track artifact references per ACK in the approval matrix (already modeled in
  TASK-1-4).
  - **Acceptance**: Re-proposal invalidates only overlapping ACKs. NACKing
    reviewer always re-reviews. Non-overlapping ACKs preserved. Example scenario:
    rev_code NACKs coder for bug in auth.py, coder fixes and re-proposes, tester's

  STAY ALIVE, WAIT FOR STOP). This preamble must be rewritten for BRC. If
  TASK-5-1 updates the rules files but `_build_agent_prompt()` still injects the
  old "signal READY and poll" preamble, agents will get contradictory

  - Whether the agent is a producer or reviewer (from the review graph env vars

  - Which roles it reviews / is reviewed by
  - The BRC lifecycle steps for its role type (propose→wait→confirm for
    producers; review→ack/nack→confirm for reviewers)
  - Attestation requirements for its specific role
  - **Acceptance**: Agents spawned in concurrent mode receive BRC protocol
    preamble, not the old READY lifecycle. Preamble is role-type-aware (producer
    vs reviewer). No contradictions with rules files (TASK-5-1). Unit tests pass.

## Test Strategy

- **Unit tests**: Each new module gets dedicated test files. Attestation schemas,
  review graph, approval matrix, PeerConsensusTracker state machine, Redis
  message store, CLI commands — all with isolated unit tests.
- **Integration tests**: Phase 5 (TASK-5-3) — full BRC lifecycle with real Redis,
  timing assertions for long-polling, multi-agent scenarios with NACK loops and
  failure modes.
- **Existing test updates**: Phase 5 (TASK-5-4) — all existing consensus/message
  tests updated for new protocol. No deprecated READY-tallying references.
- **Edge cases**: Scoped re-evaluation with overlapping artifacts, Delphi ordering
  with multiple producers, commitment device lockout, partial consensus with
  mixed critical/non-critical roles, agent crash at each BRC phase, Redis
  connection failure during long-poll.

## Risk Mitigations

| Risk | Mitigation |
|------|------------|
| Redis unavailability | Graceful error on Redis connection failure; in-memory fallback for tests only |
| Long-polling thread exhaustion | Use appropriate async/thread pool for blocking reads; max wait capped at 60s |
| Attestation overhead for agents | Configurable strictness (strict/relaxed); start strict, relax if needed |
| Scoped re-evaluation complexity | Conservative default: invalidate all ACKs on re-proposal; scoped mode opt-in |
| Delphi ordering adds latency | Only affects PROPOSE visibility; git artifacts visible immediately; minimal impact on reviewer start time |
| NACK cascade (reviewer keeps NACKing) | Bounded revision rounds per edge (default K=2); escalate to HITL after limit |
| Sycophantic ACKs despite anti-measures | Integrator cross-verification catches fabricated attestations; dynamic prompt refinement over time |
| Backwards compatibility break | One-shot replacement per design decision; no mixed-mode operation needed |
