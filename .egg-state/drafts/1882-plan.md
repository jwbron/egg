# Plan: Gateway auto-filter + commit-authorship registry for cross-role pushes

> Issue: #1882 | Phase: plan | Branch: `egg/issue-1882`

## Approach

Refine-phase HITL locked in four axes (see
`.egg-state/drafts/1882-analysis.md` "HITL Resolution"):

- **decision-1**: Option **B3** — *gateway-side commit-SHA registry*.
  The gateway maintains a durable `commit_sha → role` mapping,
  attributed by the **session token** that authored each commit.
  The gateway does not trust `commit.author_email` or any sandbox-
  reported authorship data.
- **decision-6**: Option **C1** — single-release cutover (auto-filter
  + registry + scope-filter removal in this PR). Kill switch
  `EGG_AGENT_RESTRICTIONS_ENFORCE=false` preserved.
- **decision-8**: Remove `egg-orch push --scope-filter` entirely in
  this PR.
- **decision-9**: **Fail closed**. Any commit whose authorship cannot
  be resolved via the registry is treated as own-authored for
  restriction-check purposes. Suppressing the observer cannot be used
  to bypass file restrictions.

The **architect** (see `.egg-state/agent-outputs/1882-architect-output.json`)
adopted the refine-phase defaults for all other decisions and
identified two structural refinements that this plan incorporates:

1. **Observation point — gateway-inline, not sandbox hook.** The
   HITL decision-1(d) text describes a sandbox-installed
   `post-commit` hook calling a gateway endpoint. That design is
   *infeasible in this codebase*: sandbox containers have no direct
   `.git` access (tmpfs shadow mount at `sandbox/entrypoint.py:728-
   750`), the gateway sets `core.hooksPath=/dev/null` globally, and
   `git commit --no-verify` would bypass any hook we did install. The
   gateway is already the sole commit-creation path via `POST
   /api/v1/git/execute`. This plan therefore has the gateway observe
   commits **inline in `git-execute`** and POST to the
   orchestrator's registry. This is a *strengthening* of decision-
   1(d) — bypass-proof, no bootstrap race, covers every commit-
   creating subcommand (commit, cherry-pick, rebase, revert, amend,
   merge). The plan phase flags this for explicit reviewer /
   human confirmation.
2. **Per-commit rewrite — not squash.** Refiner's decision-2 default
   was "squash all own-authored commits into one." Architect's
   decision-4 mandates per-commit rewrite via `git commit-tree` /
   `git update-ref` so pulled cross-role commits pass through
   bitwise-unchanged while own-role commits with blocked files are
   individually rewritten. The squash approach would either corrupt
   pulled commits or force a 403 bailout on mixed histories — both
   unacceptable. This plan adopts the architect's per-commit walk.

The remaining refiner defaults are adopted as recommended:
`[auto-filtered]` suffix on rewritten own-commits (decision-12),
`nothing_to_push=true` for the all-blocked case (decision-2 /
decision-11), `pulled_commits` response field (decision-5 /
decision-13), **partition helper in `gateway/agent_restrictions.py`**
(decision-15 — architect chose gateway-local over the refiner's
`shared/egg_restrictions/` since `cli_push.py` goes away this PR and
no cross-component caller remains), fail-closed for unknown-role
authorship (decision-17), **fast-forward local HEAD + re-stage blocked
files** as uncommitted changes after a successful filtered push
(decision-6).

The change decomposes into five phases, all landing in a **single PR**
on `egg/issue-1882`. Phases organise commits, not PRs.

### Phase 1 — Commit-authorship registry (store + endpoints + observer)

Build the registry that B3 requires. Gateway writes per-commit
attribution as the commits are created; push-handler reads it to
partition files.

- **Orchestrator sub-store.** Extend `orchestrator/state_store.py`
  with a `commit_authorship` sub-store on the existing
  `egg/pipeline-state` orphan branch. Storage layout:
  `.egg-state/commit-authorship/<pipeline_id>.json`, partitioned by
  pipeline so files stay bounded and rotate with pipeline lifecycle.
  Fallback file `_orphan.json` for commits registered before a
  `pipeline_id` is known. Reuse the existing `fcntl` + `RLock` +
  optimistic-versioning pattern. `register` is **first-wins**: the
  initial (sha, role) binding is authoritative; a later register
  for the same sha with a different role is rejected with an audit-
  logged collision event and the original binding is preserved.
  Prevents a malicious agent from suppressing the observer on its
  own commit and then re-registering later under a different role
  to pick attribution.
- **Orchestrator HTTP endpoints.** Add `POST
  /api/v1/commit-authorship/register` and `POST
  /api/v1/commit-authorship/lookup` in a new module
  `orchestrator/routes/commit_authorship.py`. The register endpoint
  accepts `{sha, role, pipeline_id, repo, branch}`; the role is
  authoritative — body-supplied fields are logged but not trusted.
  Auth via the existing inter-pod shared-secret header the gateway
  already uses for other orchestrator calls.
- **Gateway observer.** Add `gateway/commit_observer.py` — a
  lightweight module with `observe(exec_path, before_head, after_head,
  branch, session_role, pipeline_id, repo)`. It computes the set of
  new SHAs on `branch` between `before_head` and `after_head` using
  `git rev-list <before>..<after>` and fires a best-effort POST to
  the orchestrator registry for each new SHA with the session's
  role. Failures are logged at WARNING and never block the caller.
- **Gateway git-execute instrumentation.** Wrap the existing
  `/api/v1/git/execute` handler (gateway.py ~line 1337): snapshot
  `git rev-parse HEAD` before the inner git invocation, dispatch,
  snapshot after, and invoke the observer. This catches commit,
  commit --amend, cherry-pick, revert, merge (non-ff), rebase picks,
  and any other git subcommand that mutates refs. Internal gateway
  git operations (e.g. state-branch sync) are explicitly excluded by
  requiring `g.session.agent_role` to be present.

No sandbox-side changes are required for observation. The HITL text
assumes a hook-based design; this plan implements the functionally-
equivalent but bypass-proof gateway-inline design and documents the
deviation prominently so the reviewer can confirm.

### Phase 2 — Auto-filter building blocks (helpers + per-commit rewrite)

Reintroduce the building blocks from `6f0877f50`, but with
architect's per-commit algorithm instead of the original squash.

- **Partition helper.** Add
  `gateway/agent_restrictions.py::partition_files_by_role(role,
  files) -> tuple[list[str], list[str]]` returning `(allowed,
  blocked)`. Delegates to `AgentFilePattern.can_write()` so the
  existing blocked / block-exempt / allowed precedence is preserved.
  Unknown roles return `([], files)` and log a WARNING — aligned with
  fail-closed semantics.
- **Attributed-file enumeration.** Add `gateway/git_client.py::
  get_attributed_changed_files_in_push(exec_path, remote, branch,
  session_role, registry_client) -> tuple[list[AttributedFile], str |
  None]` where `AttributedFile` is a dataclass carrying `{path,
  commit_sha, authored_by: str | None}` (`None` means unregistered,
  which the push handler treats as own-authored per decision-9).
  Reuse the existing per-commit `diff-tree` loop in
  `get_changed_files_in_push` (lines 1301-1507) — every file that
  loop emits already has a SHA; the new function adds a bulk
  registry lookup and tags each `AttributedFile.authored_by`
  accordingly. Fail-closed invariant at lines 1492-1502 is preserved.
  Keep `get_changed_files_in_push` as a thin wrapper that drops the
  attribution for non-agent callers (e.g. checkpoint code).
- **Per-commit rewriter.** Add `gateway/gateway.py::
  _execute_filtered_push(exec_path, remote, branch, push_role,
  attributed_commits, blocked_own_files, registry_client)`.
  Algorithm (from the architect's component breakdown):
  1. Snapshot the original HEAD SHA for rollback.
  2. Walk the unpushed commits in topological order (oldest first).
     For each commit:
     - *Pulled commit* (`authored_by != push_role` and not `None`):
       re-parent onto the previous loop's `new_sha`; reuse the commit
       verbatim (preserve tree, author, committer, trailers). If the
       parent chain is unchanged, no new SHA is created.
     - *Own commit* (`authored_by == push_role` OR `authored_by is
       None` — fail-closed): read the original tree via
       `git ls-tree -r <commit>`; remove blocked paths via `git
       update-index --remove`; `git write-tree` → new_tree. If
       new_tree equals the parent's tree (commit becomes empty after
       filtering), drop the commit and continue with the same
       new_parent. Otherwise `git commit-tree new_tree -p new_parent
       -m "<orig_msg> [auto-filtered]"` reusing original author /
       date; record the returned SHA as `new_sha`.
  3. `git update-ref refs/heads/<branch> <final_new_tip>` locally.
  4. `git push <remote> <branch>`. On failure, `git update-ref
     refs/heads/<branch> <original_head>` and return 500 with the
     push error; the worktree is untouched so far.
  5. On push success: `git read-tree --reset -u <final_new_tip>` to
     sync index + worktree to the filtered state.
  6. For each blocked file from the pre-rewrite tip, restore its
     blob into the worktree and index as a staged change via `git
     checkout-index --stage=0` with the old tree's blob (decision-6).
  7. Register each new own-commit SHA with the registry
     (`authored_by=push_role`) so a subsequent push by a different
     role attributes them correctly.
  8. Return 200 with `{filtered: true, excluded_files, pushed_files,
     pushed_commits: [<new own-commit SHAs>], pulled_commits:
     [{sha, author_role}, ...]}`.
  All error paths restore HEAD via `git update-ref
  refs/heads/<branch> <original_head>` and `git reset --hard` so the
  worktree is exactly where it started — atomic from the agent's
  perspective.

No wiring into the push handler in this phase — the building blocks
land first so they can be unit-tested in isolation.

### Phase 3 — Wire registry + rewriter into the push handler

- **Replace the 403 branch.** In `gateway/gateway.py::git_push`
  (lines 967-1034 today), replace the single
  `check_agent_restrictions` 403 with:
  1. Call `get_attributed_changed_files_in_push` to get per-file
     attribution.
  2. Partition into own-files (`authored_by == push_role` OR
     `authored_by is None`, fail-closed) vs pulled-files (`authored_by
     == known other role`).
  3. Call `check_agent_restrictions(push_role, own_files)` — pulled
     files are exempt.
  4. If own_files pass → plain push (today's path), with
     `pulled_commits` added to the 200 response if any pulled commit
     was in the range.
  5. If mixed own-allowed + own-blocked → call
     `_execute_filtered_push`. Success → 200 + filtered response
     shape above.
  6. If *all* own-files are blocked → return 200 with `{filtered:
     true, nothing_to_push: true, excluded_files, pulled_commits}`.
     No ref update, no remote push, worktree unchanged. Agent sees
     the exclusion set and can re-author the work as another role.
  7. Non-agent sessions (no `session_role`) keep today's
     pass-through.
- **Phase / anchor / protected-file checks stay 403.** The auto-
  filter is minimally scoped to the agent-role restriction
  (decision-8). `check_phase_file_restrictions`, anchor-write
  scoping, branch-ownership, private-mode, concurrent-mode — all
  continue to return 403 unchanged.
- **Kill switch.** `EGG_AGENT_RESTRICTIONS_ENFORCE=false` short-
  circuits everything in this phase: no rewrite, no registry lookup
  at push time, no new response fields. Same behavior as today's
  warn-only path.
- **Audit logging.** Three distinct events — `push_auto_filtered`,
  `push_all_blocked_no_op`, `push_authorship_unregistered_fallback`
  — each recording role, excluded_files, pulled_commits (SHA +
  registry-attributed author_role), rewritten_commits (SHA
  mapping). Pulled commits also record the author email from
  `git log` for human readability (not for logic).

### Phase 4 — Remove `--scope-filter` and its env plumbing

- **Remove `EGG_AGENT_FILE_PATTERNS` emission** from

- Scrub docs and agent-config rules — `docs/guides/agent-

  `--scope-filter`. Replace with a short paragraph describing the

### Phase 5 — Test coverage

Exercise every new path plus the refine-phase 8-scenario test matrix.

- **Store**: unit tests for
  `orchestrator/commit_authorship_store.py` (or wherever the sub-
  store lands) — register idempotency, bulk lookup hit/miss/partial,
  concurrent writes (two threads same pipeline), shard isolation
  (two pipelines), state-branch commit on write.
- **Registry endpoints**: tests for
  `/api/v1/commit-authorship/register` and `/lookup` covering inter-
  pod auth, idempotency, malformed input, and a state-store-down
  error surface.
- **Partition helper**: unit tests for `partition_files_by_role`
  covering all-allowed, all-blocked, mixed, unknown role, empty
  input, and `AgentFilePattern.can_write`'s blocked / block-exempt
  / allowed precedence.
- **Commit observer**: unit tests for
  `gateway/commit_observer.py` — HEAD snapshotting before / after,
  multi-commit detection (e.g. `cherry-pick` of 3 commits fires 3
  POSTs), best-effort behavior (registry unavailable returns
  WARNING + success, does not block the git-execute response),
  non-agent session skipped.
- **Git-execute integration**: test that running
  `git commit` / `git cherry-pick` / `git revert` / `git commit
  --amend` via `/api/v1/git/execute` produces the expected
  registrations.
- **Per-commit rewrite**: unit tests for `_execute_filtered_push`
  covering each step of the algorithm — single own-commit mixed
  (allowed + blocked files), multi-commit all-own mixed (preserves
  structure), interleaved own + pulled (pulled commits bitwise
  unchanged, own commits re-parented), own-commit becomes empty
  after filter (dropped), all-own all-blocked does not run (caller
  takes nothing_to_push path), new-branch push using merge-base
  fallback, rollback on mid-walk failure, rollback on push failure.
- **Push handler end-to-end** — one test per scenario:
  1. Own-only, all allowed → plain push, no filter, no
     `pulled_commits` in response.
  2. Own-only, all blocked → 200 `nothing_to_push=true`, worktree
     unchanged.
  3. Own-only, mixed → 200 `filtered=true`, blocked files unstaged
     in worktree afterwards, original HEAD no longer points at old
     tip (fast-forwarded to new tip).
  4. Mixed own/pulled, all allowed → plain push + `pulled_commits`.
  5. Mixed own/pulled, pulled files would be blocked for the pushing
     role → pulled files exempt, plain push, no rewrite.
  6. Mixed own/pulled, own-authored portion has blocked files →
     auto-filter rewrites only own commits, pulled commits preserved
     bitwise.
  7. Unregistered commits in range → fail-closed (treat as own-
     authored), own-authored-blocked triggers rewrite.
  8. `EGG_AGENT_RESTRICTIONS_ENFORCE=false` → warn-only log, no
     rewrite, no registry lookup, no new response fields.
- **Response schema**: `filtered`, `excluded_files`, `pushed_files`,
  `pushed_commits`, `pulled_commits` on filter-path responses;
  `pulled_commits` on non-filter responses iff any commit in the
  range is attributed to another role.
- **`--scope-filter` removal**: argparse test asserting
  `egg-orch push --scope-filter` now exits with "unrecognized
  arguments" error. Delete `test_scoped_push_detection.py` if
  present.
- **End-to-end**: integration test that exercises the full path from
  a simulated agent-session container creating commits through
  `/api/v1/git/execute`, to a mixed-authorship push being auto-
  filtered on `/api/v1/git/push`, with the registry writes observed
  end-to-end.

## Structural deviation from HITL decision-1(d)

Decision-1(d) says "install the post-agent-commit hook at sandbox
entrypoint before any agent code runs, so legitimate commits don't
land unregistered." This plan *does not* implement a sandbox-side
hook. The architect's analysis (grounded in
`sandbox/entrypoint.py:728-750` tmpfs mount and the gateway-side
`core.hooksPath=/dev/null`) concluded the hook pattern cannot be
made safe here — agents can suppress it, and the sandbox has no
real `.git` to hook against. The gateway-inline observer in
`/api/v1/git/execute` gives the *same* outcome (every agent commit
is registered) with strictly stronger guarantees (bypass-proof, no
bootstrap race). **This deviation is called out explicitly here so a
reviewer auditing against the decision doc verbatim can confirm
acceptance before implementation begins.** If the reviewer rejects
this refinement, the only workable alternative still routes through
`git-execute` — so the structural choice is effectively forced by
the sandbox's existing security model.

## Risk coordination

Risk_analyst is running concurrently and has already surfaced three
HIGH risks that this plan's approach addresses:

- **R-01 net-new durable store**: plan uses the existing orchestrator
  state store (HITL decision-1(a)), not a net-new SQLite.
- **R-02 new post-commit hook + sandbox wiring**: plan replaces the
  sandbox-side hook with a gateway-inline observer, removing the
  sandbox-wiring surface entirely.
- **R-04 mixed-history commit-tree / update-ref rewrite**: plan
  tests the per-commit walk explicitly (scenario 6 above, plus unit
  tests for the walk algorithm).

Mitigation for R-03 registry race conditions (risk_analyst's medium):
register is idempotent (INSERT OR IGNORE by SHA); retries are safe.
Mitigation for R-12 unregistered historical commits: fail-closed
default makes them subject to the pushing role's restrictions, which
matches today's behavior, so long-running sessions that predate
deploy keep working.

## Post-merge manual steps

- **Deploy ordering**: ship the orchestrator image *first* so the
  new `/api/v1/commit-authorship/register` and `/lookup` endpoints
  are live before any sandbox starts registering commits through a
  newer gateway. A gateway calling a missing orchestrator endpoint
  will fail-open on the observer path (log WARNING, continue) and
  fail-closed at push time for unattributed commits — both
  acceptable transiently but avoidable by ordering.
- **No data migration**: the state store creates the
  `commit-authorship/` subdirectory on its first write. Long-running
  sessions that predate the deploy continue to work and their
  commits simply fall through to fail-closed at push time —
  equivalent to today's behavior.
- **Monitoring**: watch gateway audit logs for the first 24 h
  for `push_authorship_unregistered_fallback` entries. A sustained
  spike suggests the git-execute observer is not firing for some
  subcommand (investigate which subcommand is being missed).
