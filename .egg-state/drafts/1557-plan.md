# Plan: Add SDLC pipeline support for Jira epics

> Issue: #1557 | Phase: plan | Slice: single (HITL decision-1)

## Goal

Extend the existing `submit_task` pipeline so a Jira **epic key** is a
valid unit of work. The pipeline phases (refine, plan) are unchanged;
two new write sinks are added:

1. **Refine sink** — after HITL approval, the refined analysis is
   written to the epic's `Description` via `editJiraIssue` (wholesale
   rewrite per decision-9).
2. **Plan sink** — after HITL approval, plan nodes are
   `createJiraIssue`'d (or `editJiraIssue`'d for in-place updates) as
   children of the epic, linked by `createIssueLink`, with obsolete
   children transitioned to `Won't Do` by the orchestrator (transitions
   stay off the agent-facing gateway).

Reassess flow (when the epic already has children): existing-child
sweep classifies each child as `done` / `to_do` / `in_flight` /
`updated` / `consolidated` / `split` / `net-new` so the agent can plan
on top of the current state without re-proposing equivalent work or
clobbering work in flight.

Per HITL decision-1, **the entire feature ships as a single slice (one
PR)**. The work is organised into 19 tasks within that slice, sequenced
by the dependency table below.

## Approach

The single slice is implemented in **six logical phases of tasks**,
each phase building on the prior. Phases are an internal organisation
device only — they all ship in one PR.

### Phase A — Foundations (TASK-1-1 through TASK-1-7)

Plumb the new `mode` parameter, the epic-key field on `Pipeline`,
epic-vs-ticket detection, the per-project hierarchy-field config, the
orchestrator-side Jira credentials + transitions client, the gateway
`remoteLinks` read route, and the `EpicApplyArtifact` schema. Pure
additions — no behaviour changes to existing flows.

### Phase B — Refine sink (TASK-1-8 through TASK-1-10)

Refine prompt tweaks so the output is shaped for an epic
`Description`. Confluence link discovery during refine input
gathering. New `apply_epic` agent dispatched after refine HITL
approval to call `editJiraIssue` on the epic.

### Phase C — Plan sink (TASK-1-11 through TASK-1-13)

Plan prompt tweaks for per-node ticket-shaped descriptions, reassess
diff sections, and in-flight markers. Existing-children sweep. Plan
apply step that dispatches the `apply_epic` agent for the batch of
create/edit/link mutations and persists the plan-node → Jira-key
mapping to `phases["plan"].artifacts["epic_apply"]`.

### Phase D — Reassess flow (TASK-1-14, TASK-1-17)

Orchestrator-direct Won't-Do transitions for non-in-flight obsolete
children (atomic batch per decision-3). Per-ticket HITL gate machinery
for in-flight mutations (edit / Won't-Do / consolidate-away) with the
firing signal source recorded on each gate.

### Phase E — Implement-phase fan-out (TASK-1-15, TASK-1-16)

Plan-gate fork (Stop-after-plan vs Continue-to-implement, decision-6).
When Continue is chosen, the implement-phase pipeline fans out per
child ticket — each child is a slice in the implement slice DAG.
PR-link writeback adds a `addCommentToJiraIssue` (and a Jira remote
link when the gateway exposes a write for it) on the child ticket when
its PR opens (feedback Q4).

### Phase F — Tests + docs (TASK-1-18, TASK-1-19)

Unit + integration tests for all the new code paths; documentation
updates under `docs/guides/`.

## Manual steps

Pre-merge:

- Operator adds `ATLASSIAN_API_TOKEN` (or `JIRA_API_TOKEN`) and an
  `ATLASSIAN_USERNAME` with **transition permissions on the Jira
  project** to `~/.config/egg/secrets.env`. Without
  transition-capable creds the Won't-Do step at TASK-1-14 will 403.
- Operator creates `~/.config/egg/jira-hierarchy.yaml` mapping each
  Jira project key to either `parent` or `epic_link`. The apply step
  errors out (refusing to create children) when the epic's project has
  no mapping (decision-2).

Post-merge:

- None required — the new code path is gated by the operator opt-in
  (`submit_task` with an epic key + the YAML config), so existing
  ticket-keyed pipelines are unaffected.

## Risks (delegated to risk_analyst — summary only)

The risk analysis is owned by the `risk_analyst` peer in this plan
phase. Headline risks the planner saw while sequencing the work:

- **Atlassian write rate-limits + 429 retry policy mismatch**: write
  verbs never retry (per `gateway/jira_client.py:43-49`). A
  many-child apply could hit `429` mid-batch — `apply_epic`'s plan
  branch needs explicit per-call error handling that surfaces the
  partial-application state in `epic_apply.applied_edits` so re-runs
  are idempotent.
- **In-flight detection false negatives**: a child mid-implement whose
  pipeline hasn't yet written `pr_url` (orchestrator state) AND whose
  Jira status is still `To Do` AND whose remote-links don't yet name
  the PR — could be mis-classified as `to_do`. Decision-8's `OR`
  semantics mitigate; the per-ticket HITL gate is the operator's last
  line of defence.
- **Plan apply atomicity**: the apply step performs N+M calls per
  HITL approval. A network blip mid-batch leaves the epic partially
  applied; idempotency via the persisted `epic_apply` artifact +
  pre-call dedup against the existing-children sweep mitigates.

    today is extended to accept an epic key: the refine output writes
    to the epic's `Description`, the plan output materialises as child

    that already have children (updating, consolidating, splitting,
    or marking obsolete ones `Won't Do`).

       `auto` on an epic key auto-detects reassess when children

       agent dispatches `editJiraIssue` to wholesale-rewrite the
       epic `Description` with the refined analysis (decision-9).
    4. **Plan sink** — the plan prompt produces per-node Jira-ticket
       descriptions with a fixed structure (Problem statement / Scope
       / Acceptance criteria / Out of scope / Cross-links). After
       HITL approval, the `apply_epic` agent applies the batch:
       `createJiraIssue` for net-new nodes, `editJiraIssue` for
       updates, `editJiraIssue` + `addCommentToJiraIssue` for

       `createIssueLink` for cross-task edges. The plan-node →

       sees a classified diff (`done` / `to_do` / `in_flight` /
       `updated` / `consolidated` / `split` / `net-new`). The
       in-flight signal sources (Jira status, orchestrator
       `pr_url` artifact, remote-link PR URL) are OR'd together
       per decision-8; any in-flight mutation (edit / Won't-Do /
       consolidate-away) is refused by the apply step and instead
       opens a per-ticket HITL gate citing the firing signal.
       Non-in-flight obsolete children are transitioned to
       `Won't Do` atomically by the orchestrator after the
       single plan approval (decision-3).

       `~/.config/egg/jira-hierarchy.yaml` lets operators map each

       are created) vs `Continue-to-implement` (each child becomes
       its own slice in the implement slice DAG, decision-6).
    9. **PR-link writeback** — when a child's implement produces a
       PR, the orchestrator writes back a comment + (when the
       gateway exposes a write) a remote link on the Jira child
       (feedback Q4).

    principal in `~/.config/egg/secrets.env`. Gateway audit and
    transition-denylist invariants are preserved.
