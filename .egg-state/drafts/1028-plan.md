# Plan: Conversational Claude coordinator for dynamic agent orchestration

> Issue: #1028 | Phase: plan

## Summary

This plan implements the architect's recommended approach (Option A: Embedded
Coordinator) for a conversational coordinator agent that understands tasks,
determines workflows, and drives the orchestrator dynamically. The coordinator
is a standard agent container with elevated permissions—not a separate service—
preserving the security model and reusing all existing infrastructure.

The work is organized into five phases within a single PR: (1) coordinator role
and data model, (2) orchestrator API extensions, (3) coordinator executor and
gateway permissions, (4) MCP server, and (5) coordinator agent instructions and
integration testing. Each phase builds on the previous, and the entire feature
is guarded by a `coordinator_enabled` flag in PipelineConfig so existing
pipelines remain unaffected.

## Design Decisions

The architect evaluated three approaches and recommended **Option A: Coordinator
as an Orchestrator Extension**. Key decisions carried forward:

- **Coordinator is an agent container**: Runs `claude --print` like all agents.
  Uses the existing container lifecycle, gateway sessions, and checkpoint
  system. Follows EGG200 convention (no direct Anthropic API calls from infra).
- **Hybrid phase model**: Existing phases (REFINE → PLAN → IMPLEMENT → PR) are
  advisory for coordinator-driven pipelines. The coordinator can skip, reorder,
  or combine phases. A `coordinator` pseudo-phase in the gateway grants
  cross-phase permissions.
- **Orientation not pre-fetching**: The coordinator passes agents task
  objectives and lightweight metadata (issue number, branch, focus area), not
  pre-fetched diffs or file contents.
- **State in orchestrator, not context window**: Workflow decisions are persisted
  as structured state in the Pipeline model. A crashed coordinator re-assesses
  from current state rather than replaying prior reasoning.
- **Opt-in mode**: `coordinator_enabled` flag on PipelineConfig (default false).
  Existing SDLC CLI and fixed-phase pipelines are completely unaffected.
- **MCP server uses SSE transport**: Runs as an orchestrator sidecar, stateless,
  proxies to orchestrator APIs. Supports multiple concurrent Claude Code
  sessions and async/unattended mode.
- **Coordinator tools via REST APIs**: spawn_agent, get_pipeline_state,
  advance_phase, escalate_to_human, send_message, poll_messages, cancel_agent.
  The coordinator calls these via `egg-orch` CLI commands in its Claude session.
- **Cost guardrails**: Max agents per task (default 10), max retry per role
  (default 2), max wall-clock time (configurable). Orchestrator enforces limits.

## Open Questions from Architect

The architect registered 4 HITL decisions and 3 feedback questions. This plan
assumes the architect's recommended defaults:

- **Session persistence**: Checkpoint/resume from orchestrator state (not
  stateless polling or single long session).
- **Phase model**: Hybrid — phases advisory, coordinator can skip/reorder.
- **Authority level**: Full autonomy for routine decisions; escalate for
  ambiguous requirements, architecture decisions, and PR readiness.
- **Scope**: Core coordinator + orchestrator APIs + MCP server (async triggers
  follow in v2).

If human review selects different options, the affected tasks would need
adjustment—particularly Phase 3 (gateway permissions) and Phase 4 (MCP server).

    max retries per role). Returns container info and status.

    open-ended questions. Records in coordinator state.

### Phase 4: MCP Server

**Goal**: Build the SSE-based MCP server that bridges external Claude Code
sessions to the coordinator. This is a net-new component.

**Tasks**:

- **[TASK-4-1]** Create `orchestrator/mcp_server.py` — the MCP server process.
  Uses SSE transport (HTTP). Runs as a sidecar alongside the orchestrator,
  sharing the same network. The server is stateless — all state lives in the
  orchestrator. Key design:

  - Flask or aiohttp application listening on a configurable port
    (default 9850).
  - MCP protocol implementation: tool listing, tool execution, SSE event
    streaming for responses.
  - Authentication: validate requests against gateway session tokens.
  - Rate limiting: configurable max requests per minute (default 30).
  - Health endpoint: `GET /health` for monitoring.
  - Listens only on the egg-isolated network (172.32.0.0/24).

  - **Acceptance**: Server starts and accepts MCP protocol connections via SSE.
    Health endpoint responds. Authentication validates tokens. Rate limiting
    enforced. Tests pass.

- **[TASK-4-2]** Create `orchestrator/mcp_tools.py` — MCP tool definitions that
  proxy to orchestrator APIs:

  - `submit_task` — Accept natural language task description, optional issue
    number, repo, urgency, workflow hint. Create a coordinator-enabled pipeline
    via orchestrator API. Return task ID for tracking.
  - `get_status` — Query task state: coordinator status, running agents, phase,
    pending decisions, recent coordinator decisions. Proxy to coordinator state
    endpoint.
  - `provide_input` — Supply human input for a coordinator escalation. Resolve
    the HITL decision or feedback item via orchestrator API.
  - `list_tasks` — List active and recent coordinator-managed pipelines with
    summary status. Proxy to pipeline list endpoint with coordinator filter.
  - `cancel_task` — Request cancellation. Stop coordinator and all running
    agents via orchestrator API.

  - **Acceptance**: Each tool correctly proxies to the orchestrator API. Tool
    schemas follow MCP protocol specification. Error handling returns clear
    messages. Tests pass.

- **[TASK-4-3]** Add MCP server startup to the orchestrator deployment. The MCP
  server starts as a subprocess or sidecar process managed by the orchestrator.
  Add configuration for MCP server port, authentication, and rate limits.
  Document the MCP server connection URL for Claude Code configuration.
  - **Acceptance**: MCP server starts alongside orchestrator. Configuration
    is documented. Claude Code can connect via SSE. Tests pass.

- **[TASK-4-4]** Write tests for MCP tools: submit_task creates pipeline with
  coordinator_enabled, get_status returns correct state, provide_input resolves
  escalation, list_tasks filters coordinator pipelines, cancel_task stops
  pipeline. Authentication and rate limiting tests.
  - **Acceptance**: All test cases pass with mocked orchestrator client.

**Dependencies**: Phase 3 (needs coordinator executor and gateway permissions).

  - Available tools: `egg-orch coordinator spawn/state/phase/escalate/cancel`,
    `egg-orch message send/poll`, `egg-orch signal *`.
  - Workflow selection guidance: when to skip phases (simple bug fixes), when

  not step-by-step procedures.

## Test Strategy

- **Unit tests**: Each new module (coordinator routes, coordinator executor, MCP
  server, MCP tools) gets dedicated test files with mocked dependencies
  (container spawner, state store, orchestrator client).
- **Integration tests**: Phase 2 includes coordinator API tests; Phase 3
  includes gateway permission tests; Phase 5 includes end-to-end pipeline tests.
- **Backward compatibility tests**: Verify existing pipelines continue to work
  unchanged when `coordinator_enabled` is false (default). All existing test
  suites must continue to pass.
- **Edge cases**: Coordinator crash mid-workflow with running agents, guardrail
  enforcement (max agents exceeded, max retries exceeded, max time exceeded),
  concurrent coordinator escalations, MCP server authentication failure, MCP
  rate limiting, coordinator resume after crash re-assesses state correctly.

## Risk Mitigations

| Risk | Mitigation |
|------|------------|
| Coordinator session lifetime (~200k tokens) | State persists in orchestrator; coordinator checkpoints and resumes from state |
| Runaway agent spawning | Guardrails: max 10 agents, max 2 retries per role, max wall-clock time; orchestrator enforces |
| Gateway permission complexity | Coordinator pseudo-phase is minimal: state writes + orchestrator API only; no source code access |
| MCP server attack surface | Listens only on egg network; authentication via gateway tokens; rate limiting |
| Coordinator crash with running agents | Agents continue and auto-commit; orchestrator detects exit, optionally respawns coordinator |
| Dual execution model maintenance | Coordinator mode reuses existing infra; new code in coordinator-specific files; fixed-phase path unchanged |
| Cost increase from coordinator overhead | Coordinator runs only while actively reasoning; idle between agent runs; guardrail on total agents |
