# Plan: Conversational Claude coordinator for dynamic agent orchestration

> Issue: #1028 | Phase: plan | Revision: 2

## Summary

This plan implements a conversational coordinator agent that understands tasks,
determines workflows, and drives the orchestrator dynamically. The coordinator
is a standard agent container with elevated permissions—not a separate service—
preserving the security model and reusing all existing infrastructure.

The work is organized into five phases within a single PR: (1) coordinator role
and data model, (2) orchestrator API extensions, (3) coordinator executor and
gateway permissions, (4) MCP server, and (5) coordinator agent instructions and
integration testing. Phases 3 and 4 can be parallelized since the MCP server
depends on orchestrator APIs (Phase 2), not gateway permissions. Each phase
builds on its dependencies, and the entire feature is guarded by a
`coordinator_enabled` flag in PipelineConfig so existing pipelines remain
unaffected.

## Architecture Analysis Summary

The architect (`.egg-state/drafts/1028-analysis.md`) evaluated three approaches:

### Option A: Embedded Coordinator (Recommended)

Add a "coordinator mode" to the existing orchestrator. The coordinator runs as a
privileged agent container with a `COORDINATOR` agent role, elevated gateway
permissions, and tools to spawn other agents via orchestrator APIs. Uses
`claude --print` headless mode, consistent with all existing agents.

**Pros**: Reuses existing infrastructure (containers, gateway, message bus).
Orchestrator remains single source of truth. Gateway enforcement preserved.
Incremental (opt-in flag). No new services.

**Cons**: Session lifetime bounded by Claude's context window. Container
overhead for coordinator itself. Orchestrator API needs extensions. Phase
enforcement needs a coordinator-compatible model.

### Option B: External Coordinator (Rejected)

Separate standalone service wrapping the orchestrator, managing a Claude session
via direct Anthropic API calls.

**Rejected because**: Violates EGG200 convention (no direct LLM API calls from
infrastructure code). Adds architectural complexity, duplicated functionality,
and separate credential management.

### Option C: Host-Level Coordinator (Deferred)

Coordinator runs as a Claude Code session on the host, using `egg-orch` CLI.

**Deferred because**: Runs outside sandbox security boundary. Less isolation.
Conflates coordinator with user's development environment. Can evolve from
Option A later.

**Selected**: Option A — coordinator as an orchestrator extension.

## Unresolved HITL Decisions and Assumed Defaults

The analysis registered 4 HITL decisions and 3 feedback questions on the
contract (`1028.json`). None have been resolved by a human. This plan proceeds
with the architect's recommended defaults. For each decision, the assumed
default, affected tasks, and the nature of changes under alternatives are
detailed below.

### Decision 1: Session Persistence Model

**Assumed default**: Checkpoint/resume from orchestrator state.

The coordinator persists workflow decisions to the orchestrator's state store.
After a crash, a new coordinator session re-assesses from current orchestrator
state rather than replaying prior reasoning.

| Alternative | Affected Tasks | Nature of Change |
|------------|----------------|------------------|
| Stateless polling | TASK-1-4 (state store becomes simpler—no checkpoint logic, just current state), TASK-3-1a (executor spawns coordinator periodically instead of once, removes crash/respawn), TASK-5-1 (instructions change to "poll and act" pattern instead of persistent session) | Fundamentally changes coordinator lifecycle from long-running to ephemeral. Simpler crash handling but higher latency and token cost per decision cycle. |
| Long-running session | TASK-1-4 (remove state persistence—coordinator keeps state in context), TASK-3-1b (remove respawn logic entirely), TASK-5-1 (instructions emphasize compact prompts, no resume protocol) | Eliminates state persistence complexity but coordinator cannot survive crashes. Simpler implementation but less resilient. |

### Decision 2: Phase Model

**Assumed default**: Hybrid — phases are advisory; coordinator can skip/reorder
freely with a fallback permission model.

| Alternative | Affected Tasks | Nature of Change |
|------------|----------------|------------------|
| Within existing phases | TASK-3-3 (no coordinator pseudo-phase needed—reuse existing phase permissions per active phase), TASK-3-4 (session uses actual current phase instead of coordinator pseudo-phase), TASK-2-1b (phase endpoint restricted to advance-only, no skip/reorder) | Simpler gateway integration but constrains coordinator flexibility. Phase skip would need to traverse intermediate phases. |
| Outside phases | TASK-3-3 (build entirely new permission model for freeform coordinator, separate from phase-based permissions), TASK-3-4 (new session type outside phase system), TASK-1-1 (Pipeline model needs alternative to phase tracking) | Most complex gateway change. New permission model is a significant design exercise. Risk of divergence from existing security guarantees. |

### Decision 3: Authority Level

**Assumed default**: Full autonomy for routine decisions (spawn agents, skip
phases, loop back); escalate for ambiguous requirements, architecture
decisions, and PR readiness.

| Alternative | Affected Tasks | Nature of Change |
|------------|----------------|------------------|
| Checkpoint approval | TASK-2-1b (phase endpoint requires HITL gate—adds blocking approval flow), TASK-3-1a (coordinator pauses at phase boundaries waiting for human), TASK-5-1 (instructions add mandatory phase-boundary escalation) | Adds latency at every phase transition. Safer for high-stakes work but slower. Coordinator spends more time idle waiting for approvals. |
| Supervised | TASK-2-1a (spawn endpoint requires HITL approval before spawning), TASK-2-1b (all phase/escalate endpoints become approval-gated), TASK-3-1a (coordinator blocks before every significant action), TASK-5-1 (instructions require escalation for every decision), TASK-4-2 (MCP tools need approval workflow for each coordinator action) | Fundamentally changes coordinator from autonomous to advisory. Much higher human interaction overhead. Coordinator becomes more of a recommendation engine than an executor. |

### Decision 4: Scope of Initial Implementation

**Assumed default**: Core coordinator + orchestrator APIs + MCP server (async
triggers in v2).

| Alternative | Affected Tasks | Nature of Change |
|------------|----------------|------------------|
| Full system (add async triggers) | Adds ~3 new tasks: Slack integration, webhook handler, GitHub event trigger. TASK-4-2 (MCP tools need async notification channel in addition to SSE responses). TASK-5-5 (docs cover async modes). | Significantly more work. Async triggers are a natural follow-on but increase v1 scope substantially. |
| Prototype (CLI only, no MCP) | Remove Phase 4 entirely (TASK-4-1a, TASK-4-1b, TASK-4-2, TASK-4-3, TASK-4-4). TASK-5-4 (integration test uses CLI instead of MCP). TASK-5-5 (docs omit MCP setup). | Reduces scope by ~5 tasks. Validates coordinator concept before investing in MCP server. Human interacts via `egg-orch coordinator` CLI commands directly. |

### Feedback Questions (Unanswered)

The following feedback questions are unanswered. The plan uses sensible defaults:

1. **Cost guardrails** (feedback-1): Plan assumes max 10 agents per task, max 2
   retries per role, configurable max wall-clock time. These are enforced by the
   orchestrator in TASK-3-1b. Values are configurable via PipelineConfig.

2. **Crash recovery** (feedback-2): Plan assumes running agents continue and
   auto-commit (existing behavior), orchestrator detects coordinator exit, new
   coordinator optionally respawned to re-assess from state (TASK-3-1b). Human
   notified via existing notification system.

3. **Multi-task coordination** (feedback-3): Plan assumes one coordinator per
   issue for v1. Multiple coordinators can run in parallel across different
   issues (no shared state). Multi-issue coordination deferred to v2.

## Design Decisions

- **Coordinator is an agent container**: Runs `claude --print` like all agents.
  Uses existing container lifecycle, gateway sessions, and checkpoints.
- **Hybrid phase model**: Existing phases advisory for coordinator-driven
  pipelines. Coordinator pseudo-phase in gateway grants cross-phase permissions.
- **Orientation not pre-fetching**: Coordinator passes agents task objectives
  and lightweight metadata, not pre-fetched diffs or file contents.
- **State in orchestrator, not context window**: Workflow decisions persisted as
  structured Pydantic model in Pipeline. Crashed coordinator re-assesses from
  current state.
- **Opt-in mode**: `coordinator_enabled` on PipelineConfig (default false).
- **MCP server uses SSE transport**: Orchestrator sidecar, stateless, proxies
  to orchestrator APIs. Uses the official `mcp` Python package.
- **Coordinator tools via REST APIs**: spawn_agent, get_pipeline_state,
  advance_phase, escalate_to_human, send_message, poll_messages, cancel_agent.
- **Cost guardrails**: Max agents per task (default 10), max retry per role
  (default 2), max wall-clock time (configurable). Orchestrator enforces.

## Test Strategy

- **Unit tests**: Each new module gets dedicated test files with mocked
  dependencies (container spawner, state store, orchestrator client).
- **Integration tests**: Phase 2 coordinator API tests (TASK-2-4); Phase 3
  executor and gateway tests (TASK-3-5); Phase 4 MCP tool tests (TASK-4-4);
  Phase 5 end-to-end pipeline test (TASK-5-4) including workflow decision
  validation.
- **Backward compatibility**: Verify existing pipelines work unchanged when
  `coordinator_enabled` is false (default). All existing test suites pass.
- **Edge cases**: Coordinator crash mid-workflow with running agents, guardrail
  enforcement (max agents, max retries, max time), concurrent escalations, MCP
  auth failure, MCP rate limiting, coordinator resume re-assesses state.

## Risk Mitigations

| Risk | Mitigation |
|------|------------|
| Coordinator session lifetime (~200k tokens) | State persists in orchestrator; coordinator checkpoints and resumes from state |
| Runaway agent spawning | Guardrails: max 10 agents, max 2 retries per role, max wall-clock time; orchestrator enforces |
| Gateway permission complexity | Coordinator pseudo-phase is minimal: state writes + orchestrator API only; no source code access |
| MCP server attack surface | Listens only on egg network; gateway token auth; rate limiting |
| MCP protocol implementation | Uses official `mcp` Python package, not custom protocol |
| Coordinator crash with running agents | Agents continue and auto-commit; orchestrator detects exit, optionally respawns coordinator |
| Dual execution model maintenance | Coordinator mode reuses existing infra; new code in coordinator-specific files; fixed-phase path unchanged |
| Coordinator prompt quality | Integration test (TASK-5-4) includes workflow decision scenario to validate reasonable decisions |
