# Plan: Wire integration tests into PR CI; expand coverage (Parts A, E, F)

> Issue: #2474 | Phase: plan | Pipeline: issue-2474

## Approach

Per the operator's resolved decisions (decision-1) and plan-phase
instructions on `decision-8`, the remaining work for #2474 ships as a
**3-slice DAG / 3 stacked PRs** within this single pipeline run:

| Slice | Owns | Depends on | Runs in parallel with |
|---|---|---|---|
| **slice-1 — Part E** | Promote `ScriptedProvider` to `shared/egg_harness/testing/scripted_provider.py` + 8 new k3s regression tests under `integration_tests/regression/` | — (root) | slice-2 |
| **slice-2 — Part A** | Stage CI wiring under `.github-staging/workflows/` so the `test-integration.yml` reusable workflow runs as a new `integration:` job in `test.yml`, included in `aggregate:` | — (root) | slice-1 |
| **slice-3 — Part F** | `CLAUDE.md` + `docs/guides/testing.md` updates pointing at the new `integration_tests/regression/` subdir and the k3s-only local recipe | slice-1 | — |

slice-3 depends on slice-1 because slice-3's docs reference the
`integration_tests/regression/` directory and the named tests
(generically — no specific filenames per HITL Q6) that slice-1
creates. slice-3 does **not** depend on slice-2: slice-3's references
to the required-check name `Test / aggregate` are forward-looking
human documentation that's correct regardless of slice-2's PR-merge
order, and the operator's plan-phase instructions explicitly
specified only one dependency edge (slice-3 → slice-1).

The forest constraint (≤1 DAG parent per slice) is satisfied
trivially — slice-3 has exactly one parent, and slice-1/slice-2 are
roots. No `serialized_chain_order` is needed.

## Slice rationale

### slice-1 (Part E) — Test infrastructure + 8 new regressions

The new tests live in a dedicated `integration_tests/regression/`
subdirectory with a shared `conftest.py` that re-exports the parent
k8s fixtures and adds the helpers the 8 tests need in common
(deterministic-pipeline-id helper, kubectl-pod-env reader, BRC-message
counter, gateway-audit-log reader). Promoting `ScriptedProvider` from
`shared/tests/test_egg_harness/test_integration.py` to
`shared/egg_harness/testing/scripted_provider.py` is a prerequisite
for `test_hitl_round_trip.py` (#2430) and any future test that needs
to hand each agent role a canned LLM trajectory; the existing five
in-suite consumers continue to import the same class from the new
public location via a re-export shim.

Each new test is structured so that it **passes against current
`main`**. Per the operator's scope-expansion instruction, if a new
test surfaces an actual regression against `main`, the production-code
fix lands in **this slice's PR** rather than being deferred — that is
the explicit purpose of the new coverage.

The 8 tests, with their HITL-resolved shapes:

| # | File | Covers | Shape |
|---|---|---|---|
| E.1 | `test_slice_branch_env.py` | #2428 slice spawn env threading | 2-slice DAG; `kubectl get pod -o jsonpath` asserts each slice coder's `EGG_BRANCH` matches its slice ref |

### slice-2 (Part A) — Wire `test-integration.yml` into PR CI

Per decision-2, the `workflow_call` lives in `test.yml` as a new
`integration:` job sibling to `unit:` and `security:`, included in
the existing `aggregate:` job's `needs:` list so the canonical
required-check name stays `Test / aggregate`.

**Why `.github-staging/`**: every producer role (including coder) is
blocked from writing under `.github/` — that's a hard
branch-protection invariant, not a planner mistake. Slice-2's
work therefore stages the proposed end-state under top-level
`.github-staging/workflows/`, mirroring the `.github/workflows/`
layout. The orchestrator's PR builder auto-detects
`.github-staging/` on slice-2's PR and emits a manual pre-merge
step asking the human reviewer to `git mv .github-staging/workflows/*
.github/workflows/` before merge. (`.github-staging/` is tracked by
git; do NOT add it to `.gitignore` or the staged files won't be in
the commit and the reviewer's `git mv` will fail.)

The two staged files are:

1. `.github-staging/workflows/test.yml` — full end-state of the
   wired-in version of the existing `test.yml`. Adds the new
   `integration:` job (calling `./.github/workflows/test-integration.yml`
   once it has been moved) and updates `aggregate:`'s `needs:` to
   `[unit, security, integration]` so the aggregate fails when the
   integration tier fails. Adds `timeout-minutes: 30` to the
   `integration:` job. Existing `pull_request:` trigger and
   `concurrency:` block stay.
2. `.github-staging/workflows/test-integration.yml` — full end-state
   of the hardened version of the existing reusable workflow. Adds
   the three flake guards from HITL Q1: (a) retry on the "Import
   images into k3s" step (2–3 attempts), (b) explicit
   `--timeout=120s` on every `kubectl wait`, (c) on-failure
   capture of `kubectl get events --all-namespaces -o yaml` plus
   pod logs as a `k3s-debug` workflow artifact. Existing
   `workflow_call` + `workflow_dispatch` triggers stay.

**Gating policy** (decision-3): required-for-merge **from day 1**.
slice-2's PR description must call out the exact required-check name
(`Test / aggregate`) for the human merger to flip in
Settings → Branch protection. This is the post-merge step.

## Test strategy

### Automated

- **`make lint`** runs on every slice via the existing `Lint`
  workflow (`.github/workflows/lint.yml`) on PR.
- **`make test-all`** (unit suite) runs on every slice via
  `test.yml`'s `unit:` job. slice-1 adds tests under `integration_tests/regression/`
  which are NOT collected by `make test-all` (testpaths excludes
  `integration_tests/`), so the unit job stays green throughout.
- **`make test-integration`** runs against k3s on every slice **once
  slice-2 lands**. Locally and via `workflow_dispatch` before that.
- **Promoted ScriptedProvider**: a tiny new unit test
  `shared/tests/test_egg_harness/test_scripted_provider.py` proves
  the import path resolves and the public API matches. Catches
  accidental deletion or rename.
- **8 new regression tests** in slice-1 each carry an inline
  assertion that fails against `main` if the production fix is
  reverted (slice-1 acceptance criteria spell out the reversion
  scenario per test).

### Manual

- After slice-2 merges: reviewer/maintainer flips `Test / aggregate`
  to required in repo Settings → Branch protection. This is the
  branch-protection toggle decision-3 requires; only a human with
  admin rights can perform it.
- After slice-2 merges: reviewer follows the `docs/guides/testing.md`
  k3s-on-host recipe on a fresh laptop (or VM) and confirms
  `make test-integration` reaches green.
- After slice-1 merges: optional — manually trigger
  `test-integration.yml` via `workflow_dispatch` on slice-1's branch
  to confirm the new tests pass in CI before slice-2's wiring forces
  them onto every PR.

## Manual steps

**Pre-merge (slice-2)**: trigger `test-integration.yml` via
`workflow_dispatch` against slice-2's branch and confirm the new
`Test / aggregate` aggregate completes green. Required because once
slice-2 merges the check becomes required from day 1 (decision-3).

**Pre-merge (slice-2)**: human reviewer performs
`git mv .github-staging/workflows/test.yml .github/workflows/test.yml`
and
`git mv .github-staging/workflows/test-integration.yml .github/workflows/test-integration.yml`
(commit & push) before merging slice-2. The orchestrator surfaces
this as a Pre-merge Obligation on slice-2's PR body because coder
cannot write under `.github/`.

**Post-merge (slice-2)**: repo admin flips `Test / aggregate` to
required-for-merge in Settings → Branch protection. This is the only
human-only step in #2474 and the operator chose
required-from-day-1 (decision-3), so it MUST happen at slice-2
merge time, not deferred.

**Post-merge (none)** for slice-1 and slice-3.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| New k3s tests in slice-1 surface real regressions against `main` | Per operator scope-expansion: fix the production-code root cause in slice-1's PR. Risk-analyst will inventory the most likely fail-on-main candidates. |
| Slice-2 required-from-day-1 amplifies flake into PR-merge blockers | HITL Q1 flake guards (image-import retry, kubectl wait timeouts, on-failure k3s-debug artifact) mitigate the standard set. No fixed wall-clock budget (decision-5) — flag in follow-up if PR latency becomes a complaint. |
| `ScriptedProvider` re-export drifts the API for the existing 5 in-suite consumers | Slice-1 keeps the existing call sites in `test_integration.py` as canaries — they continue to construct `ScriptedProvider(script)` exactly as today. The new public class is the same class, not a wrapper. |
| `TestCredentialIsolation` still skipped under k3s | Out-of-scope per decision-7; tracked in follow-up #2585. Plan does NOT include a rewrite. |
| slice-3 docs reference test files by name and go stale | HITL Q6 chose generic note pointing at `integration_tests/regression/`; no specific filenames. |
| slice-2's `.github-staging/` files miss the reviewer's `git mv` | Orchestrator's PR builder surfaces the obligation in slice-2's PR body. Belt-and-braces: slice-2's PR description and `manual_steps` both spell out the exact `git mv` commands. |
| Required-from-day-1 erodes trust if first run flakes | HITL Q5 explicitly accepted this trade-off — non-blocking settle-in was rejected. Roll back via repo config (Settings → Branch protection) if necessary, NOT a code change. |
| 3-slice/restart-in-PROPOSE scenario (E.6) is sensitive to orchestrator timing | Test uses deterministic checkpoints (wait for `CONSENSUS_PROPOSE` message arrival before restart) rather than wall-clock sleeps. |
