# Plan: Agent Anchor Mechanism for Post-Compaction State Recovery

> Issue: #1032 | Phase: plan

## Summary

Implement a persistent anchor mechanism that allows agents to recover coherent working state after context window clears. Instead of lossy compaction, agents will fully clear their context and reload from a structured JSON anchor file that captures task progress, cross-agent decisions, BRC consensus state, and key context. This is a cross-cutting feature touching the shared library (`shared/egg_anchor/`), orchestrator CLI and API, Redis storage, gateway phase filter, container spawner, sandbox rules, and consensus wrapper.

The approach follows Option A from the analysis: implement as specified in the issue with phased delivery. All design decisions are resolved in the issue. The implementation follows existing codebase patterns — Pydantic models, Flask Blueprints, Redis key prefixes, JSON Schema validation, and argparse CLI subcommands.

## Implementation Phases

### Phase 1: Core Infrastructure — Schema, Constants, Python Library, CLI

**Goal**: Establish the foundation — JSON Schema for validation, constants for size limits and key prefixes, the `shared/egg_anchor/` Python library with models and atomic I/O, and the `egg-orch anchor` CLI subcommands.

**Tasks**:
- [TASK-1-1] Create JSON Schema at `.egg/schemas/agent-anchor.schema.json` — Acceptance: Schema validates all required fields (`_meta`, `agent_id`, `role`, `team`, `task`, `status`), enforces size constraints (`maxItems` on progress/decisions/key_context/errors_encountered/files_modified, `maxLength` on string fields), and matches the structure defined in the issue. `python -m jsonschema` validates a sample anchor document.
- [TASK-1-2] Add anchor constants to `shared/egg_config/constants.py` — Acceptance: Constants defined for `ANCHOR_SOFT_LIMIT_BYTES` (2048), `ANCHOR_HARD_LIMIT_BYTES` (3072), `ANCHOR_TEAM_SOFT_LIMIT_BYTES` (4096), `ANCHOR_TEAM_HARD_LIMIT_BYTES` (6144), `ANCHOR_REDIS_PREFIX` ("anchor"), `ANCHOR_MAX_PROGRESS_ITEMS` (10), `ANCHOR_MAX_DECISIONS` (8), `ANCHOR_MAX_KEY_CONTEXT` (5), `ANCHOR_MAX_ERRORS` (5), `ANCHOR_MAX_FILES` (15). Importable from `egg_config`.
- [TASK-1-3] Create `shared/egg_anchor/` Python library — Acceptance: Package contains `__init__.py`, `models.py` (Pydantic models for `AgentAnchor`, `AnchorMeta`, `ProgressItem`, `Decision`, `BRCState`, `KeyContext`, `ErrorEncountered`), `loader.py` (atomic read/write with temp-file-then-rename, API sync helper), `validator.py` (schema validation, size budget checking with soft/hard limit enforcement), and `constants.py` (re-exports from egg_config). All operations are atomic and all-or-nothing. Unit tests pass for models, serialization/deserialization, atomic write, size validation.
- [TASK-1-4] Add `egg-orch anchor` CLI subcommands to `orchestrator/cli.py` — Acceptance: Subcommands `init`, `update`, `show`, `validate`, `cleanup` are registered. `init --task "..."` creates an initial anchor file. `update` accepts `--status`, `--progress`, `--decision`, `--key-context`, `--error`, `--file` flags (batch updates are atomic). `show` displays own anchor (default) or `--agent <id>` or `--team` via API. `validate` checks schema and size limits. `cleanup` removes orphaned anchors. All commands support `--json` output.

**Dependencies**: None — this is the foundation.

**Exit criteria**: `egg-orch anchor init --task "Test task"` creates a valid anchor file at `.egg-state/agent-anchors/<agent-id>.json`; `egg-orch anchor update --status in_progress` updates it atomically; `egg-orch anchor show` displays it; `egg-orch anchor validate` passes.

### Phase 2: Orchestrator API + Redis Storage

**Goal**: Add REST API endpoints for anchor CRUD and team anchor generation, backed by Redis for durable cross-agent access.

**Tasks**:
- [TASK-2-1] Create anchor API routes at `orchestrator/routes/anchors.py` — Acceptance: Flask Blueprint registered with endpoints: `POST /api/v1/anchors/{agent_id}` (create/update), `GET /api/v1/anchors/{agent_id}` (read single), `GET /api/v1/anchors/team/{pipeline_id}` (team anchor), `DELETE /api/v1/anchors/{agent_id}` (cleanup). Endpoints validate JSON Schema on write. Team anchor endpoint generates a projection from individual anchors + pipeline state.
- [TASK-2-2] Add Redis persistence for anchors — Acceptance: Anchors stored at `anchor:{pipeline_id}:{agent_id}` Redis keys using JSON values (SET/GET, not Streams). TTL of 7 days for failed pipelines. `anchor init` and `anchor update` CLI commands sync to Redis via the API after local file write. Read operations try Redis first (for cross-agent reads), fall back to local file.
- [TASK-2-3] Implement team anchor generation logic — Acceptance: `GET /api/v1/anchors/team/{pipeline_id}` returns a combined view of all agent anchors for the pipeline, including: agent statuses and current tasks, team-level decisions, dependency graph (waiting_on/blocked_by), BRC consensus summary (confirmed/pending agents), and escalation history. Generated from individual anchors + pipeline state — never written by any agent.
- [TASK-2-4] Register the anchors Blueprint in the orchestrator app — Acceptance: Blueprint registered in `orchestrator/routes/` init or app factory. API endpoints reachable via `curl http://egg-orchestrator:9849/api/v1/anchors/...`.

**Dependencies**: Phase 1 (models, constants, loader).

**Exit criteria**: `curl -X POST .../api/v1/anchors/<id>` stores an anchor in Redis; `curl .../api/v1/anchors/team/<pipeline_id>` returns a team view; `egg-orch anchor show --agent <id>` reads from API.

### Phase 3: Gateway + Agent Integration

**Goal**: Enable anchor file writes through the gateway in all phases, enforce agent-scoped writes, integrate with container spawner and consensus wrapper, and add the sandbox recovery rule.

**Tasks**:
- [TASK-3-1] Add `.egg-state/agent-anchors/*` to gateway phase filter allowed patterns — Acceptance: `gateway/phase_filter.py` allows writes to `.egg-state/agent-anchors/*` in all phases (refine, plan, implement). `.egg/phase-permissions.json` updated with the new pattern. Gateway rejects writes to anchor files not matching the session's agent ID.
- [TASK-3-2] Add session-scoped write validation for anchor files — Acceptance: Gateway extracts `agent_id` from anchor filename, compares against session metadata (`AGENT_ANCHOR_ID` env var). Agent can only write to `.egg-state/agent-anchors/<own-agent-id>.json`. Cross-agent writes are rejected with 403.
- [TASK-3-3] Update container spawner to set `AGENT_ANCHOR_ID` env var and compaction flag — Acceptance: `orchestrator/container_spawner.py` sets `AGENT_ANCHOR_ID` (format: `{role}-{short_container_id}`) and compaction-disabled flag (e.g., `--no-compact` or equivalent) in the spawned container environment. Agent ID available via `AGENT_ANCHOR_ID` env var inside the container.
- [TASK-3-4] Create sandbox recovery rule at `sandbox/.claude/rules/anchor-recovery.md` — Acceptance: Rule file documents the post-compaction recovery protocol: (1) read own anchor via `egg-orch anchor show`, (2) poll message bus for messages since `last_message_id`, (3) verify file state against `git log`, (4) resume from current progress item, (5) update anchor after recovery. Standing instruction for all agents.
- [TASK-3-5] Extend consensus wrapper recovery prompt to load anchor — Acceptance: `orchestrator/consensus_wrapper.py` recovery prompt includes anchor data when `AGENT_ANCHOR_ID` is set. `_RECOVERY_SYSTEM_PROMPT` template enhanced with `{anchor_state}` placeholder. Recovery flow: load anchor → inject into prompt → resume BRC from `brc_state`.

**Dependencies**: Phase 1 (library), Phase 2 (API for cross-agent reads).

**Exit criteria**: Agent can push anchor file through gateway; gateway rejects cross-agent anchor writes; container spawner sets `AGENT_ANCHOR_ID`; consensus wrapper loads anchor on recovery.

### Phase 4: Checkpoint Integration + Lifecycle Management

**Goal**: Include anchors in checkpoint captures, implement orchestrator GC for orphaned anchors, and handle pipeline completion archival.

**Tasks**:
- [TASK-4-1] Include anchor files in checkpoint captures — Acceptance: Checkpoint handler captures `.egg-state/agent-anchors/*.json` files alongside other state. `egg-checkpoint show` displays anchor data when present. Anchor data included in checkpoint JSON under `anchors` key.
- [TASK-4-2] Implement orchestrator GC for orphaned anchors — Acceptance: Orchestrator periodically checks for anchors belonging to terminated agents or completed pipelines. Completed pipeline anchors are archived to checkpoint then cleared from Redis. Failed pipeline anchors retained for 7-day TTL. `egg-orch anchor cleanup` triggers manual GC.
- [TASK-4-3] Handle pipeline lifecycle events for anchors — Acceptance: On agent spawn: `egg-orch anchor init` creates initial anchor. On agent CONFIRMED (BRC): anchor `status` updated to `confirmed`. On clean termination: anchor retained in Redis and local file. On crash: anchor retained for recovery/debugging. On pipeline complete: archived to checkpoint, Redis keys cleared. On pipeline fail: retained until 7-day TTL.

**Dependencies**: Phases 1-3.

**Exit criteria**: `egg-checkpoint show` displays anchor data; orphaned anchors are cleaned up after pipeline completion; 7-day TTL respected for failed pipelines.

## Test Strategy

- **Unit tests** (`shared/egg_anchor/tests/`):
  - Model serialization/deserialization round-trips
  - Schema validation (valid and invalid anchor documents)
  - Size budget enforcement (soft limit warning, hard limit rejection)
  - Atomic file write (temp-then-rename, concurrent read safety)
  - Loader API sync (mock HTTP)

- **Unit tests** (`orchestrator/tests/`):
  - CLI subcommand tests (`test_cli_anchor.py`): init, update, show, validate, cleanup
  - API route tests (`test_anchors_routes.py`): CRUD endpoints, team anchor generation
  - Redis persistence tests: key naming, TTL, serialization
  - Consensus wrapper recovery with anchor loading
  - Container spawner env var injection

- **Integration tests** (`gateway/tests/`):
  - Phase filter allows anchor writes in all phases
  - Session-scoped validation rejects cross-agent writes
  - End-to-end: agent writes anchor → reads via API → recovers after clear

- **Manual testing**:
  - Run a pipeline with anchors enabled; verify anchor files are created at milestones
  - Simulate context clear: clear agent context, verify recovery from anchor
  - Verify team anchor shows correct combined state for multi-agent pipeline

## Rollback Plan

The anchor system is additive — it introduces new files, endpoints, and CLI commands without modifying existing behavior. To rollback:

1. Revert the PR (single PR, single revert)
2. Existing pipelines without anchors continue to work unchanged
3. The backward-compat nature of the consensus wrapper means recovery still works via the existing `_RECOVERY_SYSTEM_PROMPT` without anchor data
4. Container spawner simply won't set `AGENT_ANCHOR_ID` — no env var means no anchor behavior
5. Redis keys with `anchor:` prefix can be cleaned up via `redis-cli KEYS "anchor:*" | xargs redis-cli DEL`

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Anchor file corruption from interrupted writes | Low | High | Atomic temp-file-then-rename pattern; all writes are all-or-nothing |
| Anchor exceeds size budget, bloating context | Low | Medium | JSON Schema `maxItems`/`maxLength` constraints; hard limit rejection in CLI |
| Stale anchor after rapid state changes | Medium | Low | `_meta.sequence` monotonic counter; `_meta.updated_at` timestamp; message catch-up via `last_message_id` |
| Cross-agent anchor tampering | Low | High | Gateway session-scoped write validation; agent can only write own anchor |
| Compaction-disabled flag unavailable in runtime | Medium | Medium | Validate flag availability before rollout; fall back to CLAUDE.md instruction if flag not supported |
| Redis anchor data loss on orchestrator restart | Low | Medium | Local anchor file is source of truth; Redis is durable backup + cross-agent read path |
| Team anchor generation slow for large teams | Low | Low | Max team size is bounded by pipeline config; projection is simple aggregation |

## Migration Notes

- **No database migrations** — anchors use file system (`.egg-state/agent-anchors/`) and Redis.
- **Gateway config change** — `.egg/phase-permissions.json` updated to allow anchor file writes. Must be deployed with the gateway.
- **Container spawner change** — New env vars (`AGENT_ANCHOR_ID`, compaction flag). Backward-compatible — containers without these vars behave as before.
- **Breaking change: None** — The anchor system is purely additive. Existing pipelines without anchors are unaffected.
