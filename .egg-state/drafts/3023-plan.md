# Plan: Orchestrator-driven on-demand agent spawning — lift the event pump out of the pod so idle agents don't exist

> Issue: #3023 | Phase: plan | Refine artifact: `.egg-state/drafts/3023-analysis.md`

## Goal

Invert today's lifecycle from "phase-start spawn-all + long-lived in-pod event-pump bash loop" to
"orchestrator-owned event loop + per-event one-shot pod spawn that exits when the agent finishes".

The analysis (cq-1..cq-6 resolutions, refine artifact §"Recommended Approach") settled on **Option A**:

- Orchestrator's existing per-phase run loop in `routes/pipelines.py` adds a per-role inner tick that
  calls `_derive_next_action(tracker, role)` in-process (no HTTP round-trip).
- On `action ∈ {propose, ack, nack, confirm}`, the orchestrator composes the per-event prompt by
  calling `compose_event_prompt` in-process, then spawns a one-shot k8s Job whose container command
  is `python3 -m egg_agent --model X --max-turns N` with the composed prompt on stdin.
- The per-`(pipeline_id, role)` worktree PVC is created at phase start and reused across every
  spawn; the gateway session is created once per `(pipeline_id, role)` at phase start and refreshed
  by an orchestrator-side keep-alive (cq-2).
- The idle-budget overseer alert moves from the wrapper to the orchestrator and becomes a
  phase-level "no spawns for X minutes" signal (cq-3) at the existing 30-minute threshold
  (feedback Q5: do not retune).
- `orchestrator/consensus_wrapper.py` is deleted entirely (cq-5).
- Rollout is big-bang, rollback-by-git-revert (cq-4).
- Overseer agents are out of scope for this PR; a follow-up issue is filed for the unification (cq-6).

The work decomposes into **three dependent slices**, all landing in a single PR (cq-4 big-bang):

1. **Slice 1 — Orchestrator-side phase-level idle-budget alert.** Move the
   `stuck-phase-transition` anomaly tag emitter from the in-pod wrapper to an orchestrator
   timer. Lands first so a real signal exists before pods stop existing. No behaviour change
   for the in-pod wrapper yet — both emitters can coexist during the slice's burn-in within the
   PR.
2. **Slice 2 — On-demand spawner + per-`(pipeline_id, role)` worktree-PVC and gateway-session reuse.**
   The new `orchestrator/on_demand_spawner.py` module + the per-phase tick that drives it via
   `_derive_next_action` + `compose_event_prompt` in-process. Worktree PVC and gateway session are
   created once per `(pipeline_id, role)` and reused across every spawn for that role. The
   long-lived wrapper pods that `spawn_all` still launches in this slice are made **passive**
   for the burn-in commit by short-circuiting their `while true` event-pump loop at the top
   with an `EGG_EVENT_LOOP_OWNER=orchestrator` env guard (analogous to task-1-3's
   `EGG_PHASE_IDLE_BUDGET_OWNER=orchestrator`). The orchestrator owns event dispatch; the
   wrapper pod becomes a no-op container that holds the worktree PVC mount and heartbeats until
   slice 3 deletes it. This makes the two paths **mutually exclusive in slice 2 itself**, not
   just at the slice-3 boundary — the integration test in task 2-8 can therefore assert
   "exactly one spawn per actionable event" without a tracker race.
3. **Slice 3 — `consensus_wrapper.py` retirement + entrypoint simplification.** Pod entrypoint
   becomes `python3 -m egg_agent --model X --max-turns N` with the composed prompt on stdin.
   `orchestrator/consensus_wrapper.py`, `build_consensus_wrapped_command`, and
   `build_event_pump_wrapped_command` are deleted; their call sites in
   `concurrent_executor.py` and `routes/pipelines.py` shift to the on-demand path.
   `ConcurrentExecutor.spawn_all` collapses to "tracker registration + on-demand pre-warm"
   (see task-3-2); the long-lived per-role pod is no longer spawned at phase start.

## Risk-analyst Q1–Q3 (architect answers)

The risk_analyst's artifact poses three architect questions that the plan must answer
before it is implementable. Verbatim answers below, with the task that carries the
mitigation:

| Q | Answer | Task(s) |
|---|---|---|
| **Q1** — worktree-PVC access mode in production k3s (RWO vs. RWX) | **ReadWriteOnce, per-role.** Feedback Q3 anchors on today's `kubernetes_spawner.py` per-role-PVC pattern. Each `(pipeline_id, role)` has its own PVC; no cross-role mount contention is possible. Same-role contention is the only failure mode and is mitigated by the per-role single-pod-in-flight precondition. | TASK-2-9, TASK-2-11 |
| **Q2** — orchestrator-side gateway keep-alive thread shape (per-pipeline / per-role / single multiplexed) | **Single multiplexed loop**, driven by the orchestrator's existing per-phase tick (the same tick that drives `OnDemandSpawner.tick`). `OrchestratorSessionKeepAlive.refresh_all(now)` walks the `{(pipeline_id, role): SessionRecord}` map once per iteration. No new threads. The hot-path risk (R9) is bounded by the tick's existing latency budget. | TASK-2-6, TASK-2-8 |
| **Q3** — orphan-commit detector — land here or piggyback on #2958 | **Land in this issue (slice 2).** The pod-exit-before-BRC-verb-finalized race (R6) is created by the on-demand model itself; #2958's multi-commit-per-spawn lifecycle composes with it but is not a prerequisite. Designing once here keeps the detector authoritative under both lifecycles. | TASK-2-10 |

## Slice 1 — Orchestrator-side phase-level idle-budget alert

**Goal**: Move the 30-min `stuck-phase-transition` OVERSEER_ALERT from
`consensus_wrapper.py:531-549` (per-role, in-pod) to an orchestrator-side per-phase timer
(cq-3), keeping the threshold (feedback Q5). This lands first so a signal exists before any
pods stop existing in slice 2.

**Dependencies**: none (in-process orchestrator change only).

### Tasks

- **[TASK-1-1]** Create `orchestrator/phase_idle_budget.py` with a `PhaseIdleBudgetTimer`
  class. It owns:
  - A `DEFAULT_PHASE_IDLE_BUDGET_MIN = 30` constant (parity with
    `consensus_wrapper.py:59`'s `EGG_BRC_IDLE_BUDGET_MIN`, feedback Q5).
  - State `(pipeline_id, phase, last_spawn_at, last_alert_at, per_role_last_action)` —
    the per-role last-action map (AC-R4 mitigation) gives operators back the per-role
    drill-down they had with today's wrapper alert, even though the alert itself is now
    phase-level (cq-3).
  - A `record_spawn(pipeline_id, phase, role, action)` API that resets `last_spawn_at` and
    updates `per_role_last_action[role] = (action, now)`.
  - A `check(now, pending_hitl_count)` API that emits `stuck-phase-transition` once at the
    1× threshold and once at the 2× threshold (matching today's wrapper semantics at
    `consensus_wrapper.py:531-549`), via the `mcp__progress__overseer_alert`-equivalent
    direct orchestrator entry point used by `orchestrator/overseer/monitor.py`.
  - **HITL-pending suppression (AC-R13)**: when `pending_hitl_count > 0`, the alert is
    downgraded to `priority=low` and the alert body carries
    `pending_hitl_ids: [...]` in `reason`, so the operator sees the alert as a benign
    "stalled on operator input" signal rather than a runtime-health red flag. The 2×
    threshold alert is suppressed entirely while HITL is pending (the operator already
    has an open ask).
  - **`per_role_state` payload field (AC-R4)**: every emitted alert includes a structured
    `per_role_state: {<role>: {"last_action": str, "minutes_since": int}}` field, derived
    from `per_role_last_action`. This is the drill-down the per-role wrapper alert
    provided; operators reading the alert can see exactly which roles are idle and for
    how long.
  - Idempotent re-fire (does not re-emit while still inside the same threshold bucket).
  - **Acceptance**: file exists; class exposes `record_spawn`, `check`, `reset`; constant equals 30;
    unit tests cover (a) 0 idle minutes → no emit, (b) 30 idle minutes → 1× emit once with
    a populated `per_role_state` payload field, (c) 60 idle minutes → 2× emit once (1× not
    re-emitted), (d) `record_spawn(role=X, action=Y)` resets and updates per-role state,
    (e) idempotent across multiple `check(now)` calls inside the same bucket,
    (f) **HITL-pending suppression**: with `pending_hitl_count=1` at the 30-min threshold,
    the emitted alert has `priority=low` and lists the pending HITL ID in `reason`;
    (g) **HITL-pending 2× suppression**: with `pending_hitl_count=1` at 60-min, no
    additional alert is emitted (the 1× LOW alert from (f) remains the most recent).
  - **Files affected**: `orchestrator/phase_idle_budget.py` (new),
    `orchestrator/tests/test_phase_idle_budget.py` (new).

- **[TASK-1-2]** Wire `PhaseIdleBudgetTimer.check(now, pending_hitl_count)` into the orchestrator's
  existing per-phase tick in `orchestrator/routes/pipelines.py` (the run loop that already polls
  consensus for phase-completion). Each tick:
  1. Reads the pending-HITL count for this pipeline from `orchestrator/routes/decisions.py`
     (whichever helper exposes the open-decision count; the tick already reads decision
     state for phase-completion gating).
  2. Calls `PhaseIdleBudgetTimer.check(now=time.monotonic(), pending_hitl_count=...)` for
     the active phase.
  3. Surfaces a structured log line `phase_idle_budget_tick(pipeline_id, phase, idle_minutes,
     pending_hitl_count)` once per emitted alert.
  - **Acceptance**: tick invokes `check` exactly once per loop iteration; test asserts that
    after the wall-clock fixture advances past 30 minutes with no `record_spawn` calls and
    zero pending HITL, the overseer alert handler is invoked exactly once with
    `anomaly="stuck-phase-transition"` and `priority=medium`; second test asserts that with
    one pending HITL, the same idle interval emits `priority=low` and the pending HITL ID
    appears in `reason`.
  - **Files affected**: `orchestrator/routes/pipelines.py`,
    `orchestrator/tests/test_pipelines_phase_idle_budget.py` (new).

- **[TASK-1-3]** Coexistence guard: while the in-pod wrapper still exists (it does, until slice 3),
  the orchestrator-side timer is the authoritative emitter and the wrapper's
  `consensus_wrapper.py:531-549` emitter is **silenced** behind a code-path branch keyed on
  "an orchestrator-side timer is running" — detected by the wrapper at startup via a new
  `EGG_PHASE_IDLE_BUDGET_OWNER=orchestrator` env var injected by
  `concurrent_executor._spawn_agent`. In this slice we **inject the env var unconditionally**;
  slice 3 deletes the wrapper-side emitter outright.
  - **Acceptance**: `EGG_PHASE_IDLE_BUDGET_OWNER=orchestrator` appears in the spawn env emitted
    by `_spawn_agent` for every role; wrapper unit test confirms the alert subshell short-circuits
    when the var is set; the alert is emitted exactly once per phase per threshold (no double-emit).
  - **Files affected**: `orchestrator/concurrent_executor.py`,
    `orchestrator/consensus_wrapper.py:531-549` (gated short-circuit; full deletion deferred to
    task-3-1), `orchestrator/tests/test_consensus_wrapper.py`.

## Slice 2 — On-demand spawner + worktree-PVC and gateway-session reuse

**Goal**: Drive one pod spawn per actionable event (cq-1, feedback Q4). Reuse the per-role
worktree PVC and gateway session across every spawn for that role (cq-2).

**Dependencies**: slice 1 (so an idle-budget alert exists during burn-in).

### Tasks

- **[TASK-2-0]** Coexistence guard for the long-lived wrapper pod (BLOCKER 1 resolution).
  `spawn_all` still spawns one wrapper-wrapped pod per role in slice 2 (the wrapper-deletion
  lands in slice 3 / task-3-1). Without a guard, both that pod's in-pod `while true` event
  loop at `consensus_wrapper.py:564-602` AND the orchestrator's new on-demand tick (task-2-8)
  would call `egg-orch brc next-action`, compose prompts, and emit `mcp__brc__propose`/
  `ack`/`nack` for the same actionable event — double-commit, double-BRC-verb emission,
  tracker races. Resolution mirrors task-1-3 exactly: a new `EGG_EVENT_LOOP_OWNER` env var
  unconditionally injected with value `orchestrator` by
  `concurrent_executor._spawn_agent`, and a short-circuit at the very top of the
  `_EVENT_PUMP_WRAPPER_TEMPLATE`'s main loop (`consensus_wrapper.py:564`) that turns the
  loop into a passive sleep when `EGG_EVENT_LOOP_OWNER=orchestrator`:
  ```bash
  if [ "${{EGG_EVENT_LOOP_OWNER:-}}" = "orchestrator" ]; then
      cw_log "Event-pump owner is the orchestrator; wrapper enters passive mode (heartbeat only)."
      emit_heartbeat "WAITING_FOR_EVENT" "passive (orchestrator-owned event loop)"
      # Sleep forever — the pod holds the worktree PVC mount + emits heartbeats
      # to keep the gateway session warm. SIGTERM from the orchestrator at phase
      # end (or slice-3 retirement) reaps it via the EXIT trap installed above.
      while true; do
          sleep "$HB_INTERVAL_SECS"
          emit_heartbeat "WAITING_FOR_EVENT" "passive (orchestrator-owned event loop)"
      done
  fi
  ```
  The branch lands at the top of the `while true` loop (before `fetch_state`), so the
  passive pod never calls `egg-orch brc next-action` and never invokes the agent — there
  is no path on which both pods can act on the same event. The branch is unconditionally
  active in slice 2 (env var is always injected) and becomes dead code in slice 3 along
  with the rest of the wrapper.
  - **Acceptance**: env var injection asserted (alongside task-1-3's existing assertion);
    new wrapper unit test under `orchestrator/tests/test_consensus_wrapper.py` confirms
    that with `EGG_EVENT_LOOP_OWNER=orchestrator` set, the wrapper does NOT call
    `egg-orch brc next-action`, does NOT invoke the agent, and DOES emit heartbeats;
    integration test in task-2-8 asserts exactly one BRC verb is emitted per actionable
    event (no double-emit from the two paths).
  - **Files affected**: `orchestrator/consensus_wrapper.py:560-602`,
    `orchestrator/concurrent_executor.py` (injection — extending task-1-3's existing
    env-var addition), `orchestrator/tests/test_consensus_wrapper.py`.

- **[TASK-2-1]** Expose `_derive_next_action` from `orchestrator/routes/consensus.py:280-406` as a
  module-level callable that the orchestrator run loop can call in-process. Today it is a
  module-private function reached via the HTTP route. Add a thin public `derive_next_action(...)`
  alias that takes a `tracker` + `role` and returns the same `(action, event_payload, reason)`
  tuple. Keep the route handler calling the alias so behaviour stays byte-identical for external
  callers (the in-pod wrapper today + any future caller during burn-in).
  - **Acceptance**: function is importable as `from orchestrator.routes.consensus import
    derive_next_action`; existing route tests pass without change; new unit test asserts in-process
    + HTTP route return identical results for the same tracker snapshot.
  - **Files affected**: `orchestrator/routes/consensus.py`,
    `orchestrator/tests/test_consensus_next_action.py`.

- **[TASK-2-2]** Create `orchestrator/on_demand_spawner.py` with an `OnDemandSpawner` class. It owns:
  - A reference to the `KubernetesSpawner`, the `PhaseIdleBudgetTimer` (slice 1), the
    `OrchestratorSessionKeepAlive` (task-2-6), and the orchestrator's `GatewayClient`
    (so it can call `register_session(...)` directly at phase start).
  - A `tick(pipeline_id, phase, roles)` API that, for each role in `roles`, calls
    `derive_next_action(tracker, role)`:
    - `wait` → no spawn; do nothing.
    - `complete` → no spawn; the orchestrator's phase-completion check (already exists) handles
      transition.
    - `confirm` → spawn one pod with the same composed prompt path as `propose/ack/nack` (the
      agent calls `mcp__brc__confirm` inside). No special-case path.
    - `propose | ack | nack` → call `compose_event_prompt(role, event_payload, ...)` in-process,
      then call `OnDemandSpawner.spawn_event(role, prompt, model_decision)` (task-2-4).
  - A `record_phase_start(pipeline_id, phase, roles, slice_id?)` API that performs **per-role
    phase-start wiring** (BLOCKER 2 & BLOCKER 3 resolution). For every role in `roles`, it:
    1. **Creates the gateway session** (BLOCKER 3 resolution) by calling
       `GatewayClient.register_session(container_id=f"{pipeline_id}-{role}-session",
       agent_role=role.value, pipeline_id=pipeline_id, phase=phase, branch=worktree_branch,
       repos=..., upstream=..., upstream_model=..., retry_transient=True)` — the same API
       `kubernetes_spawner.spawn_agent_job` calls today at
       `kubernetes_spawner.py:761-794`, lifted out to phase start so it runs once per
       `(pipeline_id, role)` instead of once per spawn. The returned `SessionInfo.session_token`
       is captured.
    2. **Registers the token in keep-alive**: calls
       `OrchestratorSessionKeepAlive.register(pipeline_id, role, token,
       idle_timeout_minutes=DEFAULT_SESSION_IDLE_TIMEOUT_MINUTES)` (task-2-6) so the validate
       cadence kicks in.
    3. **Pre-warms the worktree PVC** by ensuring the per-role PVC exists / is mounted
       (reusing `KubernetesSpawner`'s existing per-role worktree creation path — feedback Q3
