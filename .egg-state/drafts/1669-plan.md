# Plan: Block direct git push in concurrent mode

## Summary

Add concurrent-mode push enforcement to the gateway by introducing a `consensus_push` marker that flows from `egg-orch consensus propose --push` through the git wrapper to the gateway. When `EGG_CONCURRENT_MODE=true`, the gateway rejects pushes from pipeline agents that lack this marker, forcing all pushes through the BRC consensus protocol. This structurally enforces the "all changes must be reviewed" invariant instead of relying on agent compliance.

**Risks / edge cases**: Infrastructure pushes (checkpoints, pipeline state) are already exempt and the new check is placed after that exemption. Non-concurrent pipelines are unaffected. A `CONCURRENT_PUSH_ENFORCEMENT` killswitch follows the existing `PUSH_TARGET_ENFORCEMENT` pattern for emergency bypass. Agents could theoretically set `EGG_CONSENSUS_PUSH=1` themselves, but this is acceptable — the goal is structural enforcement against accidental misuse, not cryptographic prevention.

## Implementation

### Phase 1: Implement

Add the consensus_push marker flow (orch_cli → git wrapper → gateway) and gateway enforcement with tests.

**Tasks**:
1. **[task-1-1]** In `sandbox/egg_lib/orch_cli.py:cmd_consensus_propose()` (~line 1120-1131), pass `EGG_CONSENSUS_PUSH=1` in the subprocess environment when executing `git push`. Use `env={**os.environ, "EGG_CONSENSUS_PUSH": "1"}` in the `subprocess.check_output()` call. This marks the push as originating from the consensus protocol. Acceptance: `cmd_consensus_propose()` with `--push` flag passes `EGG_CONSENSUS_PUSH=1` to the git subprocess.
2. **[task-1-2]** In `sandbox/bin/git:push_via_gateway()` (~line 226-237), read the `EGG_CONSENSUS_PUSH` env var and include `"consensus_push": true` in the JSON payload sent to the gateway when it is set to "1". Add it to the `json.dumps()` call that builds the payload. Acceptance: The git wrapper includes `consensus_push: true` in the push payload when `EGG_CONSENSUS_PUSH=1` is set.
3. **[task-1-3]** In `gateway/gateway.py:git_push()`, add a concurrent-mode push enforcement check after the push target enforcement block (~line 814) and before the branch ownership check (~line 817). When `EGG_CONCURRENT_MODE` env var is `"true"` (case-insensitive) AND the session has a `pipeline_id` AND the push is not an infrastructure push AND `data.get("consensus_push")` is not truthy, return a 403 error with message: `"Direct push blocked in concurrent mode. Use: egg-orch consensus propose --push"` and details including `mode`, `pipeline_id`, and `requirement`. Add a killswitch: `CONCURRENT_PUSH_ENFORCEMENT` env var (default "true"), following the `PUSH_TARGET_ENFORCEMENT` pattern at line 784. Acceptance: Gateway returns 403 for direct pushes in concurrent mode; passes consensus-marked pushes through.
4. **[task-1-4]** Add tests in `gateway/tests/test_concurrent_push_block.py` covering: (a) push blocked in concurrent mode without consensus_push marker, (b) push allowed with `consensus_push=true` in payload, (c) push allowed when `EGG_CONCURRENT_MODE=false`, (d) push allowed for non-pipeline sessions (no `pipeline_id`), (e) killswitch `CONCURRENT_PUSH_ENFORCEMENT=false` disables enforcement, (f) infrastructure pushes are exempt. Follow the test patterns from `gateway/tests/test_push_error_enrichment.py`. Acceptance: All 6 test scenarios pass.
5. **[task-1-5]** Update `sandbox/agent-config/rules/mission.md` line 66 to reflect that direct push is now **blocked** in concurrent mode (not just recommended against). Change wording to make it clear the gateway enforces this. Also update the 403 error message in `sandbox/bin/git` (~line 274-288) to include a concurrent-mode-specific hint when the error is about concurrent push blocking. Acceptance: Agent rules accurately describe the enforcement; git wrapper shows helpful error for concurrent push blocks.
