# Plan: /sdlc auto-resolve phase_gate follow-up decisions from captured context

## Summary

The /sdlc skill already surfaces draft-embedded decisions upfront during `phase_gate` HITL handling (Step 5) and attaches the collected answers to the phase_gate resolution's `context` string. But when the orchestrator subsequently registers those same questions as standalone `choice`/`feedback` `pending_decisions` on later polls, the skill's per-decision handlers have no memory of the earlier answers and re-prompt the user. The fix (Option 1 from issue #1905, skill-only) introduces a persistent `resolved_questions_map` that Step 5 populates; the `choice` and `feedback` handlers consult it before prompting and auto-resolve on a compatible match. The orchestrator protocol (`_parse_resolution` / contract decision registration) is explicitly not modified.

**Risks / edge cases**:
- Question rephrasing by the refiner between the draft and the registered decision: normalized-exact match (case-insensitive, whitespace-trimmed) will miss, and the skill falls back to prompting — this is the correct behavior and is explicitly called out as a non-goal in the issue.
- A captured free-text ("Other") answer that isn't in a `choice` decision's `options` list: the handler must detect the mismatch and fall back to prompting instead of forcing an invalid selection.
- A `feedback` group where some questions match captured answers and others don't: prefill the matches, prompt only for the unmatched, merge into a single `provide_input` call.
- Multiple phase_gates over the pipeline lifetime: newer answers overwrite older ones by normalized question key; no explicit map clearing needed.
- Transparency is an acceptance requirement: each auto-resolution must produce a user-visible note so an incorrect match is catchable.

## Implementation

### Phase 1: Implement

Edits are confined to `skills/sdlc/SKILL.md`. No code or tests change — the skill is a markdown behavior spec. Verification is manual by re-running `/sdlc` on an issue whose refiner produces embedded `<!-- egg-hitl-decision -->` markers.

**Tasks**:
1. **[task-1-1]** In `skills/sdlc/SKILL.md` Phase 4 (starting at `## Phase 4 — HITL`), insert a new subsection (above the existing `### For phase_gate decisions:` header) titled `### Resolved Questions Map` that defines `resolved_questions_map` as a session-scoped in-memory dict of `{normalized_question_text → answer}`, specifies the normalization rule (lowercase + `strip()`), and states that both the phase_gate Step 5 handler populates it and the choice/feedback handlers consult it. Then update Step 5 of the phase_gate handler (currently lines ~632–656) to explicitly record "As you collect each answer, also store it in `resolved_questions_map` keyed by the normalized question text" alongside the existing Resolved Questions summary string. Acceptance: the SKILL.md file defines `resolved_questions_map` once, explains normalization, and Step 5 references populating it.
2. **[task-1-2]** In `skills/sdlc/SKILL.md` the `### For choice type decisions:` section (currently lines ~717–733), prepend a "Before prompting" paragraph instructing: (a) compute `normalized_q = decision.question.strip().lower()`, (b) look up `resolved_questions_map[normalized_q]`; if present, compare its value against each entry of `decision.options` using the same normalization — if a match exists, skip `AskUserQuestion`, call `provide_input` with `{"action": "select", "selected": "<matched option verbatim>"}`, and print a one-line note of the form `Auto-resolved <decision_id>: selected '<option>' from captured context.`; (c) if no match or no compatible option, fall through to the existing prompt flow. Acceptance: the choice handler documents the consult-before-prompt flow, the matching rule, the fall-through behavior, and the user-facing note.
3. **[task-1-3]** In `skills/sdlc/SKILL.md` the `### For feedback type decisions:` section (currently lines ~735–749), prepend a "Before prompting" paragraph instructing: (a) for each question in the `questions` array, compute `normalized_q = question.question.strip().lower()` and check `resolved_questions_map`; (b) collect matches into a prefilled `answers` dict keyed by the question's `id` (or the `q-<1-based index>` fallback described in the existing paragraph); (c) if all questions are prefilled, skip `AskUserQuestion` entirely; otherwise present only the unmatched questions via `AskUserQuestion` and merge the new answers into the prefilled dict; (d) call `provide_input` with the merged `{"action": "submit_feedback", "answers": {...}}`; (e) print a one-line note naming the decision ID and which question IDs were auto-resolved from captured context. Acceptance: the feedback handler documents per-question lookup, partial-match merging, the all-matched fast path, the single merged `provide_input` call, and the user-facing note.
