BLOCKER 1 — Slice 2 coexistence is a correctness hazard and is unspecified. Task 2-8 says "the orchestrator is actively spawning per-event pods alongside the long-lived wrapper pods. The two paths coexist in this slice for one PR-internal commit and are made mutually exclusive in slice 3." But the in-pod wrapper loop at consensus_wrapper.py:565-602 *also* calls `egg-orch brc next-action` and would invoke the agent for the same event. Two pods both running `compose_event_prompt` and firing `mcp__brc__propose`/`ack`/`nack` for one actionable event causes double-commit, double-BRC-verb emission, and tracker races. Even within a single PR's intermediate commit, slice 2's integration test (task 2-8 acceptance) can't pass without specifying the suppression mechanism on at least one side. Please specify: shadow-mode no-op spawner in slice 2 until slice 3 cuts over, OR an env-keyed early-return on one side (analogous to task 1-3's `EGG_PHASE_IDLE_BUDGET_OWNER=orchestrator` pattern — e.g. an `EGG_EVENT_LOOP_OWNER=orchestrator` short-circuit at the top of the wrapper's `while true` loop in slice 2), OR fold the cutover into a single atomic task so coexistence never exists.

After slice 3 retires the wrapper (task 3-1), it is undefined whether `spawn_all` still runs (registering roles without spawning?), is repurposed to registration-only, or is removed entirely. Task 3-2 says `_spawn_agent` "no longer builds the wrapper command; the on-demand path constructed in task-2-4 is now the only path", but does not address what calls `_spawn_agent` from `spawn_all` anymore. No task explicitly wires `OnDemandSpawner.record_phase_start` into the phase-start path. Please add an explicit task (in slice 2 or slice 3) that names: (a) the call site that invokes `record_phase_start` at phase start, (b) the disposition of `spawn_all` post-slice-3 (retired, registration-only, or pruned to per-role registration), and (c) the consensus-tracker registration path under the on-demand model.

Task 2-6 builds `OrchestratorSessionKeepAlive` with a `register(pipeline_id, role, token, idle_timeout_minutes)` API that already requires a token. The plan never names which task or module *creates* the per-`(pipeline_id, role)` session and obtains the initial token. Today the wrapper triggers session creation implicitly on first gateway call (per gateway/session_manager.py); under the orchestrator-owned model this must become explicit.
